# マップ追加の前提となるゲームの表と制約

> 対象: 電波人間のRPG2 (`kahara`) v1.1.0。分類: ゲーム既存仕様。
> 根拠: [再編前の解析記録](https://github.com/sweshelo/naauao/blob/27cc7ec6682589c764906ada88e78f5d04d57cc2/new-map.md) と本文に記す関数・実データ。従来の「確定」は元の解析で確認した範囲を指し、今回の再編で ROM 全体を再検証した意味ではない。
> アドレスは特記なき限り実行時/Ghidra アドレス (code.bin の位置 = アドレス − `0x100000`)。RPG3 には適用しない。

既存ダンジョン内のマップ追加に関係する解析結果。PNMP の形式・フック・Panana の実装は [実装設計](../integrations/panana/new-map.md)。元文書と照合できるよう節番号を保つ。

## 1. マップの表を読む処理 (確定)

code.bin の全体からリテラルプールの語を走査し、表の中を指すポインタをすべて洗い出した結果です。

| 表 | 置き場所 | 読む関数 | 行数の即値 |
|---|---|---|---|
| 区画の表 (205 行 × 40 B = `{map hash, 区画 1〜9 の hash}`) | 0x4C1A74 (.rodata、1 個だけ) | `FUN_002d9b18` だけ (リテラル 0x2D9C74) | `cmp r0, #0xCD` (0x2D9B68) |
| ダンジョンの表 (56 行 × 16 B = `{ダンジョン ID, 名前 "D01", マップ数, マップの行の配列}`) | 0x4C3AFC (.rodata) | `FUN_0020e384` (マップ → mapData のキー)、`FUN_002f1f48` (マップ → 行)、`FUN_002f8e1c` (マップ → ダンジョン ID) | 3 関数とも `< 0x38` (ダンジョンの行数) |
| マップの行 (0x1C B) | 0x5204F4 (.data) | 上のダンジョンの表の +0x0C 経由だけ。ほかは `FUN_002f1f48` / `FUN_0020e384` の既定値 (行 0 = D01B01001) | なし |
| mapData のキー (205 個 + 2) | 0x4C1738 (.rodata) | 起動時の静的初期化 (0x488264〜0x4889A8、`ldr`/`str` 205 組の展開) がマップの行 +0x10 に写す。`FUN_0020e384` は +0x334 / +0x338 (206・207 番目、特別なマップ用) を直接読む | なし (展開済み) |
| ワールドマップの区画 (4 行 × 0x20 B) | 0x4C3A7C | `FUN_002d9ac4` (4 つの hash の比較) + `FUN_0020e4a8` ほか 8 関数 | 関係しない |

- 区画 0〜9 の取り出し (`FUN_002d58ac`、`FUN_0020e424` など、[map.md](map.md) §2 の表) は、すべて `FUN_002d9b18(out, map, k)` を通る。区画の表を読むのはこの 1 関数だけ。
- `FUN_002d9b18` は、見つからないと行番号 −1 (= 表の 40 バイト手前、キーの配列の末尾) を読み、その値でマップ DB を引く。今は未知の hash を渡すとごみを読む。
- ダンジョンの表を回す 3 関数は、どれもマップの hash を比べるだけ。行の位置 (配列の何番目か、表全体の何番目か) を使う処理はない。そのため、配列を別の場所に移しても動く。
  - `FUN_002f1f48` の呼び出し元 (`FUN_001c4ec4`、`FUN_001ca5a0`、`FUN_0021f9f4`、`FUN_00237978`、`FUN_002f8bd0`) は、戻り値の欄を読むだけ (下の表)。行の位置から番号を計算する処理 (0x1C で割る処理) もない。

### マップの行 (0x1C バイト)

| 位置 | 型 | 内容 | 使い手 |
|---|---|---|---|
| +0x00 | u32 | マップの hash | 3 関数の検索 |
| +0x04 | s32 | 階 (負 = 地下 B、正 = 地上 F、0 = 屋外) | `FUN_0021f9f4` (ランタイム +0xA8C8)、階の表示 `FUN_00237978`、`FUN_001c4ec4` (mapGroup のフラグ 8 かつ階 ≥ 0 なら `FUN_0021ff80`) |
| +0x08 / +0x0C | u32 | ワールドマップとのつながり (OUT 系のマップだけ。+0x08 = 0xA8654391 など) | `FUN_001ca5a0`。ダンジョンの中のマップは 0 / 0 |
| +0x10 | u32 | mapData のキー (ファイルでは 0、起動時に埋まる) | `FUN_0020e384`、`FUN_002f8bd0` |
| +0x14 | u8 | 1〜5 (186 行が 3)。ランタイム +0xA8CB に写す。推定: 表示・カメラの種類 | `FUN_001ca5a0` |
| +0x18 | char* | マップのコード ("D01B02001") | `FUN_001c4ec4` (M02 / M05 の OUT の判定) |

### 表の複製に注意 (確定)

マップの行の表は、ヘッダーで定義された `static` の配列らしく、**.data に 128 個の複製**がある (0x518DF0〜0x5E0C38、どれも同じ中身)。mapData のキーの配列も .rodata に 128 個、それぞれに静的初期化がある。
生きているのは 0x5204F4 の 1 個だけ (ダンジョンの表 0x4C3AFC が指す)。ダンジョンの表の複製 0x4C41C0 (→ 0x521B70) も、どこからも参照されていない。
残りの複製は静的初期化が +0x10 を書くだけで、読まれないと解析されている。ただし根拠はリテラル走査であり、レジスタで合成されるアドレスまで排除したものではない。

## 3. マップの数に依存するセーブ・配列 (確定)

- セーブ変数 (flagData.bin、150 行) に、要素数が 205 前後でマップ番号で引くものはない。
  - 0x6B〜0x6F (210 個) はモンスター (+0x4A >> 4) で引く。0x8D (57 個) はダンジョン ID、0x92 (344 個) は mapGroup +0x22 からの「ダンジョンごとの枠」(+0x24 個) で、マップの番号ではない。
- **オートマップ** (ミニマップの踏破) だけが、マップごとのセーブ。
  - セーブ +0x410 + 枠 × 4 のポインタ (16 枠) → 14 件 × 0x9C バイトの記録。1 件 = `{u32 マップの hash, 0x98 B のビット列}`。ビット列は 30 × 40 セル (x 0〜29、y 0〜39、`FUN_0021a9e0`) で 1 ビット。
  - 枠 = `FUN_002f8de0(ダンジョン ID)`: D01〜D10 = 0〜9、K01〜K04 = 10〜13、S05 / S06 (ID 0x1C / 0x1D) = 14 / 15。ほかのダンジョン (町・祠・F 系など) にはオートマップがない。
  - 記録はマップの hash で探し、なければ空き (hash = 0) を割り当てる (`FUN_002f8cb0`、`FUN_002f8d40`)。**マップの番号には依存しない**ので、新しいマップもそのまま記録を 1 件もらえる。
  - 上限はダンジョンごとに 14 マップ。今のマップ数は D02 / D03 / D08 が 12、K03 が 11、ほかは 10 以下。14 を超えると、あふれたマップは「オートマップなし」(0 が返る。呼び出し元の `FUN_0021a9e0` は 0 のとき何もしない) になるだけで、壊れはしない。
- 宝箱などの状態 (セーブ変数 0x8E) は、ダンジョンの EventObject の行ごと ([map.md](map.md) §6)。新しいマップの宝箱には、そのダンジョンの EventObject に空いている行 (mapGroup +0x1C 未満) を使う。
- 今いるマップ (変数 0x50)、ワープ記録 (0x61)、テレポーター+ の記録は 32 ビットの hash をそのまま持つ。どんな hash でも入る。

## 5. マップ DB への追加 (確定)

- 索引の検索 `FUN_002d9a4c` (開始位置) / `FUN_002d99dc` (サイズ) は、先頭の件数 (u32) で範囲を決め、hash を **符号なし** (`cmp` + `lo`/`hs`) で比べる lower_bound。元のファイルも符号なしの昇順 (2082 件)。
- lower_bound は一致を確かめない。そのため、新しいマップの**区画 0〜9 の 10 個の hash は、すべて DB に入れる**。空の区画は、サイズ 0 のエントリにする (既存のマップも空の区画はサイズ 0)。
- 区画 0 の hash = マップの hash。区画 1〜9 は、ほかと重ならない新しい値にする。
- DB (約 553 KB) は起動時にまとめて読み込まれる。数 KB 増える程度なら問題ない見込み (推定、[PNMP のリスク](../integrations/panana/new-map.md) §7)。


## 6. 座標上限についての注意

オートマップの保存範囲 30 × 40 と、実行時のマップセル配列の安全な座標範囲は同じとは限らない。[map.md](map.md) §3 は x 方向 1 列あたり 30 セル (`0x438 = 30 × 0x24`) と記録している。旧追加設計にあった「y 0〜39」は保存範囲を根拠にした推奨で、実行時の安全性を確認した値ではない。既存データの最大 x 29 / y 25、Panana の 30 × 30 制限とも区別する。
