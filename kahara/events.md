# イベントとギミック

> 対象: 電波人間のRPG2 (`kahara`) v1.1.0。分類: ゲーム既存仕様。
> 根拠: [再編前の解析記録](https://github.com/sweshelo/naauao/blob/27cc7ec6682589c764906ada88e78f5d04d57cc2/events.md) と本文に記す関数・実データ。従来の「確定」は元の解析で確認した範囲を指し、今回の再編で ROM 全体を再検証した意味ではない。
> アドレスは特記なき限り実行時/Ghidra アドレス (code.bin の位置 = アドレス − `0x100000`)。RPG3 には適用しない。

マップ上の出入口・宝箱・キャラクター・ギミックの「動き」の仕組みです。v1.1.0 の解析結果で、アドレスは Ghidra 上のもの。
データの形は [map.md](map.md) (§2 区画、§6 EventObject、§8 モデル、§9 宝箱) を参照。全イベントの一覧は [reference/events.md](reference/events.md) (`tools/gen_reference.py` で生成)。
スクリプト (0x24) の行ごとの中身は [reference/scripts.md](reference/scripts.md)、抽出方法は [event-list.md](event-list.md)、Panana の UI は [実装メモ](../integrations/panana/event-list.md)。

確度: **確定** = コードとデータで確認。**推定** = 欄の使われ方からの推測。


## 1. 全体の流れ (確定)

```
マップの区画 (3 / 4 / 5 / 8) のレコード
  └─ EventObject の行 (ダンジョンのアーカイブ: mapGroup +0x0C の xXX_EventObject.bin)
       ├─ オブジェクト (モデル: map.md §8)
       └─ ハンドラ (区画・種類ごとのクラス) ── vtable[4] = 「動作の生成」(引数: EventObject +0x4D の種類)
                                                   └─ 動作のクラス (調べる・踏む・開ける …)
```

## 2. 状態 (確定)

- 行ごとに 2 ビットの状態を持つ。保存先はセーブ変数 0x8E の `mapGroup +0x1A + 枠`。
  - 枠は EventObject +0x44 (0xFFFF のときは行番号)。
  - 行番号が mapGroup +0x1C (ダンジョンの枠数) 以上の行は、状態を読み書きしない。
- 読み: `FUN_0031b10c(行)` → `FUN_0031bff4`。書き: `FUN_0031b0d8(行, 値)` → `FUN_003048f8`。
- **`FUN_0031aa2c(行)` = イベントの完了**: 行のオブジェクト (`FUN_002f973c`: オブジェクト +0x5E が行番号のもの) の +0x86 が 0 なら、次を行う。
  - EventObject の +0x4F → 状態 3、+0x4E → 2、+0x4D → 1 のうち、0 でない最初の欄の値を書く。
  - `FUN_0030cb88(obj, 1)` でオブジェクトを完了にする (扉・門は通れるようになる)。
- オブジェクトの操作 (スクリプトでの使い方):
  - `FUN_0031c970(行)`: 行のオブジェクト (なければ 0)
  - `FUN_0031c958(ハンドル, obj, 0)`: 32 バイトのハンドルを作る
  - `FUN_0031c834(ハンドル, アニメ, 0)`: アニメ。hardfp で s0 = 速さ (1.0)、s1 = 開始位置 (0.0) も渡す。s0 / s1 が不定だとアニメが進まない
  - `FUN_0031c89c(ハンドル)`: 解放
  - 効果音は `FUN_00317524(番号)`
- アニメの番号 (推定。ギミックのモデル共通):

| 番号 | 意味 | 使われ方 |
|---|---|---|
| 0x52 | 開いた姿 (扉) | D01: 読み込み時にスイッチが押されていれば、扉 (行 10 / 11) に |
| 0x53 | 開く | スイッチを押したとき、扉・門に |
| 0x54 | 閉じた・押されていない姿 | 床スイッチ (種類 0x1D / 0x1E) の初期 |
| 0x55 | 開いた・押された姿 | 床スイッチの初期、D01 の門 (gimk_03_gate_08) の読み込み時 |
| 0x56 | 押される | 床スイッチを踏んだとき (効果音 0x70) |
| 0x57 | 戻る | 床スイッチ 0x1D から降りたとき (効果音 0x6B) |

| +0x08〜+0x43 | 種類ごとの引数 (§4) |

床スイッチ 0x1D / 0x1E (確定):
- 作るときに自分の状態を読み、0 ならアニメ 0x54、それ以外なら 0x55 にする。オブジェクト +0x80 (押されている) もこれに合わせる。
- 毎フレーム、上に何か (+0x78 / +0x7C / +0x81) があって押されていなければ、`FUN_002d7548` で押す。
  - アニメ 0x56、効果音 0x70、パーティを押し戻したあと +0x80 = 1。
- 0x1D は、上に何もなくなると戻す (0x57、効果音 0x6B)。
- どちらも **ほかの行とのつながりを持たない** (状態の保存もしない)。バニラのデータでは使われていない。
  - ダンジョンのスクリプトが、自分のスイッチの判定に `FUN_002d7404` を呼んでいる。

## 5. スクリプト (種類 0x24、確定)

種類 0x24 の動作は、**ダンジョン (セーブ変数 0x4F) と行番号ごとにコードに直接書かれている**。
各ハンドラの「動作の生成」関数が、0x24 のとき `FUN_0030b788` (ダンジョン) で分岐し、さらに行番号で分岐して専用のクラスを作る。
例: 区画 5 の種類 2 のギミックは `FUN_001d1970`。ダンジョン 1 → `FUN_0017f688`、ダンジョン 0x13 → その中で行 10 / 11 / 15 / 16 …。

**スイッチと扉・門のつながりはデータにない。** 例 (D01 = 山のどうくつ):

| スイッチ (区画 5) | クラス (押したとき) | 対象 | 読み込み時 (押されていれば) | 押したとき |
|---|---|---|---|---|
| 行 2 (D01B02001 の (19.5, 16.5)) | `FUN_002583f4` | 行 10 = 扉 (19, 15) | アニメ 0x52 + `FUN_0031aa2c(10)` | カメラ演出 → `FUN_0031aa2c(10)` → アニメ 0x53 + 効果音 0x5C |
| 行 3 (D01B02001 の (19.5, 13.5)) | `FUN_00258924` | 行 11 = 扉 (19, 12) | 0x52 + `FUN_0031aa2c(11)` | 同上 |
| 行 4 (D01B02001 の (14.5, 6.7)) | `FUN_00258e54` | 行 13 = 門 gate_08 (13, 10) | 0x55 + `FUN_0031aa2c(13)` | `FUN_0031aa2c(13)` → 0x53 + 効果音 0x6F |
| 行 9 (D01B01001 の (14.5, 13.5)) | `FUN_00258284` | 行 1 = D01B01001 の門 (14, 15) | 0x55 + `FUN_0031aa2c(1)` | |

スイッチ自体は床スイッチ 0x1E のクラス (`FUN_00318e4c`) を作ってから、vtable を専用のもの (0x4FECA4 など) に差し替えている。

- このため、既存のスイッチと扉の組は、同じダンジョンの中で行番号を保ったまま動かすことしかできない (行番号を変えるとつながりが切れる)。
- 自由に組むには [イベント拡張 MOD §7](../integrations/panana/event-mods.md) を使う。
- 行を定数で完了させる (`FUN_0031aa2c(定数)`) 関数は 23 個ある。スクリプトの対象を探す手がかりになる。
  - 例: `FUN_0017f688` → 1, 10, 11, 13、`FUN_002583f4` → 10、`FUN_00259710` → 34, 35 …

## 6. 看板・会話のメッセージ

- 看板 (0x1F) と 0x21: +0x08 のメッセージを表示する。
- 一言 (0x01〜0x03): 常に +0x08。
- 会話 (0x07〜0x09): 話しかけた回数・+0x48・行の状態には関係なく、**ストーリーの進行 (セーブ変数) だけで** 4 つから選ぶ。上から順に判定 (`FUN_002e6af4` / `FUN_00216030`。0x8D[n] = `FUN_0031bac4(n+1)`、0x91[n] = `FUN_0031d774(n)`):

| 条件 | 台詞 |
|---|---|
| 0x91[0x18] / [0x19] / [0x1C] / [0x1D] がすべて 2 | +0x14 (クリア後) |
| そうでなく 0x8D[9] == 2 | +0x10 |
| そうでなく 0x8D[8] != 3 | +0x08 (序盤) |
| それ以外 | +0x0C (悪の組織を倒したあと) |

- 進行に合わせて別のキャラ (別の行) に入れ替えるのは、+0x00 / +0x04 と +0x4B / +0x4C の出現条件による。
- 扉 (0x14 / 0x15) の欄にメッセージはない (§4)。
- 旧調査のコードに直接書かれたメッセージ ID は 458 か所 (179 関数)。[event-list.md](event-list.md) の literal pool 走査は 1,024 ID と記録しており、集計範囲・単位が異なる。元スクリプトと対象 ROM が揃った再集計までは、458 を全 ID 数として使わない。例: `FUN_00261000` → 0x1E1E「地底人の記録1」、`FUN_004260cc` → 0x2182〜0x2187。ID を計算で作る箇所もあるので、「どこからも使われない ID」は判定しにくい。
- 再利用: EventObject の台詞 348 ID のうち、2 つ以上の行から使われるものは 0。1 つの行の複数の欄で同じ ID のものが 5 (例: d10 行 36 の +0x08 と +0x0C が 0x2126)。この走査で EventObject とコードの両方から使われるのは 0x1D76 (m02 行 25) だけ。コード直書きのうち 20 ID は複数の関数から使われる。
- メッセージ ID は通し番号で、ダンジョンの台詞は MessageField_JP.gsmb (0x1BDF〜0x21AF)。本文は `reference/events.md` に出す (本文中の Ď / ď / č などは声のタグで、画面には出ない。[messages.md](messages.md) の「本文の制御コード」)。

## 7. MOD 拡張 (別文書)

汎用スイッチ (0x30、PNSW) とボス戦 (0x31) は [Panana / elpulse の MOD 仕様](../integrations/panana/event-mods.md)。この2種類はバニラのイベント種類に含めない。

## 8. ゲーム既存のボス戦とイベント範囲

### 8.1 ゲームのボス戦の作り (確定)

- 決まった敵との戦闘は **`FUN_002fc790(固定の組の行, BGM)`** で始まる (`encounters.md` §5)。呼び出しは 31 か所で、ほとんどが区画 8 の範囲のスクリプト (種類 0x24)。
  - 例: F07OUT000 の行 2 (`FUN_0023d904`) は「0x91[0x10] が 2 でなければ、+0xA44 = 0x10 にして `FUN_002fc790(0x0C, 0x1C)`」。D05F01003 の行 23 (ポーン、`FUN_0027006c`) は同じ形で 0x91[0x0B]、組 9。
  - BGM は soundData の行 (0x1B / 0x1C / 0x1D = BGM_BATTLE_*)。
- **勝ったあと**: 戦闘の終わり (`FUN_001ce2e8`、vtable 0x4FBB30 の [3]) が、グローバル (`*0x564638`) +0xA44 (u16) の下位 8 bit を読む。
  - 勝ったとき (+0x3FB が 0、または +0x3FF が 0 でない) で、値 n が 0 でなければ 0x91[n] = 2 (`FUN_0031d710`)。そのあと +0xA44 を 0 にする。
  - n = 3 は負けてもよい戦闘 (パーティを回復する `FUN_00304884`)。
  - 負けたとき (+0x3FB ≠ 0 かつ +0x3FF = 0) は 0x91 を書かない。
  - スクリプトは「0x91[n] が 2 なら戦わない」で一度きりにしている。何度でも起きる戦闘 (E01OUT000 の行 4 など) は +0xA44 を書かない。
- 台詞と戦闘は別の範囲 (行) に分けることが多い (D05 の行 22 = 台詞、行 23 = 戦闘。D06 の行 15 / 16)。台詞の範囲の [4] (完了) が 0x91[n] = 1 にし、戦闘の範囲はそれを見る。

### 8.2 区画 8 の範囲の動作 (確定)

- 範囲のハンドラ (vtable 0x4FC634) の [2] = `FUN_0023d72c` が、行の **+0x4D / +0x4E / +0x4F の種類から動作を 3 つまで作る**。引数はそれぞれ行の **+0x08 / +0x1C / +0x30** (0x14 バイトずつ)。作るのは `FUN_002cdda4`、なければ [4] = `FUN_001f41c8` (種類 0x0B / 0x24)。
- [3] = `FUN_0023d82c` が、行の状態 (§2) で使う動作を選ぶ: 状態 0 → +0x4D の動作、1 → +0x4E (なければ +0x4D)、2 / 3 → +0x4F (なければ +0x4E、+0x4D)。
- 完了 (`FUN_0031713c`、動作の vtable [4]) は、状態 0 → 1、1 → 2 (+0x4E ≠ 0 のとき)、2 → 3 (+0x4F ≠ 0 のとき) と進める。
- つまり 1 つの行で「状態ごとに違うイベント」を作れる (ゲームのデータでは使われていない)。
- 動作のクラス: 基底 `FUN_0031b170(obj, 行)` (vtable 0x4FB518: [1] 解放、[2] 範囲に入ったときの処理 (コルーチン)、[3] なし、[4] 完了、[5] 0 を返す)。スクリプトは 0x10 バイトを確保して vtable の [2] (と [4]) を差し替える。
