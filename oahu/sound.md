# RPG3 (oahu) の BGM・効果音

RPG3 の音の形式と、BGM・効果音が**どこで決まるか** (マップ・ダンジョンの戦闘・決まった戦闘・コード)、戦闘の背景 (§3.5) をまとめる。アドレスは Update (v4096) の code.bin。RPG2 (kahara) の音は [kahara/encounters.md](../kahara/encounters.md) §4・§5。

## 1. 形式
- **RPG2 と同じ。** RomFS の `sound/sound.bcsar` (CSAR) に音 611 個の名前・種類・波形・シーケンスがあり、BGM と ME は `sound/stream/*.bcstm` (DSP ADPCM、クルーザーの 2 曲だけ PCM8) のストリーム。ストリーム・波形・シーケンスの 3 種類とも再生確認の記録がある ([検証に用いた実装](../integrations/panana/oahu.md))。
  - ストリームのファイル名は音の名前と違うことがある (音 `BGM_VILLA_DESERT` → `BGM_DESERT.dspadpcm.bcstm`)。CSAR のファイル表がパスを持つので、名前から組み立てずにファイル表を引く。
  - `sound/voice/` は音声合成 (電波人間の名前の読み上げ) のデータ。
- Update の RomFS は音を差し替えない (patchList の 11 アーカイブに音はない)。音は Base だけで読める。

## 2. soundData.bin (master `21350000`、597 行 × 0xC)
RPG2 の soundData (418 行) と同じ並び。行番号がゲームの「音の番号」で、各テーブル・コードはこの行番号で音を指す。

| off | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | サウンドアーカイブのアイテム ID (`0x01nnnnnn` = 音 nnnnnn)。行 0 は 0 |
| +0x04 | u32 | 0x340 (全行同じ) |
| +0x08 | u8 | 音量 (全行 100)。残りの 3 バイトは埋め草の D0 |

- 行 1〜36 が BGM (1 `BGM_TITLE` … 7〜10 `BGM_BATTLE_1〜4` … 24〜31 `BGM_CAVE_*`、32 `BGM_MAOU_TOWER`、35・36 `BGM_FISHING_1/2`)、37〜58 が ME (短い曲)、59 以降が効果音 (`SE_SYS_*`・`SE_FLD_*`・`SE_BTL_*` など)。
- 行 50 と 53 は同じ音 (`ME_FISH_GET_1`)。soundData から指されない音が 16 個ある (`BGM_EVENT_FESTA`、`ME_BANNER`、`SE_BTL_DROP1` など)。
- 音 → soundData の変換は、サウンド管理 (`*0x5A5B08`) の +0x56C に入るコールバック `FUN_001A68DC(行)` (行の +0x00 を返す)。`@0x2135F0` で登録する。

## 3. どこで鳴るか

### 3.1 マップ (mapData、167 行 × 7)
RPG2 と同じく **[4] フィールドの BGM、[5] 戦闘の BGM、[6] 足音** (いずれも soundData の行。[0]〜[3] はタイルセットなどの資源)。

- マップの mapData の行は、マップのキーで mapData の索引 (行のあとの追加領域、ハッシュ → 行) を引いて決まる (`FUN_0048EE20`、結果は `*0x59EE60` +0xF4)。どのマップがどのキーを持つかはマップの解析 (#66) の範囲。
  - 状態 1〜3 (ワールドマップなど) ではキー `0xDAF3A36F` (`@0x556288`) = 行 164 を使う。
- **フィールドの BGM**: `FUN_0024CB8C(mapData[4], マップのキー, …)` が鳴らす行を決める (`@0x24CB3C`、`@0x24CF20`)。ふつうは [4] のままだが、次のときは差し替える。

  | 条件 | 行 |
  |---|---|
  | キー `0xA8654391` (ワールドマップ。全ダンジョンの mapGroup +0x04 がこの値) | 状態 (`FUN_0023BC6C`、`FUN_0021395C(3〜6)`、フラグ 0x59 / 0x5B) により 3 `BGM_WORLDMAP` / 4 `BGM_FUNE` / 5 `BGM_CRUISER_1` / 6 `BGM_CRUISER_2`。名前からは乗り物 (船・クルーザー) と推定 |
  | キー `0x7D6021D8` で `FUN_001EDCF0(0x1E, 2)` が真 | 0x23 `BGM_FISHING_1` |
  | `FUN_002AB0BC(キー)` = 0x16 で `FUN_001ED9B8(3)` が真 | 0x11 `BGM_ELEGY` |

- **戦闘の BGM (ふつうの戦闘)**: マップの行ではなく、**ダンジョンの行の [5]**。ダンジョンに入ると mapGroup +0x2E がセーブ +0x5469 に入り (`@0x24D1B0`)、戦闘を始めるときに mapData[*(+0x5469)][5] を `FUN_00213970` で鳴らす (`@0x25047C`、`@0x2F8D40`)。
  - したがって、ダンジョンが指していない行の [5] は鳴らない可能性が高い (推定)。元のデータではほぼ全行 7 `BGM_BATTLE_1`。8 `BGM_BATTLE_2` はボス再戦の館 (行 96・97)、10 `BGM_BATTLE_4` はコロシアム (行 72・73) と行 164。
- 足音 [6] は 88〜92 (`SE_FLD_STEPS1〜5`)。読み手は `@0x1C3D14` ほか (未確認)。

### 3.2 mapGroup (89 行 × 0x34) の音まわりの欄
| off | 型 | 内容 |
|---|---|---|
| +0x04 | u32 | 0xA8654391 (ダンジョンのある全行。ワールドマップのキーと推定) |
| +0x1C | u32 | 名前 (MessageSystemCommon。例 行 1 = 0x89「ドローンのどうくつ」) |
| +0x2E | u8 | **ダンジョンの mapData の行** (戦闘の BGM はこの行の [5]) |
| +0x2F | u8 | 2 つ目の mapData の行 (町は家の中など。0 = なし。居住島はすべて 24) |

- RPG2 の mapGroup +0x26 / +0x27 に当たる。

### 3.3 決まった戦闘 (ボス戦など)
- **`FUN_0021112C(&群れのハッシュ, BGM)`** (群れは monsterGroup の索引で引く) と **`FUN_00211228(群れの行, BGM)`** が決まった群れとの戦闘を始める。RPG2 の `FUN_002fc790(行, BGM)` に当たる。BGM は `FUN_00213970` で鳴らす。
- **BGM が 0 のときは群れで決まる: monsterGroup +0x32 bit2 (0x04) が立っていれば 8 `BGM_BATTLE_2`、なければ 7 `BGM_BATTLE_1`** (`@0x2111C0`)。bit2 が立っている群れは Update の master で 22 個 (Base では 24 個。9・19・20・21・28・42・43・50・63・76・90・91・93・94・95・100・111・112・113・115・116・187。クリムゾンキーパー・ジャシン・ドローンＺ などボス)。
- **モンスターごとの BGM はない。** monsterParameter に音の欄は見つからず、曲は群れのビットか呼び出し側の引数で決まる。
- コードの中の呼び出し (群れはリテラルのハッシュから引いたもの):

  | `@0x2BAE18` / `@0x2BB264` | 0 → 8 | 19 クリムゾンキーパー / 20 フロストキーパー |
  | `@0x2C1524` | 9 | |
  | `@0x2C1934` / `@0x2D1DB0` / `@0x30DFA8` | 0 → 8 | 111 ブラックナイト / 187 ポーン / 76 テンペスター |
  | `@0x2F4478` / `@0x3829C4` | 7 | 116 キラービースト |

  | `FUN_00211228` を 7 / 8 / 9 で呼ぶ 10 か所 (`@0x353968`、`@0x3621D0`、`@0x36AEB4` など。ほかに 0 で呼ぶ 3 か所) | 7〜9 | 呼び出し元の構造体の欄 (+0x14 など) の行 |

#### イベントの戦闘 (EventObject) の BGM (確定)
区画 8 の動作の生成 `FUN_00272034` が戦闘のクラスを作る。コンストラクター **`FUN_00384120(mem, 種類, 引数1 & 0xFF, 引数2 & 0xFFFF, 引数3)`** は +0x14 = 群れの行 (monsterGroup の行番号)、+0x16 = フラグ (0 でなければ `FUN_001EE8B8` が 2 以上なら戦わない、`FUN_001EE958` で進める)、+0x18 = 引数 3 を持つだけで、**BGM の欄はない**。BGM はクラス (vtable) ごとの定数:

| クラス (vtable → 実行) | 作られる所 | BGM |
|---|---|---|
| 0x586BB4 → `0x3840C8` (基本形) | 動作の種類 0x0D (全ダンジョン共通)。ダンジョン 5 の行 0x1E、ダンジョン 8 の行 0x2B もこの形 | **0** → 群れの bit2 で 8 / 7。+0x15 が立っていれば +0x10 のハッシュで `FUN_0021112C` |
| 0x586BD4 → `0x384164` | 種類 0x2E (スクリプト)、ダンジョン 0x0B の行 0x3C / 0x3D / 0x3E (`FUN_001A2734`) | **9** `BGM_BATTLE_3` |
| 0x585E80 → `0x36219C` | ダンジョン 10 の行 8 | 9 |
| 0x585EE0 → `0x36406C` | ダンジョン 0x0C の行 0x0F | 9 |
| 0x5860BC → `0x36AE80` | ダンジョン 0x10 の行 0x15 (`FUN_001A3848`) | 8 |
| 0x5860FC → `0x36B104` | ダンジョン 0x11 の行 2 | 8 |
| 0x58613C → `0x36B388` | ダンジョン 0x12 の行 0x12 | 8 |
| 0x585B8C → `0x353674` | ダンジョン 2 の行 0x0F | 7 (`@0x353968`、推定: 同じクラスの関数) |

- 「ダンジョン」= `FUN_004EE968(*+0x5C)` の値、「行」= そのダンジョンの EventObject の行番号 (ハンドラ +4)。
- ほかに `FUN_00211228` を定数で呼ぶ所: `@0x364140` / `@0x3641AC` / `@0x364210` (7、クラス未特定)、`@0x1E67AC` / `@0x31B53C` (0、宝箱の種類 4 など)。
- 以前の記録の「`FUN_00384120` の BGM 9」は、作ったあと vtable を 0x586BD4 などに差し替えた派生クラスのこと。基本形は BGM 0 (群れで決まる)。
- monsterGroup +0x32 のほかのビット: bit1 (`FUN_004EACD4`) と bit2 (`FUN_004EAF7C`) は戦闘の初期化で戦闘のフラグ (+0x2D662 bit0) を立てる (逃げられない等と推定)。BGM・背景には使わない (確定: 読み手はこれと上の BGM の選択だけ)。値は 0x80〜0x87 (bit7 は全行)。

### 3.4 コードで決まった BGM
`FUN_00213970(行, …)` (BGM を鳴らす。呼び出し 28 か所) に定数を渡しているところ:

| 行 | 呼び出し | 場面 (推定) |
|---|---|---|
| 0x17 `BGM_ENDING` | `@0x1D7AE8`、`@0x1D8CB8`、`@0x1D9AC8` | エンディング |
| 0x0B `BGM_DENPAISLAND` | `@0x209AA4` | |
| 0x0A `BGM_BATTLE_4` | `@0x2E040C`、`@0x3217E0`、`@0x346730` | 特別な戦闘 (`FUN_00213388(1)` のあと) |
| 0x23 `BGM_FISHING_1` | `@0x24E7BC`、`@0x327E68` | 釣り |

- ほかに、曲の一覧を順に回す処理 (`@0x27E0C0`。+0x0A からの u16 の並び) と、イベントのスクリプトから鳴らすもの (`@0x27EA00` など) がある。スクリプトの中の BGM は未集計。

### 3.5 戦闘の背景 (確定)
RPG3 の戦闘の背景は**マップの資源 (mapResource) の欄**で、群れやモンスターには背景の欄がない (RPG FREE! は群れが背景と BGM の行を持つ。[lanai/battle-field.md](../lanai/battle-field.md))。

- **`FUN_001C3D08`** (戦闘の初期化 `FUN_001C3274` の中) だけが読む。
  1. `R = *(u8 *)(*0x59EE60 + 0xF4)` (フィールドのオブジェクトの「今の mapData の行」)
  2. `mapData[R]` (master +0x364) の **[1]** で `mapResource` (master +0x380) の行を引く
  3. その **+0x10** が 0 でなければ `FUN_002CB7BC(*0x5A59DC, 0x52120000, +0x10)` でアーカイブ `52120000` のそのエントリを読んでモデルにする (`@0x1C3D98`)。+0x04 / +0x08 (地面のテクスチャ) があれば `FUN_0027B670` でそれも貼る。
  4. +0x10 が 0 なら何も読まない (背景なし)。
- アーカイブ `52120000` を参照するコードはこの 1 か所だけで、btmp のハッシュをコードに書いた所もない。→ **背景を差し替える処理は「R を変える」ことだけ**。
- R を書くのは `FUN_0048EE20(obj, 状態, 行)` だけ (+0xF4 = 0、+0xF6 = 状態。状態 1〜3 ならキー `0xDAF3A36F` の行 = 164。第 3 引数が 1〜0xA6 ならその行):

  | 呼ぶ所 | 渡す行 | 場面 |
  |---|---|---|
  | `@0x2274F4` (`FUN_0022728C`、vtable 0x57E678。`FUN_002258B8` から) | **セーブ +0x5469** (= ダンジョンに入ったときの mapGroup +0x2E) | マップ (フロア) の読み込み (推定)。ダンジョン・町ではこれ |
  | `@0x24D258` (`FUN_0024D050`、vtable 0x57EEE8) | キー `0xF2283D05` の行 = **144** | +0x546A = 3 にする場面。行 144 は [1] = 4、[4] = 3 `BGM_WORLDMAP` なのでワールドマップへ出る処理と推定 |
  | `@0x2F8E34` (`FUN_002F8C10`、ふつうのエンカウント) | ワールドマップ (マップの種類 2) のときだけ `FUN_004C7048(x, z)` = **worldmapParts (master +0x604) の足元の行の +0x0A**。0 ならキー `0xB63D5E74` の行 = 161 | ワールドマップの戦闘 |
  | `@0x2E03BC` (`FUN_002E01F8`)、`@0x3465D8` / `@0x3466E4` | 状態 3 / 2 / 3、行 0 → **164** (`btmp_15_arena`) | 特別な戦闘 (このあと `FUN_00213970(10)` = `BGM_BATTLE_4`) |

- 決まった戦闘 (`FUN_0021112C` / `FUN_00211228`) は R を変えない → **ボス戦の背景は今いるダンジョンの背景**。
- 背景は R (`+0xF4`)、ふつうの戦闘の BGM はセーブ +0x5469 と、読む場所は別だが、ダンジョンではどちらも mapGroup +0x2E の行になる。ワールドマップでは両方とも worldmapParts +0x0A の行。
- 戦闘の初期化 (`FUN_001C3274`) は BGM を鳴らし直さない。
- コロシアム (mapData 行 72 / 73) と再戦の館 (96 / 97) は [1] が 4 / 24 / 25 で、mapResource 24 / 25 の +0x10 は 0。そこで戦うのは上の特別な戦闘 (行 164 = arena) と推定。
- mapData 160〜166 はワールドマップの地形用 ([1] だけ、[5] = 7、164 だけ [5] = 10)。worldmapParts 95 行の +0x0A は 0 / 160〜166 (行 0 と 94 が 0)。

#### 52120000 (Base、version 7、22 エントリ、すべて種別 8・LZ)
名前はエントリの 0x180 B のヘッダーの UTF-16 パス (`rom:/cg/model/map/map_parts/<名前>/<名前>.bch`)。
- エントリのヘッダー (22 個共通): +0x00〜+0x0B は 0、+0x0C = `01 00 01 00`、+0x14 = 0x30、+0x18 = 0xC8 / 0xCC、+0x34 = 2、**+0x38 = BCH の位置、+0x3C = BCH のサイズ** (22 個すべてで +0x38 + +0x3C = 展開後のサイズ)、+0x40 = 0x54 (パスの位置)。パスの後に f32 の 1.0 が 3 つ (拡大率と推定)。
- BCH の位置は 0x180 が 16 個、**0x100 が 6 個** (btmp_12_flat・13_sand・14_sea・08_iceA・18_hell・19_snow)。パスと 1.0 の並びが 0x100 以内に収まると 0x100 になる (0x80 単位にそろえると推定)。ヘッダーの +0x38 を読むコードは未特定 (データでは全件一致)。
- 中身は 22 個とも BCH (CGFX はない)。BCH のヘッダーを確かめるのは `FUN_00454048` ('BCH\0' とバージョン)。CGFX のマジックを比べるコードは見つからない。
