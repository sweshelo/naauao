# RPG3 (oahu) のストーリーの進行度とナビ

R ボタンの「ナビ」が次にやることを教えてくれる仕組みから、**ストーリーの進行度を表すセーブの値**を特定し、シナリオの段階・テキスト・進行の条件を ROM から洗い出した。オリジナルの MOD ストーリーを作るための下調べ。アドレスは Update (v4096) の code.bin (`analysis.md` §1)、マップ・EventObject の用語は `map.md`。

確度: **確定** = コードで読み方を確認し、実データで裏付けたもの。**推定** = 呼び出し元とデータの形からの推測。

結論を先に書く:

- **進行度 = セーブのキー 0x74 (16 bit、0〜99)** (確定)。ナビはこの値を行番号にして master の `mapNavi.bin` (135 行 × 0x30) を引き、見出しとヒント 4 つを出す。100 以上の行 (100〜134) は図鑑・釣り・植物などのやりこみのヒント。
- 進行度はシナリオの**章立て (表示用の目印)** で、イベントの出現条件にはほとんど使われない。イベントの出し入れを決めているのは、**全体の物語の値 0xF9[0〜45] (u8)** とフラグ 0xFA[0〜19]、ダンジョンごとの値・フラグ、EventObject の行ごとの状態 (§3)。
- 進行度・物語の値を書くのは **code.bin のスクリプトのクラス** で、値は命令の即値 (`mov r0, #段階` → `FUN_00213010`) に埋め込まれている (§4)。データ (RomFS) だけでは書き換えられないが、書き込み箇所は全部特定できた (§5 の表)。
- 物語の値 0xF9[k] は、多くが「ボスごとに 0 → 1 (出会った) → 2 → 3 (倒した)」の段階 (§3.2)。EventObject の消える条件 (0x15「0xF9[k] ≥ v」) と名前つきの条件 (0x01「0xF9[k] = 3」) がこれを読む。

## 1. ナビの表 `mapNavi.bin` (確定)

master (`21350000`) のエントリ `681D3800`。GS テーブル (135 行 × 0x30、テーブル名 `MapNavi`)。読み手はマスター +0x738 (`sound.md` §4)。

| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | 0 以外なら、段階がこの行に変わったときに `FUN_0021387C(値)` に渡す (BGM と推定)。全行 0 |
| +0x04 | u32 | 目的地 = mapGroup の **+0x08** (その場所のハッシュ。`mapJumpPoint` / `worldmapPort` と同じ値)。0 = 目的地なし |
| +0x08 | u32 | 画面の部品の ID (推定)。`FUN_001DF738` が `FUN_002A44E4(…, 値)` に渡し、画面の部品を ID で探す。全行 `0x01100010` |
| +0x0C | u32 | 見出し (MessageField_JP 42359〜。例「アンテナ塔へ行こう！」。場所の名前だけを差し込む行も多い) |
| +0x10 + 8 × i | u32 | ヒント i (0〜3) のメッセージ ID (MessageField_JP 42458〜42678)。0 = なし |
| +0x14 + 8 × i | u16 | ヒント i のナビのモーションの番号。`FUN_001F1484` が `FUN_0023AE8C` に渡す (確定) |
| +0x16 + 8 × i | u8 | `FUN_0023ACFC` (→ `FUN_004AEA10`) に渡す値。表情と推定 |
| +0x17 + 8 × i | u8 | 再生のしかた (推定): 下位 2 ビット = `FUN_0023AE8C` の第 3 引数、0x04 = `FUN_00210030(…, 1)`、0x08 = `FUN_0023AF08` を呼ぶ |

- 引く関数: `FUN_001F1484` 付近 (`@0x1F1704`): 段階を `FUN_00212FB8` で読み、**100 (0x64) 以上なら `FUN_001F0EF8` (やりこみのヒントを選ぶ) へ**、それ未満ならその行の `+0x10 + ヒント番号 × 8` のメッセージを出す。ヒント番号は `FUN_002113AC` = セーブのキー 0xFC (u8)。
- 行 0 は空、行 1〜99 がストーリー、行 100 は空、行 101〜134 はやりこみ (釣り・植物・アンテナ・魔物・アイテム・スタンプなど) のヒント。
- テキストは MessageField_JP の末尾 (42359〜42678) にまとまっている。抜き出したもの (ROM 由来なのでリポジトリには入れない): Panana プロジェクトの共有フォルダ `oahu-story/navi.tsv`。

## 2. 進行度 (セーブのキー 0x74) (確定)

| 関数 | 内容 |
|---|---|
| `FUN_004B212C` / `FUN_00212FB8` | 段階を読む: `FUN_004A2D3C(セーブ, 0x74)` (u16) |
| `FUN_004B2170` | 段階を書く: `FUN_004A2DB8(セーブ, 0x74, 値)` |
| `FUN_00213010(段階)` | **段階を変える**: 今の段階と違えば、新しい行の +0x00 を鳴らし (0 なら何もしない)、ヒント番号 (0xFC) を 0 に戻して、0x74 に書く。書き込みはすべてこの関数を通る (`bl` と末尾呼び出しの `b` で 93 か所。うち 1 か所は §4.2 の動作自身の実行 `@0x2ECE00`) |
| `FUN_002113AC` / `FUN_00211404` | ヒント番号 (キー 0xFC) を読む / 書く |

- 書く側はほぼ必ず「**今の段階 < N なら N にする**」の形 (`bl FUN_00212FB8; cmp r0, #N; movlo r0, #N; bllo FUN_00213010`)。つまり段階は前にしか進まない。
- 段階を読んで比べる所は 112 か所あるが、ほとんどがこの「進めるだけ」の比較。段階で分岐する処理は、マップに入ったときの共通の判定 (§4.2) くらい。**EventObject の出現条件で 0x74 を見る行はない** (条件 0x1F〜0x21 の値 1 に 0x74 はない)。

### 2.1 物語の値・フラグを読み書きする関数 (確定)

## 3. セーブの値の全体 (確定)

### 3.1 セーブの値の定義 `flagData.bin`
master の `flagData.bin` (259 行 × 0x10) は**セーブの値の定義表**で、行番号がキー (`FUN_004A2D3C` などの第 2 引数)。セーブ (`*0x5A5000`) +0x14 の読み手で引く (`FUN_004A2D3C` → `FUN_004A236C`)。

| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | 最大値 (0 = 制限なし。例 0x29 = 99,999,999、0x2C = 99) |
| +0x08 | u16 | 要素の数 (配列なら 2 以上) |
| +0x0A | u8 | 0x02 (全行) |
| +0x0B | u8 | ビット数 × 4 (0x04 = 1 bit、0x20 = 8 bit、0x40 = 16 bit、0x80 = 32 bit …) |
| +0x0C | u8 | 未解析 (1〜0x28) |

- 例: 0x74 = 16 bit × 1 (進行度)、0xFC = 8 bit × 1 (ナビのヒント番号)、**0xF9 = 8 bit × 540 (値)**、**0xFA = 1 bit × 596 (フラグ)**、0x49 = 8 bit × 196、0x55 = 今のダンジョン (mapGroup の行、`FUN_004EE968`)。
- 0xF9 / 0xFA の要素の数は、mapGroup の各行の範囲の合計と一致する (0xF9: 535 + 5 = 540、0xFA: 560 + 36 = 596)。
- `flagDataHonolulu.bin` / `flagDatakahara.bin` は同じ形 (前作のセーブの読み込み用と推定)。

### 3.2 物語の値は mapGroup 行 0 の範囲
mapGroup の +0x26 / +0x28 (0xF9 の先頭 / 数)、+0x2A / +0x2C (0xFA の先頭 / 数) を全行並べると、**行 0 (名前「なし」) が 0xF9[0〜45]・0xFA[0〜19]** を持つ。ダンジョンではなく**ゲーム全体の物語の値**。以降は d10 = 0xF9[46〜50]・0xFA[20〜25]、d20 = 0xF9[51〜55]・0xFA[26〜31] … とダンジョン・町・島ごとに 5 個前後ずつ並ぶ (ダンジョンの値は条件 0x04〜0x11、0x02 / 0x03 が読む)。

0xF9 の全体の値は、ほぼ**ボス (化身など) 1 体に 1 つ**で、0 → 1 (出会った・戦う前) → 2 → 3 (倒した) と進む。3 を書くのは戦闘のあとの処理、1 を書くのはボスの前のスクリプト。

- 名前つきの条件 0x01 (`FUN_001ED9B8`、値 1 = 1〜47) の中身 (§2.1 の読み出し関数を止めて `FUN_001ED9B8(n)` を動かし、呼ばれた関数と引数で確認): 1〜12 は順に **0xF9[4 / 7 / 10 / 15 / 17 / 18 / 19 / 21 / 24 (≥ 3) / 25 / 27 / 28] = 3** (= ボスを倒した)。13 = ダンジョン 0x0D のフラグ 1 か 2、14 = ダンジョン 0x0E のフラグ 3 か 4、16 / 17 / 18 = ダンジョン 0x10 / 0x11 / 0x12 のフラグ 1、それ以外 (15、19〜) は常に偽。

## 4. 進行度を書く所 (確定)

### 4.1 スクリプトのクラス
`FUN_00213010` の呼び出し (§4.2 の動作の実行を除く) 92 か所のうち、段階がすべて即値で読めたのは 89 か所。残りもレジスタの値をさかのぼると即値の候補が分かる (§4.3)。Panana の実行器 (panana#85 `src/oahu/scripts.ts`) で EventObject の全行のクラスを作り、クラスの関数から呼び出しを辿ると **50 か所が EventObject の行 (主に種類 0x2E のスクリプト) に結びつく** (§5 の表の「d20 行 39」など)。

残りは EventObject から直接は作られないクラス (戦闘のあと、カットシーンの続き、マップに入ったとき) にある。表では関数のアドレスで示した。

### 4.2 マップに入ったときなどの共通の判定 (推定)
起動時に `FUN_00279E7C(…, FUN_0018D848, 1, 0)` で登録される `FUN_0018D848` (引数 0〜14 で分岐) の先に、`FUN_0019A788`〜`FUN_0019BDA0` の判定が並ぶ。どれも「(ダンジョンのフラグなど) かつ 段階 < N」なら、**段階を N にする動作** (`FUN_002ECE28(obj, N)`、16 バイト、+0x0E = 段階) を作る。段階 2・7・9・10・12・21・31・37・48・49・62・65・70・72・81・98 はここで書かれる。

### 4.3 段階 0・1・73・96 と、レジスタで渡す所 (確定)
- **段階 1**: `FUN_001E8458` (`@0x1E846C`)。`FUN_001EE850` (0xFA を書く) のあと `FUN_001EDC14()` が 1 なら r0 = 1 のまま、それ以外は `movne r0, #2` で、**1 か 2** を書く。
- **段階 101〜123**: `FUN_001F0EF8` (`@0x1F13B8`、やりこみのヒントを選ぶ) が、まだ済んでいない項目の行 (101・102・103・104・105・107・108・109・111・112・113・116・117・119・120・121・122・123) をレジスタ r4 で選んで段階に書く。物語が終わった (段階が 100 以上) あとの R ボタンのナビはこの行を出す。
- **段階 34 / 35 / 36**: `FUN_00244118` が会ったリーダーの数で 3 つの `mov` を選ぶ (分岐の先で r0 を決めて 1 つの呼び出しに合流)。
- **段階 0** はセーブの初期値で、書く所はない。**段階 73・96** を即値で書く所も、レジスタの候補に入る所もない (使われていない段階と推定)。

## 7. MOD で物語を作るときに分かったこと

- **データだけで変えられる**: ナビの見出し・ヒント・目的地 (`mapNavi.bin` とメッセージ)、EventObject の出る / 消える条件 (どの物語の値で出すか)、会話の文面。
- **code.bin を変える必要がある**: 段階・物語の値を「いつ・いくつに」書くか (スクリプトの即値。§5 の書き込み箇所の `mov` を書き換える code.ips で済む)、新しいスクリプトの流れ。
- ナビの行は 100 未満がストーリー (`@0x1F1708` の `cmp r0, #0x64`)。99 段を超える物語にするにはこの比較と、やりこみの行 (100〜) の位置を変える必要がある。
- 全体の物語の値は 0xF9[0〜45] のうち、使われていないもの (**0xF9[5・34・37〜45]、0xFA[18・19]**。スクリプトの書き込みも、EventObject の条件も、code.bin の即値での読み書きもない。Panana の §9 の走査による) を MOD の物語に割り当てられる見込み (ゲームでの確認はまだ)。
- 書き込みの値を変えるときは、前の `cmp r0, #N` (「今の段階 < N なら」) も同じ値にしないと、進めるだけの判定がずれる。ARM の即値は 8 ビットを偶数回ローテートした値だけなので、段階 (0〜255) はどれも書けるが、0xF9 の値などで 256 以上を `mov` 1 命令にはできない。

## 9. Panana での扱い (panana #87)
- 書き込み箇所は手で並べず、Update の code.bin を走査して求める: §2・§2.1 の書き込み関数への `bl` / `b` を全部拾い、呼び出しの前の命令をさかのぼって引数のレジスタを決める即値を集める (呼び出しの条件、呼び出しを飛び越える分岐、`movne` / `moveq` の組、`mov rX, rY`、呼び出しへ合流する分岐の手前の `mov<c>` まで見る)。前の `cmp r0, #N` は「段階が小さいときだけ」の印として一緒に扱う。
- どの EventObject の行の書き込みかは、実行器 (`map.md` §5.3) で作ったクラスの関数の範囲に呼び出しが入るかで決める。
