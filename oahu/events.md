# RPG3 (oahu) の EventObject

対象: 日本版 RPG3 (oahu)、Update TitleVersion 4096 の code.bin。アドレスは実行時仮想アドレス。以下の「確定」は既存のコード解析・実データ照合による記録、「推定」「未確認」はそのまま区別する。Base / Update の資源の選択は [更新データ](../roms/oahu-update.md) を参照。

レコードを配置する区画の構造は [マップ](map.md)、モデルの参照は [マップモデル](map-models.md)、セーブ値は [ストーリー](story.md) を参照。


## 1. 欄
レコードは RPG2 の 0x50 バイトから **0x58 バイト**になった。出る条件・消える条件がそれぞれ 1 値から 2 値になり、種類ごとの引数以降は RPG2 の +0x08 から RPG3 の +0x10 へ **8 バイト後ろにずれる**。

| 位置 | 型 | 内容 | RPG2 |
|---|---|---|---|
| +0x00 / +0x04 | u32 × 2 | 出る条件の値 1 / 2 (+0x53 とともに) | +0x00 のみ |
| +0x08 / +0x0C | u32 × 2 | 消える条件の値 1 / 2 (+0x54 とともに) | +0x04 のみ |
| +0x10〜+0x4B | | 種類ごとの引数 (RPG2 の +0x08〜+0x43) | |
| +0x10 / +0x14 | u32 | 出入口の種類 (0x13 / 0x15 / 0x16 / 0x18 / 0x1B / 0x1E / 0x1F / 0x21 / 0x2E の一部): **行き先のマップ / 地点 ID** (区画 3 の +0x00) | 区画 3 にあった |
| +0x4C | u16 | 状態の枠 (0xFFFF = 行番号) | +0x44 |
| +0x4E | u16 | モデル (mapObject の行)。範囲では半径 | +0x46 |
| +0x50 | u16 | bit15 と下位 15 bit を範囲の登録に渡す (推定: 範囲の高さなど) | +0x48 |
| +0x52 | u8 | 種類ごとの引数 (1 / 2) | +0x4A |
| +0x53 | u8 | **出る条件**の種類 (0 = なし) | +0x4B |
| +0x54 | u8 | **消える条件**の種類 (0 = なし) | +0x4C |
| +0x55 | u8 | **種類** | +0x4D |
| +0x56 / +0x57 | u8 | 完了時の状態の値 (推定) | +0x4E / +0x4F |

- 行の読み出しは RPG2 と同じ: 今いるダンジョンの表がマスター +0x428 (`FUN_0022c084(+0x428, 行)`)。
- 状態の枠 (推定): mapGroup +0x22 (u16) = 先頭、+0x24 (u8) = 数 (D10 = 0 / 51、D20 = 51 / 65 … と積み上がる)。

## 2. 出現条件 (確定)
`FUN_004b6ac8(行)` = 出る: +0x53 が 0 か、条件 (+0x53, +0x00, +0x04) が成り立つ。`FUN_004b6b38(行)` = 消える: +0x54 が 0 でなく、条件 (+0x54, +0x08, +0x0C) が成り立つ。

条件は `FUN_004b62bc(行, 種類, 値 1, 値 2)`。**RPG2 (181 種類) とは別の表**で、値を 2 つ取る。セーブ変数は `FUN_004a2740(セーブ, キー, 添字, 出力)`: キー 0xF9 = 値 (u8)、0xFA = フラグ。ダンジョンの範囲は mapGroup の +0x26 (u16、0xF9 の先頭) / +0x28 (数)、+0x2A (u16、0xFA の先頭) / +0x2C (数)。

| 種類 | 成り立つとき |
|---|---|
| 0x01 | 名前つきの条件 値 1 (`FUN_001ed9b8`。例 1 → 0xF9[4] = 3、2 → 0xF9[7] = 3 …: ボスを倒した。全体は [ストーリー](story.md) §3.2) |
| 0x02 / 0x03 | ダンジョン 値 1 のフラグ 値 2 が立っている / 立っていない |
| 0x04 / 0x05 / 0x06 | 今のダンジョンの値 値 1 が = / ≥ / ≤ 値 2 |
| 0x07〜0x11 | ダンジョン 値 1 の値 値 2 が = 種類 − 7 (0〜10) |
| 0x12 / 0x13 | フラグ 0xFA[値 1] が立っている / 立っていない |
| 0x14 / 0x15 / 0x16 | 値 0xF9[値 1] が = / ≥ / ≤ 値 2 |
| 0x17 / 0x18 | セーブのキー 0x49 の 値 1 が真 / 偽 (値 1 = 0 は真。種類 0x0C / 0x1C の行だけが使う、[ストーリー](story.md) §3.3) |
| 0x19 / 0x1A | `FUN_004ef1a4(値 1)` の結果が = / ≠ 値 2 (未解析) |
| 0x1B / 0x1C | 値 1 = 0x65〜0x69 で選ぶ判定 (`FUN_0038d250` など。未解析) / その否定 |
| 0x1D / 0x1E | `FUN_001ed418(今のダンジョン, …)` が ≥ / ≤ 値 2 (未解析) |
| 0x1F / 0x20 / 0x21 | 表 (`FUN_004a2d3c`、値 1 の行) の値が = / ≥ / ≤ 値 2 |
| 0x22 | `FUN_0021152c(値 1)` がこの行 |

バニラで多いのは、+0x53 = 0x17 (390 行)、+0x54 = 0x15 (106 行) / 2 (73 行)。

## 3. 種類 (+0x55) と動作の生成
- 作りは RPG2 と同じ ([RPG2 のイベント](../kahara/events.md) §1): 区画のレコードがハンドラ (`FUN_003128d4` が基底: +4 = 行、+8 = EventObject の行) を作り、vtable[4] の「動作の生成」(引数: ハンドラ、+0x55 の種類、…) が動作のクラスを作る。
- **種類 0x2E (46) = スクリプト** (RPG2 の 0x24)。例: 出入口のハンドラ (`FUN_004bcf30`、vtable 0x588104) の動作の生成 `FUN_004bc7c8` は、0x2E のときダンジョン (`FUN_004ee968(*+0x5C)`) で分岐して `FUN_00195fb0` などダンジョンごとの関数に入る。v4096 で 636 行。
- 同じ `FUN_004bc7c8` が扱う種類: 0x13 / 0x14 / 0x15 / 0x16 / 0x17 / 0x18 / 0x19 / 0x1A / 0x1B / 0x1C / 0x1D / 0x1F / 0x20 / 0x21 / 0x2E (出入口・扉・階段の動作)。
- ハンドラの vtable[4] (動作の生成) は、引数が (ハンドラ、種類 +0x55、**行の引数 +0x10 へのポインタ** (推定。0x13 などで `*引数` = 行き先のマップ、`引数[1]` = 地点として使う))。ハンドラの +4 = 行、+0x18 = ハンドラを作るときの第 3 引数。

  | ハンドラ (vtable) | 区画・レコード | 動作の生成 |
  |---|---|---|
  | `FUN_004bcf30` (0x588104) | 3 (出入口・扉) | `FUN_004bc7c8` |
  | `FUN_004bc4ec` (0x5880E8) | 4 (宝箱) | `FUN_004bc3c0` |
  | `FUN_002724e8` (0x57F634) | 8 (範囲、種類 < 100) | `FUN_00272034` |
  | `FUN_004a99a0` (0x587E20) | 5 の種類 0〜2 | `FUN_004a9000` |
  | `FUN_00237fc0` (0x57EA94) | 5 の種類 3 | `FUN_0026b9c0` |
  | `FUN_0023006c` (0x57E73C) | 5 の種類 4 / 5 / 6 / 0x0B / 0x0D / 0x0E | `FUN_0022fe14` |
  | `FUN_002373ec` (0x57EA64) | 5 の種類 7 / 8 / 9 | `FUN_0019e1a0` |
  | `FUN_001f9168` (0x57DF78) | 5 の種類 0x0C | `FUN_002239c8` |

- **実行器で確かめた** (Panana `src/oahu/scripts.ts`): 上の動作の生成を、今のダンジョン (`FUN_004ee968`) と確保 (`FUN_00122b14`) をスタブにして行ごとに動かすと、種類 0x2E の 636 行のうち 533 行でクラス (vtable) が決まり、全体では 2,368 行のうち 2,246 行、クラスは 375 種類。そのうち 155 種類は MessageField_JP (ID 40000〜) のメッセージを読み込む (例: 0x580968 は地底人スカウトの会話)。
- 件数 (全 82 ダンジョン、2,524 行): 0x2E 636、0x15 260、0x10 218、0x0C 195、0x1C 195、0x13 143、0 156、0x17 98、0x0F 94、0x21 81、0x1B 78、0x27 54、0x16 47 …。種類ごとの意味は未解析 (RPG2 とは番号が違う)。


### 3.1 スクリプト (0x2E) のクラスと、呼び出す関数

Update v4096 の `code.bin` で、0x2E の 636 行を Panana の実行器 (`src/oahu/events.ts`・`scripts.ts`) で作り直して確かめた。533 行でクラスが決まり、vtable は 348 種類。「確定」はコードで確かめたこと、「推定」は解釈。

**作り (確定)**
- `FUN_004bc7c8` の 0x2E の分岐 (@0x4BCBFC) が `FUN_004ee968` で今のダンジョンを取り、表 @0x4BCC28 (0〜0x12) と比較 (0x13〜0x58) で、ダンジョンごとの関数 (ダンジョン 1 → `FUN_00195FB0`、3 → `FUN_00196050` …) に末尾ジャンプする。
- ダンジョンの関数の引数は r0 = 行番号 (ハンドラ +4)、r1 = ハンドラ +0x18、r2 = 行の +0x10 へのポインタ。行番号で分かれ、確保 (`FUN_00122B14`、大きさは即値) → 基底のコンストラクタ → `str vtable, [obj]` でクラスを作る。行全体はハンドラ +8 にある。
- 一番下の基底は `FUN_001F927C(obj, 行)` (0x10 バイト、vtable 0x57DF94): +4 = 行、+8 = 1、+0xA (u16) = ダンジョン。
- よく出る基底:
  - `FUN_0026AFB8`: 話す NPC (vtable 0x57F4C8、0x70〜0x40C、約 140 行)。+0x10 = NPC の部品 (vtable 0x588120)、+0x5C / +0x60 / +0x64 = メッセージとその引数、+0x68 / +0x6C = 向き。
  - `FUN_001F927C` のまま: 0x10 / 0x5C、45 行。
  - `FUN_002D2618`: 0x84。+0x70〜+0x7C に、行の +0x10〜+0x1C のメッセージ 4 つ。
  - そのほか: `FUN_0039E450` / `FUN_0039B33C` (0x6C / 0x70)、`FUN_002496C8` (出入口、0x70)、`FUN_001E6804` (宝箱、0x7B8)、`FUN_00384120` (戦闘、0x1C)。ほかに約 30 種類。
- vtable は少なくとも 8 項目:
  - [0] 0、[1] 解放、**[2] 本体**、[3] `FUN_001F91A0` (何もしない)、**[4] 完了 `FUN_001F91A8`**、[5] `FUN_004C4210` (0 を返す)、[6] 話す NPC の動きの選択 `FUN_0026ACB4`、[7] 0。
  - `FUN_002D2618` の系統は、[8]〜[0xB] でメッセージを選び、[0xC] で話す。
- [2] はステートマシンではなく、上から順に動く普通の関数。待つ関数の中で `FUN_0010F860()` (今のスレッドで 1 フレーム譲る) を繰り返すので、状態をクラスに持たなくてよい。[2] を走らせるスレッドの作り手は未確認 (推定: イベントのスレッドで 1 回呼ぶ)。
- 終わるときは、[2] の中で vtable[4] `FUN_001F91A8` を呼ぶ。これは EventObject の行 (マスター +0x428) の状態 (`FUN_001ED418(ダンジョン, 行)`) を `FUN_001ED748(ダンジョン, 行, 新しい状態)` で 0 → 1、1 → 2 (+0x56 ≠ 0)、2 → 3 (+0x57 ≠ 0) と進める。今のダンジョンの状態を直接書くのは `FUN_001ED718(行, 状態)`。

**0x2E の行で空いている欄 (確定、636 行で数えた)**
- 0 でない行: +0x10 は 190、+0x14 は 173、+0x18 は 110、+0x1C は 67、+0x20〜+0x2C は 3〜6 ずつ。**+0x30〜+0x48 (7 語) は 0** (+0x34 に 1 行だけ 0x67)。+0x52 は 44 (1 / 2)、+0x56 は 9。
- +0x57 は 0 行だが、完了の 2 → 3 を決めるので空き欄としては使えない。

**新しいコードとデータの置き場所**
- text の末尾 0x5558C0〜0x556000 (0x740 バイト) は全部 0 で参照もなく、text と同じページで実行できる (確定。text の最後の語は 0x5558BC)。
- どこからも呼ばれない関数は静的には確かめきれない (`push {…lr}` から数えると 1,805 個・0x5C1D4 バイトだが、`FUN_001D9BBC` のように push の前から始まる関数を数え違える。未確認)。
- master の表の読み手 (*0x59F200 + オフセットの 0x1C バイト、+4 = 表) は `FUN_001D9BBC(&エントリのハッシュ)` が決まったハッシュの比較の連なりでつなぐので、新しいハッシュの表には読み手ができない (確定)。行は `FUN_0022C084(読み手, 行)`、索引は `FUN_0022C0A8(読み手, キー)`。
- アーカイブのエントリをハッシュで読むのは `FUN_00470E24(obj, &ハッシュの並び, 数, アーカイブのハッシュ, [sp])` (資源の管理 *0x5A59DC 経由、非同期。読み終わりの確認は `FUN_004705AC`、解放は `FUN_00470694` / `FUN_004706C8`)。vtable 0x5877F4 はカメラ専用かもしれない (推定)。


## 4. 解析の範囲と未確認

- 2,524 行は全 82 ダンジョンの EventObject 総数。実行器の集計 2,368 行との差は種類 0 の 156 行に一致するが、元記録は除外条件を明記していない。両方の件数を保持し、2,246 行を総数に対する成功件数とは読み替えない。
- 種類 (+0x55) ごとの意味と引数 (+0x10〜+0x4B)、+0x50 / +0x56。0x2E は §3.1 で欄の使われ方を数えた。
- 0x2E の本体 (vtable[2]) を走らせるスレッドの作り手。
- 出現条件 0x19〜0x1E・0x22 の中身、状態の枠 (mapGroup +0x22 / +0x24) の書き込み側の確認。
- イベントアーカイブは mapGroup +0x14 が指す。Update で差し替わるのは `97CF0000` (m10)。
