# RPG3 (oahu) のアクション (actionData.bin)

master (21350000) の `actionData.bin` (1126 行 × 0x30) の欄と、**系統 (+0x2C) ごとに +0x18・+0x1A などの意味がどう変わるか**をまとめる。アドレスは Update (v4096) の code.bin。

RPG2 (kahara) のアクションは [kahara/battle.md](../kahara/battle.md) と [kahara/reference/actions.md](../kahara/reference/actions.md)。RPG3 は行が 0x3C → 0x30 に縮み、並びも違う。

## 1. 処理の流れ

| 段階 | 関数 | 内容 |
|---|---|---|
| 結果を作る | `FUN_001B5A80` | 行を引き (`FUN_0029D5D8`)、**+0x2C をそのまま結果の種類 (結果 +0x10) にする**。種類で 39 通りに分岐する (表 `0x1B5BE0`、0〜38)。 |
| 結果を当てる | `FUN_001B51E8` | 結果の種類で 39 通りに分岐する (表 `0x1B52E8`、0〜38)。 |
| 道具を使う | `@0x229978` | 系統 35 だけ、ここでアクションの行を選び直す (§3)。 |

- 39 以上 (39・40) はどちらの表にも入らず、何も起きない。メッセージだけ出るアクションに使われている。
- 結果の欄: +0x04 = アクションの行へのポインタ、+0x08 = 値 (ダメージ・回復量など、s16)、+0x0C = 状態の強さ、+0x0E = 状態の番号、+0x0F = 持続ターン、+0x16 = モンスターの行 (系統 19〜22)。
- 「+0x18〜+0x1A の乱数」は `FUN_001B3174(min, max)`。結果 +0x1C bit0 が立っているときは乱数を使わず平均 ((min+max)/2) になる (AI が見積もるときと推定)。

### 仲間を呼ぶ (系統 19・20) の補足

呼べる条件、群れからの選び方、元データの例は [summon.md §2](../common/summon.md#2-rpg3-oahu)。

### 変身 (系統 21・22) の補足

- +0x1A は `ldrh` で読んで下位 8 ビットだけ使う (`@0x1B45AC`)。monsterParameter は 201 行なので 255 までで足りる。
- 変身の 34 行 (系統 21・22) のうち、ボディから出すもの (種類 3、+0x2A = 101 倒される一撃、107 ブレス・呪文、110 属性) と、ワザの枠から AI が選ぶもの (種類 0。箱に隠れる・ふくらむ) がある。
- ジャシン (#147) の #870: +0x18 = 1、+0x1A = 147、+0x2A = 101、+0x2C = 21。ボディ (monsterParameter +0x34) に入れ、倒される一撃で発動して #147 に作り直す。
- 発動の条件 (+0x2A) とボディ・自動の枠の関係は [Panana の変身調査 PR #77](https://github.com/sweshelo/panana/pull/77) (本書に未収録の詳細) を参照。

### 変身の見た目 (monsterParameter +0x62)

- 系統 21 (`FUN_0029C93C`) はユニットのデータ (行・能力・名前) を作り直すだけで、モデルは変えない。元のデータの系統 21 の組はどれも同じ見た目の形態どうし。
- 系統 22 は、演出 (`@0x219F3C`) の中でさらに `FUN_0029C790` を呼ぶ。使った側の付き添いのオブジェクト (ID = 0xb | 側 << 5 | 枠 << 13、`FUN_00270F6C`) を探し、そのモデルと入れ替える (`FUN_00387D80`)。
- 付き添いのモデルは、戦闘の始めに `FUN_0029BAD0` が **monsterParameter +0x62** (u16、モンスターの行) から読む (`FUN_0038B1D0(obj+0x14, 行)`)。0 なら読まない。
- 元のデータで +0x62 を持つのはドローンＺ #160 (+0x62 = 161、じしょう・まおう) だけ。`FUN_001C9F68` も +0x62 を読む。
- なので、ほかのモンスターを見た目ごと変身させるには、そのモンスターの +0x62 を変身先の行にし、系統 22 のアクション (例 #966) を使う。読んでおけるモデルは 1 体に 1 つ。能力・名前はアクションの +0x1A、見た目は +0x62 で別々に決まる。

### 状態のダメージ (系統 36) の値

- `FUN_001B752C`: ダメージ = 最大 HP (`FUN_004CD954`) × +0x18 / 100 (+0x18 は 100 で頭打ち)。最低 1、最大 +0x1A (9999 で頭打ち)。
- つまり「上限」は 1 回のダメージの最大値。どく #343 は 10% で上限 200、もうどく #344 は 25% で上限 500、ほかは 5% で上限 100。HP の多いボスほど上限で止まる。
- 系統 10 (HP 自動回復) も同じ「% と上限」の形。

### 新しいアクションを作るときの注意

- 行は actionData の最後に足せる。ゲームは表の頭の行数で行の番号を確かめる (`FUN_0029D5D8`)。
- 系統を変えると +0x18・+0x1A の意味が変わる。変身にするなら +0x1A をモンスターの行に、仲間を呼ぶなら +0x1A をモンスターの行 (か +0x18 を群れの行) にする。
- 種類 (w0 bit0-2) と系統は別々に決まる。ボディ・自動の枠から出すなら種類 3、ワザの枠なら種類 0。
- 状態を付ける系統 (5・6・7) では、+0x2E・+0x1C・w1 の成功率と持続ターンがそろって初めて効く。

## 5. 演出の進行とカメラ

Update v4096 の `code.bin` で確かめた。「確定」はコードで確かめたこと、「推定」は意味の解釈。RPG2 の進行 ([kahara/action-performance.md](../kahara/action-performance.md) §2.2「演出の進行」) は actionData +0x1C で選ぶが、RPG3 の actionData にはこの欄がなく、種別とカテゴリで決まる。

### 5.1 進行の選び方 (確定)

`FUN_0021B838` (@0x21B8EC〜0x21B9C8)。結果 = `FUN_0021FA04(枠, 0, 0)`。種別は結果 +0x10 (= actionData +0x2C)、w0 は actionData +0x00。進行の番号は枠 +8、段は枠 +9 に入る。

| 種別 (+0x2C) | 進行 |
|---|---|
| 0 | 1 |
| 1・0x12 | w0 & 7 == 2 なら 3、ほかは 2 |
| 0x14 | 15 |
| 0x17 | w0 & 7 == 4 なら 4、== 2 なら 3、ほかは 6 |
| ほか | 枠 +0x412 == 5 なら 5、w0 & 7 == 4 (道具) なら 4、ほかは 3 |

アクション 0xF4 / 0xF5 は枠 +0x404 の数だけ繰り返す。

ジャンプ表 `FUN_0021BE98` (@0x21BEA8、16 個)。関数が 1 を返すと、変わった番号で引き直す。

| 進行 | 関数 |
|---|---|
| 0 | なし |
| 1 | `FUN_002196AC` |
| 2 / 9 | `FUN_00218E5C` (r1 = 0 / 1) |
| 3・4・5 / 10 | `FUN_00219988` (0 / 1) |
| 6 / 11 | `FUN_0021B9E4` (0 / 1) |
| 7 | `FUN_0021A2EC` |
| 8 | `FUN_0021A67C` |

r1 = 1 の版 (9・10・11) は使う側の付き添い (`FUN_0029B780`) が演じる。使う側の一覧は `FUN_004C58CC` で、枠 +0x418 が本人、+0x407 が人数、+0x41A〜 が一緒に使う者。

### 5.2 段の順番 (確定)

演出の行の再生は `FUN_0032AFB0(枠の再生器, directData の行, 物の ID, 0)`、再生器は `FUN_004C32AC(物, ch)`。待ちは `FUN_0021E10C` (枠 +0xC のフレーム数)。カメラが終わるのを待つ `FUN_0021E958` を呼ぶのは、進行 3 の段 2 (@0x21A27C、w0 & 7 == 2) だけで、ほかは決まったフレーム数 (0xF・0x14・0x1E・0x3C・2・4) を待つ。

- **3 (`FUN_00219988`)**: 段 0 で +0x1E / +0x20 (+0x1E が 0 ならすぐ 12 へ)。段 1 でカメラ U、メッセージ、0x14 待つ。系統 22 なら @0x219F3C で白くして `FUN_0029C790`。そのあと種別で分かれる: 0 / 0x10 は終わり、0xF (つかまえる) は 7、0x13 は 14、+0x22 か +0x26 があれば 12、なければ終わり。w0 & 7 == 2 のときは段 2 でカメラの終わりを待ち、種別 1 なら 9、0x17 なら 11、ほかは 10 (付き添いの番)。
- **2 / 9 (`FUN_00218E5C`)**: 段 0 で +0x1E / +0x20 と +0x26・+0x22 / +0x24 を同時に流す。段 1 でカメラ U、0xF 待って 12 (か 8)。
- **12 / 13 (`FUN_0021DC78`)**: 段 0 で +0x26 と各対象の +0x22 / +0x24 (13 は +0x28)。段 1 で 12 はカメラ T、13 はカメラ U1。+0x26 の終わりで `FUN_0021C5E0`、2 待って `FUN_00197910` (結果を当てる、推定)。系統 22 なら `FUN_0023B35C` で白を戻す。0x1E 待つ。12 で枠 +0x408 があれば 13 へ。
- **1 (`FUN_002196AC`)**: カメラ U → +0x1E / +0x20。
- **6 / 11 (`FUN_0021B9E4`)**: メッセージ、0x1E 待つ → +0x1E / +0x20 → カメラ U。
- **7 (`FUN_0021A2EC`)**: カメラ T、0x1E 待つ → +0x22 / +0x24 → カメラ T。
- **8 (`FUN_0021A67C`)**: カメラ G と、決まった directData の行 0x14。
- **14 / 15 (`FUN_002194A4` / `FUN_0021A878`)**: actionCamera の行 0x11 を直接使う (15 は 0x1E 待ってから。最後に 0x3C 待つ)。

### 5.4 actionCamera.bin (master、26 行 × 0x4C)

- 読み手は master の読み手 +0x2A0 ([master-readers.md](master-readers.md))。行を引くのは `FUN_0021E41C(カメラ, 行, 物 ID, 枠, 速さ s0, …)` で、行の番号で 26 通りに分かれる (表 @0x21E4A8)。
- 行は 6 列 × 3 候補の u32 (エントリのハッシュ)。+0x48 / +0x49 / +0x4A は 3 候補の重みで、`FUN_0021E2A0` が乱数 (`FUN_001B1F40`) で 1 つ選ぶ。+0x4B はどの行も 208 で、読まれない。18 個のハッシュの並び (列ごとか候補ごとか) は未確認。
- 選んだハッシュはアーカイブ 0x7A880000 のカメラのデータとして `FUN_00470E24` で開かれる。欄は視点や時間の数値ではなく、カメラのアニメのファイル (確定。中身は未調査)。
- 列 (0〜5) の選び方は行で違う: 0xA / 0xB・5・7・0x10・0x11・0x18・0x19 は大きさの種類 (§5.5、`FUN_0021EA18`)、6 は付き添いの大きさ、4 は使う側の大きさ、0xC・0xD・0x13〜0x17 などは `FUN_001F37E8` (陣営の並び、推定)、0x12 / 0x13 は `FUN_001F3A84`。

### 5.5 大きさの種類 (monsterDesign +0x77)

`FUN_004CB2E4` (確定)。RPG2 の MonsterDesign +0x6E にあたる。

- 仲間の記録 P (記録 +0) があるとき: P+0x340 の bit0 なら列 4、bit1 なら列 5。どちらもなければ P+0x33E を使う。
- P がないとき (敵、推定): monsterParameter (記録 +4 → +3 の行) +0x48 & 0x1FF → monsterDesign (402F0000、読み手 +0xA10) **+0x77**。0xA / 0x10 / 0x14 なら列 3。
- 値から列へ: 1・2 → 0、4 → 1、6 → 2、ほか → 3。電波人間は 0。
- P+0x33E / +0x340 は `FUN_0029CB98` が +0x77 から作る: 0xA は 8 と bit0、0x10 は 8 と bit1、0x14 は 8、ほかはそのまま。なので仲間の 10 / 16 は列 4 / 5、敵の 10 / 16 / 20 は列 3。
- 元のデータの +0x77: 2 が 43 行、4 が 52、6 が 30、10 が 35、16 が 3。

### 5.6 変身とカメラ

- 系統 21 / 22 の `FUN_0029C93C` は新しい行を記録 +4 → +3 (と P+0x368) に書き、P があれば `FUN_0029CB98(記録, 1)` で P+0x33E / +0x340 を作り直す (確定)。
- 列はカメラを置くたびに `FUN_004CB2E4` で選び直す (残しておく値はない)。変身のあとに置くカメラは、新しい形態の monsterDesign +0x77 で選ばれる (確定)。
- 決め手は行 (monsterParameter +0x48 のデザイン) で、系統 22 で `FUN_0029C790` が入れ替えるモデル (+0x62) の大きさは見ない。見た目が変わらない系統 21 の変身でも、行の大きさが違えば列は変わる。
- 例: ドローンＺ #160 (デザイン 129、+0x77 = 10) → #161 (130、16)。敵ならどちらも列 3、仲間なら列 4 → 5。
- 変身はその行動の途中 (進行 3 の段 1) で起きるので、そのとき出ているカメラは変わらず、次に置くカメラから変わる (推定)。背の大きく違う形態へ変身するとき (はなもぐら → じしょう・まおう など) に見切れるのは、変身の行動の残りのカメラが前の形態の列のままだからと考えられる (推定、未確認)。
