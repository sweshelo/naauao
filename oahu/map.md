# RPG3 (oahu) のマップとイベント

RPG2 の `map.md` / `events.md` / `event-list.md` に当たる、RPG3 のマップの区画とイベント (EventObject) の調査結果。アドレスは Update (v4096) の code.bin (`analysis.md` §1)。関数名は Ghidra の自動名 (`FUN_<アドレス>`)。

確度: **確定** = コードで読み方を確認し、実データで裏付けたもの。**推定** = 呼び出し元とデータの形からの推測。

結論を先に書く: **仕組みは RPG2 とほぼ同じ**。マップ DB の形式・タイル・mapParts によるモデルの選び方・EventObject のハンドラと「動作の生成」・状態の枠はどれも RPG2 と同じ作り。違うのは、マップ → 区画の表が code.bin から RomFS に移ったこと、区画の並びと 1 件のサイズ、座標の単位の一部、EventObject の欄の位置 (+8 ずれる) と出現条件の中身。

## 1. 全体像

```
マップ名 "D10B01001" ── マップ表 (B68E0000 / 5405E800、300 行 × 0x44) の行
   ├─ +0x00〜+0x24  区画のハッシュ × 10 (スロット 0〜9)
   │     └─> マップ DB (B68E0000 / A2C14C00) の区画のデータ
   ├─ +0x28  mapData のキー (0 = ダンジョンの既定)
   ├─ +0x2C  ダンジョン (mapGroup の行)
   └─ +0x34  階
ダンジョン (mapGroup の行) ── +0x14 イベントのアーカイブ (xXX_EventObject.bin)
                          └─ +0x2E / +0x2F mapData の行 ── タイルセット + mapResource ── タイルのモデル (type 8 の BCH)
```

## 2. マップ DB とマップ表 (確定)

### 2.1 マップ DB
- アーカイブ `B68E0000` のエントリ `A2C14C00` (種別 0、LZ10、822,496 B)。エントリのハッシュは RPG2 (`A90C8038` の `A2C14C00`) と同じ。
- 形式も RPG2 と同じ (`map.md` §1): `u32 件数, 件数 × {u32 ハッシュ, u32 オフセット, u32 サイズ}` (ハッシュの昇順) + データ。v4096 では 2,700 件。
- 読み出しは `FUN_004cf498(*0x5A59DC, 0xA2C14C00, 0)` で読み込み、`FUN_004cf004` (開始) / `FUN_004cf07c` (サイズ) で引く。

### 2.2 マップ表 (RPG2 の code.bin 0x4C1A74 に当たる)
- **RomFS に移った**: 同じアーカイブ `B68E0000` のエントリ `5405E800` (種別 0、20,400 B = 300 行 × 0x44)。
- 起動時に `FUN_002aba68` が読み込み、`{先頭, 末尾}` を `0x59F2C8` に置く。行の検索 (`FUN_002ab010(マップ)`) は先頭から順に +0x00 を比べる (見つからなければ先頭の行)。**行を足すだけで新しいマップを作れる**見込み (RPG2 のような code.bin の上限はない。未確認)。

| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | スロット 0 = マップのハッシュ (= タイルの区画のハッシュ) |
| +0x04〜+0x24 | u32 × 9 | スロット 1〜9 の区画のハッシュ (§3) |
| +0x28 | s32 | mapData のキー (0 = なし。`FUN_002ab058`)。0 でなければ mapData をキーで引き直す (§4) |
| +0x2C | s32 | ダンジョン = mapGroup の行 (`FUN_002ab0bc`) |
| +0x30 | s32 | **敵の出方** 1〜5 (§11.1)。`FUN_002760ac` がランタイム +0x546A に写す |
| +0x34 | s32 | 階 (地下は負)。`FUN_002ca100` がランタイムに写す |
| +0x38 | char[12] | マップ名 (`D10B01001` など) |

- 300 行: D 90、M 108、S 46、I 24、K 14、F 13、E 3、H 1、W 1 (`W01` = ワールドマップ。区画の形が別。§8)。
- ワールドマップ `A8654391` (W01) だけは別の表 (`0x556D54`、9 × u32) から区画を引く関数がある (`FUN_002ab73c` など、RPG2 の `worldmap.md` に当たる)。

### 3.1 区画 0: タイル (20 B)
| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | タイルの種類 (0〜65)。セルには「種類 + 1」で入る |
| +0x04 / +0x06 | s16 | x / y (セル) |
| +0x08〜+0x0F | | 0 (全マップで 0) |
| +0x10 | u8 | 下位 2 bit = 向き (90° 単位) |
| +0x11 | u8 | 文字: `'z'` (0x7A) または 0 = 既定、`'a'`〜`'g'` = 1〜7 |
| +0x12 | u16 | 0 |

- 中身は RPG2 の 12 バイトの欄 (`map.md` §3) と同じで、+0x08 に 8 バイトの空きが入った形。グリッドもセル 0x18 バイト、x 方向 1 列 30 セル (0x2D0) で RPG2 と同じ。
- 屋内の判定も同じ: 種類 + 1 が 0x10〜0x1C のタイルがあるとランタイム +0x546C が立つ。

### 3.2 区画 1: 床のギミック (16 B)
`{s16 x, s16 y, …, u8 +0x0C, u8 +0x0D 種類}`。種類 3 は置かない、0 はマップのフラグ (+0x546F) を立てる、2 はセル +0x0A の bit0 を立てる。オブジェクトは `FUN_0036493c(x, y)`。22 マップにだけある。

### 3.3 区画 2: 置物 (20 B)
| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | mapObject の行 (0 で打ち切り) |
| +0x04 / +0x06 | s16 | x / y (100 単位) |
| +0x08 / +0x0C | f32 | ずれ (× 100) |
| +0x10 | u8 | 向き 0〜3 (`FUN_00276078` で c = 1〜4) |

- mapObject の行 0xEF〜0xFE は高さを −5 にする (RPG2 の 0x9E〜0xAD の壁際の置物に当たる)。置くのは `FUN_00275f2c`。

### 3.4 区画 3: 出入口・階段・扉 (24 B)
| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | この地点の ID (ほかのマップの行き先として参照される) |
| +0x04 | u32 | **EventObject の行** (0 = なし) |
| +0x08 / +0x0A | s16 | x / y (セル) |
| +0x0C / +0x10 | f32 | ずれ (種類 0x64 のとき、× 100) |
| +0x14 | u8 | 向き (セル +0x15 に +1 して入る。RPG2 の +0x15) |
| +0x15 | u8 | **種類** (RPG2 の +0x14) |

- **行き先 (マップ・地点) はレコードではなく EventObject の +0x10 / +0x14 に移った** (§5)。RPG2 のレコードの +0x04 / +0x08 に当たる欄はない。
- 種類 → セルの欄の変換 (`FUN_002ca100`) は RPG2 と同じ表 (4 上り階段 / 5 下り階段、0x0B〜0x0E 鍵、0x14〜0x42 町の建物、…)。種類 0x14〜0x42 は「そのまま」で、RPG2 (0x13〜0x2E) より範囲が広い。
- **種類 0x64 = 壁の扉** (RPG2 の区画 7)。`FUN_00274a6c` が置き、位置は 250 + x × 500 + dx × 100。ハンドラは `FUN_004bcf30`。v4096 で 86 件。
- モデルと置き方は §9.6。
- 種類の件数: 0x15 (21) が 210 件、5 / 4 (階段) 132 / 131、0x0A 111、9 102、0x64 86、2 56 …

### 3.5 区画 4: 宝箱 (24 B)
`{u32 +0x00, u32 EventObject の行, s16 x, s16 y (125 単位、0〜299。範囲外は 0), f32 dx, f32 dz, …}`。オブジェクトは `FUN_003684a4`、ハンドラは `FUN_004bc4ec`。+0x00 の下位バイトは宝箱の見た目 (0〜2、§9.1)。中身は EventObject の +0x10 が指す treasureGroup の行 (§10)。

### 3.8 区画 9 (24 B、推定)
`{u32 種類, u32, u8 +0x08 値, …, s16 +0x0C x, s16 +0x0E y}`。種類 1〜3 は `FUN_001ff580`、0 は `FUN_004bf6c8` に渡す (マスターの +0x50C の表と照合)。34 マップ (主に島・町の外) に 1,705 件。植物・釣りの地点と推定 (未確認)。

## 4. タイルの見た目 (確定)

- mapData の行: mapGroup +0x2E (屋内なら +0x2F)。designedMap の行があればその +0x0C。マップ表 +0x28 のキーが 0 でもなし (`*DAT_00227e60`) でもなければ、そのキーで mapData を引き直す (`FUN_00227bf0`)。RPG2 の +0x26 / +0x27 が +0x2E / +0x2F に移っただけ。
- モデル (`FUN_00313628`): `mapParts[セルのタイル (= 種類 + 1)] + 8 + タイルセット × 0x20 + 文字 × 4` のハッシュ。タイルセット = mapData[0]、アーカイブ = mapResource[mapData[1]] の +0x00。
- mapParts は **67 行 × 0x20C** = `{u32 a, u32 b, 16 タイルセット × 8 文字 × u32, u32 末尾}` (RPG2 は 48 × 0x18C、12 タイルセット)。
- モデルのエントリはアーカイブ (例 `0AB60000`、`07E40000`) の **種別 8** = 0x180 バイトのヘッダー + BCH。ヘッダーの +0x54〜 は UTF-16 のパス (`rom:/cg/model/map/map_parts/bgpt_15_green/bgpt_15_green_01.bch`)、+0x3C = 0x180 (BCH の位置)、+0x40 = BCH のサイズ。
- mapResource (34 × 0x24): +0x00 タイルのモデルのアーカイブ、+0x04 テクスチャのアーカイブ、+0x08 そのテクスチャのエントリ (種別 2、`bg_ground_01` など)、+0x0C 空のモデル (モデルのアーカイブの種別 8、`bgpt_01_caveA_sky`)、+0x10 戦闘の背景 (アーカイブ `52120000` の種別 8、`btmp_01_caveA`)、+0x14 土台のモデル (モデルのアーカイブ、`bgpt_01_caveA_base`)。
- mapObject (510 × 0x38): +0x00 アーカイブ、+0x04 モデルのエントリ (種別 2 の BCH)。

## 5. EventObject (0x58 バイト、確定)

### 5.1 欄
RPG2 (0x50) の欄が、+0x08 の後ろに「消える条件の値」が 2 つ増えて、**+0x08 以降が 8 バイトずつ後ろにずれた**形。

| 位置 | 型 | 内容 | RPG2 |
|---|---|---|---|
| +0x00 / +0x04 | u32 × 2 | 出る条件の値 1 / 2 (+0x53 とともに) | +0x00 のみ |
| +0x08 / +0x0C | u32 × 2 | 消える条件の値 1 / 2 (+0x54 とともに) | +0x04 のみ |
| +0x10〜+0x4B | | 種類ごとの引数 (RPG2 の +0x08〜+0x43) | |
| +0x10 / +0x14 | u32 | 出入口の種類 (0x13 / 0x15 / 0x16 / 0x18 / 0x1B / 0x1E / 0x1F / 0x21 / 0x2E の一部): **行き先のマップ / 地点 ID** (区画 3 の +0x00) | 区画 3 にあった |
| +0x4C | u16 | 状態の枠 (0xFFFF = 行番号) | +0x44 |
| +0x4E | u16 | モデル (mapObject の行)。範囲では半径 | +0x46 |
| +0x50 | u16 | bit15 と下位 15 bit を範囲の登録に渡す (推定: 範囲の高さなど) | +0x48 |
| +0x52 | u8 | 種類ごとの引数 (1 / 2) | +0x4A |
| +0x53 | u8 | **出る条件**の種類 (0 = なし) | +0x4B |
| +0x54 | u8 | **消える条件**の種類 (0 = なし) | +0x4C |
| +0x55 | u8 | **種類** | +0x4D |
| +0x56 / +0x57 | u8 | 完了時の状態の値 (推定) | +0x4E / +0x4F |

- 行の読み出しは RPG2 と同じ: 今いるダンジョンの表がマスター +0x428 (`FUN_0022c084(+0x428, 行)`)。
- 状態の枠 (推定): mapGroup +0x22 (u16) = 先頭、+0x24 (u8) = 数 (D10 = 0 / 51、D20 = 51 / 65 … と積み上がる)。

### 5.2 出現条件 (確定)
`FUN_004b6ac8(行)` = 出る: +0x53 が 0 か、条件 (+0x53, +0x00, +0x04) が成り立つ。`FUN_004b6b38(行)` = 消える: +0x54 が 0 でなく、条件 (+0x54, +0x08, +0x0C) が成り立つ。

条件は `FUN_004b62bc(行, 種類, 値 1, 値 2)`。**RPG2 (181 種類) とは別の表**で、値を 2 つ取る。セーブ変数は `FUN_004a2740(セーブ, キー, 添字, 出力)`: キー 0xF9 = 値 (u8)、0xFA = フラグ。ダンジョンの範囲は mapGroup の +0x26 (u16、0xF9 の先頭) / +0x28 (数)、+0x2A (u16、0xFA の先頭) / +0x2C (数)。

| 種類 | 成り立つとき |
|---|---|
| 0x01 | 名前つきの条件 値 1 (`FUN_001ed9b8`。例 1 → 0xF9[4] = 3、2 → 0xF9[7] = 3 …: ボスを倒した。全体は `story.md` §3.2) |
| 0x02 / 0x03 | ダンジョン 値 1 のフラグ 値 2 が立っている / 立っていない |
| 0x04 / 0x05 / 0x06 | 今のダンジョンの値 値 1 が = / ≥ / ≤ 値 2 |
| 0x07〜0x11 | ダンジョン 値 1 の値 値 2 が = 種類 − 7 (0〜10) |
| 0x12 / 0x13 | フラグ 0xFA[値 1] が立っている / 立っていない |
| 0x14 / 0x15 / 0x16 | 値 0xF9[値 1] が = / ≥ / ≤ 値 2 |
| 0x17 / 0x18 | セーブのキー 0x49 の 値 1 が真 / 偽 (値 1 = 0 は真。種類 0x0C / 0x1C の行だけが使う、`story.md` §3.3) |
| 0x19 / 0x1A | `FUN_004ef1a4(値 1)` の結果が = / ≠ 値 2 (未解析) |
| 0x1B / 0x1C | 値 1 = 0x65〜0x69 で選ぶ判定 (`FUN_0038d250` など。未解析) / その否定 |
| 0x1D / 0x1E | `FUN_001ed418(今のダンジョン, …)` が ≥ / ≤ 値 2 (未解析) |
| 0x1F / 0x20 / 0x21 | 表 (`FUN_004a2d3c`、値 1 の行) の値が = / ≥ / ≤ 値 2 |
| 0x22 | `FUN_0021152c(値 1)` がこの行 |

バニラで多いのは、+0x53 = 0x17 (390 行)、+0x54 = 0x15 (106 行) / 2 (73 行)。

### 5.3 種類 (+0x55) と動作の生成
- 作りは RPG2 と同じ (`events.md` §1): 区画のレコードがハンドラ (`FUN_003128d4` が基底: +4 = 行、+8 = EventObject の行) を作り、vtable[4] の「動作の生成」(引数: ハンドラ、+0x55 の種類、…) が動作のクラスを作る。
- **種類 0x2E (46) = スクリプト** (RPG2 の 0x24)。例: 出入口のハンドラ (`FUN_004bcf30`、vtable 0x588104) の動作の生成 `FUN_004bc7c8` は、0x2E のときダンジョン (`FUN_004ee968(*+0x5C)`) で分岐して `FUN_00195fb0` などダンジョンごとの関数に入る。v4096 で 636 行。
- 同じ `FUN_004bc7c8` が扱う種類: 0x13 / 0x14 / 0x15 / 0x16 / 0x17 / 0x18 / 0x19 / 0x1A / 0x1B / 0x1C / 0x1D / 0x1F / 0x20 / 0x21 / 0x2E (出入口・扉・階段の動作)。

## 10. 宝箱の中身 (treasureGroup、確定)
- マスター 21350000 の `treasureGroup.bin` (+0x310、283 行 × 0x50)。1 行は 10 枠 × `{u32 値, u16 重み, u8 種類, u8 0xD0}`。値が 0 の枠は飛ばす。空の枠は `{0, 1, 1, 0xD0}`。
- 開けると `FUN_00229734` が重みに比例して 1 枠を選び、`FUN_001E66B0` が種類で分ける: 1 = アイテム 1 個 (値 = アイテム ID、メッセージ 0x2C5)、2 = G (値 = 額、0x2C8)、3 = ジュエル (値 = 数、0x2CA)、4 = **戦闘** (`FUN_00211228(値 & 0xFF, 0)`: monsterGroup の行 = 値の下位バイトと戦う。BGM は群れの +0x32 bit2)。種類 4 の値は 1〜4 = たからばこぞう / トレジャーメイジ / おばけざいほう / ビックリッチ。
- 例: 行 135 = 100 G / 300 G / 1000 G (重み 5 / 3 / 1)。

## 11. 出現する群れ (区画 6、確定)
- 区画 6 のヘッダー (+0x00) が、マップ全体で出る群れ (monsterGroup のハッシュ)。0 = 出ない。既定のハッシュ 0x6B223E6C は 0x557C00 にある (monsterGroup 行 0 = なし)。v4096 で 0 でないヘッダーは 89 マップ。
- 区画 6 のセルは、そのセルだけ出る群れを上書きする。データの 988 個のセルはどれも群れを持つ (RPG2 の「敵が出ないセル」に当たる値 0 のセルは RPG3 のデータにはない)。
- マップ表の +0x30 は敵の出方 (§11.1)。

### 11.1 敵の出方 (マップ表 +0x30、確定)
- `FUN_002760AC` がマップに入るとき +0x30 をランタイム +0x546A に写す。ただし写すのは区画 6 のヘッダーが既定 (0x6B223E6C) でないときだけで、既定なら 0。初期値は 3。
- `FUN_0047DB20` がこれを歩く敵の出し手 `FUN_002C60B4` に渡す。出し手は表 `0x557DA0` から同時に出る数の上限 (+0x161) と、次が出るまでの間隔 (秒、最小〜最大の乱数。`FUN_002C8E90` が +0x24 に置く) を引く。今の数は +0x20。

| 値 | 同時に出る数 | 間隔 (秒) |
|---|---|---|
| 1 | 2 | 2〜5 |
| 2 | 3 | 2〜5 |
| 3 | 4 | 1〜3 |
| 4 | 6 | 1〜3 |
| 5 | 10 | 1〜1.5 |

- v4096 のデータは 3 / 4 / 5 だけ。
- Panana: マップページで何も選ばないと、ヘッダーの群れ (選び直せる) とセルごとの群れが出る (panana#99)。
