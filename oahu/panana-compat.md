# Panana の RPG2 / RPG3 両対応の所見

`oahu/analysis.md` の結果をもとに、Panana (現在 RPG2 専用、TypeScript 約 23,000 行) を RPG3 にも対応させる場合の見通しをまとめる。結論を先に書く。

## 結論
- **アーカイブ形式は 2 と 3 で同じ。** RomFS のルートアーカイブ (version 5 / 7、28 バイトのエントリ、ZIP / LZ10)、GS テーブルのヘッダー、GMSG の形式はどれも共通で、エントリのハッシュも同じ名前なら同じ値。読み書きの土台はそのまま使える。
- **違うのは中身。** テーブルの行のサイズと欄の並び、メッセージのタグ番号と ID の振り方、code.bin のアドレスはすべて別。さらに 3D モデルが CGFX から BCH (H3D) に変わった。
- したがって **1 つのアプリで両対応にするのが現実的**。共通の土台 (ROM 読み込み・アーカイブ・GMSG・UI の枠・書き出し) を共有し、ゲームごとの部分を「ゲーム定義」として分ける。ただし RPG3 側の編集機能は、テーブルの欄と code.bin の解析をやり直す分だけ、RPG2 と同じだけの解析が要る。
- 最初の一歩は小さい: RPG3 のダンプを読めるようにし (Base + Update の 2 ファイル入力)、テーブルとメッセージを表示するところまでは、既存のコードの大半を流用できる。

## 1. 層ごとの見通し

| 層 (現在の行数) | 内容 | RPG3 での扱い |
|---|---|---|
| `src/rom/` (464) | CIA / NCCH / RomFS / BLZ / IPS | **ほぼ共通**。タイトル ID の判定を 2 作分にし、Base + Update の 2 ファイル入力と `patchList.bin` による仮想マージ (`analysis.md` §3.3 A) を足す。100〜200 行程度 |
| `src/archive/` (381) | gsarc / gstable / LZ10 / ZIP | **共通**。version 7 と unk = 1 はそのまま読める (書き戻しも元の値をコピーしているので可) |
| `src/game/gmsg.ts` など | GMSG の読み書き | 形式は共通。タグの表 (ルビ 0x27〜 → 0x2B〜 など) と ID 範囲をゲームごとにする |
| `src/game/` (8,070) | テーブルの欄、イベント、スクリプト、code.bin 由来の定数・パッチ | **大半がゲームごと**。欄の定義・アドレス (`FUN_` / 定数約 300 か所)・code.ips の中身は RPG3 で解析し直し |
| `src/cgfx/` (2,111) | CGFX → three.js | RPG3 のモデルは BCH (H3D)。**BCH の読み込みを新しく作る** (頂点・テクスチャの PICA の部分は CGFX と共通なので流用できる)。エフェクトは RPG3 も CGFX |
| `src/editor/` (4,001) | マップエディタ | マップの区画の形式を RPG3 で調べてから。RPG2 の構造と近ければ共通化、違えば別実装 |
| `src/sound/` (1,020) | bcsar / bcstm | **共通 (確認済み)**。RPG3 も `sound/sound.bcsar` と bcstm で、そのまま読めて鳴らせる (`oahu/sound.md`) |
| `src/pages/` `src/ui/` (6,410) | 画面 | 枠・ダイアログ・一覧などは共通。各エディタの欄はゲーム定義から作る形にすると重複が減る |
| `src/export/` (124) | MOD の書き出し | 書き出し先のタイトル ID を `00040000000EF000` にする。RPG3 では patchList の 11 アーカイブを Update 版から作る (`analysis.md` §3.3 B)。**MOD を Update CIA として書き出す**方法も取れる (`oahu/update.md`。`ctrbuild.py` の RomFS / NCCH / CIA の組み立てを TypeScript に移す。数百行) |

## 2. 分け方の案
- `src/rom/`・`src/archive/`・GMSG・UI の枠は共通のまま。
- ゲームごとの部分を `src/game/kahara/` と `src/game/oahu/` (内部名) に分け、起動時にダンプのタイトル ID (`00040000000A7900` / `00040000000EF000`) で選ぶ。
- テーブルの欄は「オフセット・型・意味」の定義 (いまの各 `*.ts` の読み書き関数) をゲームごとに持つ。エディタはその定義を受け取る。
- RPG3 で解析が済んでいない機能は、その画面を出さない (段階的に足す)。

## 3. 要検討の点
- **3D の作り直しが一番大きい。** マップ・モンスター・キャラクターがすべて BCH なので、マップエディタとモンスターの表示・モーションは BCH の対応が前提になる。
- **code.bin の解析はゼロから。** イベントの ARM 実行器、AI 向けのスクリプト逆アセンブル、code.ips の各パッチは、RPG3 (Update, TitleVersion 4096) のアドレスで調べ直し。
- **入力が 2 ファイルになる。** ユーザーには Base と Update の CIA を両方選んでもらう (片方だけなら警告)。Update のバージョンは 4096 だけ確認した。
- コードベースの大きさ: 共通化すると、RPG3 の分は主に `src/game/` 相当 (いまの 8,000 行と同程度) と BCH の読み込み (CGFX と同程度、2,000 行前後) が増える見込み。共通部分を二重に持つよりは小さい。
