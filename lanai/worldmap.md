# RPG FREE! (lanai) のワールドマップ (W01 / W02)

> 対象: 電波人間のRPG FREE! 日本版 Base v0 + Update v17408 (code.bin は Update)。分類: ゲーム既存仕様。
> 根拠: Panana (`LanaiSession` / `LanaiMaps`) で全 9 世界のデータを読んだ結果と、code.bin の逆アセンブル (capstone 5.0.7)。2026-11-10 にユーザーの PC で調べた (ROM のテストは panana `test/lanai-world.test.ts`)。
> アドレスは実行時アドレス (code.bin の位置 + `0x100000`)。RPG3 の [worldmap.md](../oahu/worldmap.md) と同じ作りで、違うところを中心に書く。

確度: **確定** = コードとデータの両方で裏付けた、またはデータの全件で成り立つ。**推定** = 形や類似からの見立て。

## 結論

RPG3 (oahu) とほぼ同じ作り。違いは 3 つ。

1. 地形 (oahu は master の `W01_ground.bin`) は、**マップ表の行のスロット 9** にある (マップ DB のエントリ)。コンテンツごとに別の世界。
2. code.bin に区画の表 (oahu の `0x556D54`) はない。ゲームは**マップ表の行のスロット 0〜9 をそのまま使う**。スロット k の中身は oahu の区画 k と同じ (宝箱のスロット 8 だけ 1 件 12 B に変わった)。
3. 入口の行き先は EventObject の**動作の型 `0x8000001F`** (+0x14 マップ、+0x18〜+0x24 地点 × 4)。入口のモデルは EO の +0x5A (MapObject の行) で、0 なら WorldmapParts の +0x0C。向きは lanai のほかの区画と同じ 1 / 2 / 4 / 8 のビット ([map.md §3.2](map.md))。

地形の形・部品の広げ方・プールの数は oahu と同じ。プールは 9 つの世界すべてで oahu の再計算方法と全件一致する。

区画のハッシュは名前から決まるので、9 つの W01 は同じハッシュ、3 つの W02 も同じハッシュ (DB はコンテンツごとに別)。どのスロットも DB にある (サイズ 0 のものもある)。

### 1.2 マップ表の行 (+0x28〜+0x3C)

- W01: +0x28 = 0x80000000 (c2 / 3 / 12 / 69) か 0、+0x2C = MapGroup の行、+0x30 = 3、+0x34 = 0、+0x38 = 0x80000002 (c2 だけ 0x80000007)、+0x3C = 1。
- W02: +0x28 = 0、+0x30 = 3、+0x34 = 0、+0x38 = 0x80000003、+0x3C = 1。
- +0x38 は行 ID の形だが、どの表かは未解析。

### 1.3 世界ごとの違い (確定)

- スロット 9 (地形) は 9 種類 (コンテンツごとに別の世界)。同じコンテンツの W01 と W02 はバイト単位で同じ (33 / 71 / 126)。
- 部品のある範囲 (x / y / 起点のセル数): c2 32-68 / 24-77 / 440、c3 0-299 / 0-299 / 8557 (部品 51 が 7144 で全面を覆う)、c12 17-78 / 29-85 / 944、c33 0-99 / 2-97 / 2144、c69 43-58 / 39-60 / 142、c71 40-60 / 39-56 / 130、c101 20-54 / 9-53 / 449、c124 46-84 / 21-64 / 594、c126 12-87 / 11-77 / 1623。
- スロット 1 は c124 以外すべて 0。スロット 7 は全件 0。
- W02 は W01 と入口の位置が同じで ID が違う (c33 / c126 は F3D0C9EA)。c71 の W02 は入口が 3 つ。c33 / c126 の W02 の範囲は W01 と同じ位置で、AreaInfo の行 ID だけ +6 ずれる。

## 2. スロット 9: 地形 (確定)

oahu の `W01_ground.bin` とヘッダーの値まで同じ。

```
+0x00     u32 1, u32 0x14 (グリッド), u32 0x2BF34 (プール), u32 0x2C0B0 (区画 7 の初期値リスト), u32 0x2C0B4
+0x14     300 × 300 × {u8 WorldmapParts の行, u8 向き}   y × 300 + x、0 = なし
+0x2BF34  u32 × 95   部品ごとのプール
+0x2C0B0  {s16 x, s16 y} のリスト (x = 0 で終わり)。9 件とも最初から空
+0x2C0B4  u32 × 95 (380 B)。9 件とも全部 0 で用途は未解析 (oahu ではファイルの外を指していた欄)
```

- 向き: byte 1 は全件 0〜3。**ここだけは 1/2/4/8 ではなく oahu と同じ 0〜3** で、ローダーは `& 3` だけ取る (`@0x1f473c`)。
- 部品の値: 実データは 2〜83。
- プール: 9 世界 × 95 個すべてが、2 × 2 ブロック内の起点のセル数の最大 (oahu §3.2 の再計算) と一致。値は 1〜4。
- ローダー `FUN_001f4558`:
  - 部品ごとに `FUN_0031C038(master のホルダー +0xFCC, 部品)` で WorldmapParts の行を引く。+0x04 のフラグ: 0x08 でセルに印、0x10 で 2 × 2、0x20 で 2 セル (向き 0 / 2 なら x+1、1 / 3 なら y+1)。oahu と同じ。
  - 引数 (スタック +0x9C) が 0 のときは部品 0x35 / 0x37 を 0x3E、0x36 / 0x38 を 0x3F に置き換えて読む (`@0x1f48c0`。mount_04〜07 → wall_01 / 02)。条件は未解析。
  - スロット 1 は `FUN_002108f0`、スロット 7 は `FUN_002107c0` で読む。ヘッダー +0x0C のリストのセルは `FUN_00210784` で立てる。
  - その後 `@0x1f4dcc〜` で、部品が 0 / 1 / 0x41 / 0x54〜0x56 以外のセルに、フラグ 0x04 の有無で 2 / 1 を書く (地形の種類の格子と推定)。
- 部品のモデルを読むのは `FUN_002b8a6c` (部品 2〜0x56、0x54〜0x56 は別の大きさ)。プールの数を読む所は `FUN_002a8aa0` の中と推定 (未確認)。

## 3. スロット 2: 入口 (32 B、確定)

| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | WorldmapParts の行。ROM は 88 / 90 / 93 だけで、0 (oahu の「モデルなし」) はない |
| +0x04 | u32 | 全件 0。モデルは EO +0x5A から決まる (§4) |
| +0x08 | u32 | 入口の ID。MapGroup +0x18 の「最初の地点」もこの ID |
| +0x0C | u32 | ワールドの MapGroup の EventObject の行 (1〜5) |
| +0x10 / +0x12 | s16 | x / y (セル) |
| +0x14 / +0x18 | f32 | ずれ (0、±0.5、±1) |
| +0x1C | u8 | 向き 1 / 2 / 4 / 8。コードが 1 / 2 / 4 / 8 を比べて角度を選ぶ (`@0x1fc390`) |
| +0x1D〜+0x1F | | 全件 0 (oahu の mapJumpPoint の行は使われていない) |

例 (c2 #0、S01OUTF01 へ): `5a000000 00000000 9a647da6 03000000 2500 4a00 00000000 00000000 01 00 0000`

## 4. 入口の行き先と戻り (確定)

- 入口 +0x0C は、その世界の MapGroup の EventObject の表 (MapGroup +0x1C。W01 は `52858400`、W02 は `4211EC00`、1 行 100 B) の行。
- 行き先の動作は型 **`0x8000001F`**。全 28 件がワールドの EO にだけある。+0x14 = 行き先のマップ、+0x18 / +0x1C / +0x20 / +0x24 = 地点 ID × 4。4 つの使い分けは未解析 (入る向きごとと推定)。
- c3 / c124 には型 0x2D (スクリプト) の入口もある。
- **EO +0x5A u16 = 入口のモデル** (MapObject の行)。0 なら WorldmapParts +0x0C (`@0x1fc334`)。ROM の値: 535 / 538 / 539 tepee02 / 541 cave04 / 542 cave05 / 544 house07 / 553 pyramid16 / 780 mount_05 / 781・782 tower42・43。
- EO の例 (c2 W01 EO[1] → D01001F01): +0x10 = `1f000080 63283d9c bee32078 × 4`、+0x5A = 0x21A。
- 戻り: 行き先のマップの EO の型 0x80000011 (ダンジョンの出口: 引数 A8654391、入口の ID)、0x80000014 (同じ引数)、0x8000000D (村の端: A8654391、入口の ID、向き 1/2/4/8)。到着点は入口の ID そのもので、oahu の「モデルなしの出る位置」はない。W02 向けは 09A1DA1B。
- MapGroup: +0x14 = A8654391、+0x18 = 最初の入口の ID、+0x2E = 0x42 (下位 3 bit = 2 = ワールド。[battle-field.md](battle-field.md) の BGM の分岐)。MapData +0x04 = 0x13 (BGM_MAP_WORLDMAP)。
- 船の港の一覧はない (WorldmapPort / MapJumpPoint / MapAppearWorldmap の表がない)。

## 5. ほかのスロット

- **スロット 3 / 4 (エンカウントの範囲、確定)**: `{u32 AreaInfo の行 ID, s16 x, s16 y, u8 幅, u8 高さ, u16 0}`。全件 3 × 3。コードは x・y・幅・高さを 3 で割る (`× 0x5556 >> 16` と `× 0xAB >> 9`、`@0x1fc8ec`)。ROM の x・y は 3 の倍数でないものが多く (c2 は 21 件中 2 件だけが倍数)、ゲームは切り捨てて使う。例: `02000080 3200 1a00 03 03 0000`。
- **AreaInfo** (コンテンツの表 `E86E3C00`、12 B、行 ID 付き。ホルダー +0x15E4 で引き、+0x04 が 0 なら飛ばす): +0x00 u32 0、+0x04 u32 MonsterGroup の行 ID (全件そのコンテンツにある)、+0x08 u8 1 = 陸 / 2 = 海 / 4 = 行 0、+0x09〜 D0。oahu はハッシュで引いていたが lanai は行 ID。
- **スロット 5 (32 B)**: c3 に 1 件。ダンジョンの区画 8 と同じ形と推定。
- **スロット 6 (20 B)**: データなし。oahu の区画 6 (置物) と同じ形と推定。
- **スロット 7**: 全件 0。リストも空。oahu と同じく「地図の開けた範囲」と推定。
- **スロット 8 (12 B)**: `{u32 EO の行, u32 種類, s16 x, s16 y}` (`@0x1fd170`。oahu は 8 B)。c3 に 4 件 (EO 5 / 4 / 7 / 6、種類 0)。種類 0 のモデルは EO +0x5A (0 なら MapObject の行 0x20)。c3 の 4 件は gimk_02_door_033 で、動作は 0x2D。種類 1 は `@0x1fd054` で別の処理。ROM のワールドに宝箱はない。
- **暗い海 (スロット 1)**: 値があるのは c124 だけ (0 = 2617、1 = 172、2 = 176、3 = 87035)。1〜3 はすべて部品のないセル。oahu と同じ意味と推定。

## 6. WorldmapParts (master `5DD05400`、95 行 × 16 B、確定)

コードは master のホルダー +0xFCC で引く ([battle-field.md](battle-field.md) の +0xFC8 とは 4 ずれる)。

| 位置 | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | 地形のモデル = アーカイブ `0E820000` の type 4 (BCH、`bgpt_wld_*.bch`、86 個) |
| +0x04 | u8 | フラグ (0x10 = 2 × 2、0x20 = 2 セル、0x08 = 印、0x04 / 0x02 / 0x01) |
| +0x05 | u8 | 0x34 |
| +0x08 | u32 | BattleField の行 (3 sea / 4 flat / 5 opnforest / 6 sand / 7 snow / 8 snowfst) |
| +0x0C | u16 | 入口の既定のモデル (MapObject の行) |
| +0x0E | | D0D0 |

- 例: 行 1 `0078df34 02 34 0000 03000000 0000 d0d0` (sea_00)、行 88 `00000000 00 34 0000 05000000 1602 d0d0`。
- 行の並び: 0 = なし、1 = 海、2〜86 = 地形 (oahu と同じ並び)、87〜94 = モデルなし (入口の種類)。
- +0x0C: 88 → 534 wld_cave02、89 → 535 wld_twn01、90 → 533 wld_tower01、91 → 538 obj_invisible (F9270000)、92 → 534、93 → 536 wld_fish21。
- 入口のモデルはアーカイブ `D64E0000` (`wld_*.bch` が 44 個)。
- 共有テクスチャは `0E820000` の `tex_worldmap.bch` (`D47B4000`、`@0x1f4968` に直書き)。ほかに `tex_wld_menu.bch`、`wld_ship03` / `04.bch`、`bg_wld_{land,sea}_{back,front}.gsc`。

## 7. code.bin の検索 (確定)

- W01 / W02 と各スロットのハッシュ、`5DD05400`、マップ DB とマップ表のエントリは code.bin に u32 として現れない (区画の表はない)。
- 直書きがあるもの: `0E820000` (`@0x1c997c` / `0x1f414c` / `0x1f4260` / `0x431fcc` / `0x432330`)、`D47B4000` (`@0x1f4968`)。

## 8. 編集するには

- 地形: マップ DB のスロット 9 を書き換え、プールを oahu の方法で作り直す (master は触らない)。W01 と W02 はハッシュが別なので別々に書ける。
- 入口: スロット 2 のレコードと、EO の型 0x1F の +0x14 / +0x18〜+0x24、+0x5A (モデル)。戻りは行き先のマップの EO (型 0x11 / 0x0D など) の引数 2 = 入口の ID。
- 向き: 地形のセルは 0〜3、入口と出口は 1 / 2 / 4 / 8。
- 範囲: x・y・幅・高さは 3 の倍数にするのが安全。
- Panana の実装: panana `src/lanai/worldmap.ts` (編集の形)、`worldsource.ts` / `WorldPage.tsx` (ワールドマップのページ)。

## 9. 未解明

- マップ表 +0x38、地形ヘッダー +0x10 の 380 B、EO 型 0x1F の 4 つの地点の使い分け、型 0x14 と 0x11 の違い。
- 部品の置き換え (mount → wall) の条件、+0x04 の 0x01 / 0x02 の意味、プールを読む所。
- スロット 8 の種類 1、スロット 5 / 6 の欄 (データが少ない)、暗い海の段階 1・2 の見た目、入口のモデルの角度 (1 / 2 / 4 / 8 と角度の対応)。
- エミュレータでは確かめていない。
