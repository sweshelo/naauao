# チェックイン・通信・配信の表

対象: lanai Update v17408 の code.bin。サーバーは 2026 年時点で停止している。以下は **ゲーム側のコードから読んだ要求と応答の形**。実際のサーバーの応答を記録したものではない。

## 1. 通信先 (code.bin の文字列、確定)

ホストはすべて `https://la1.denpamen.com`。

| パス・クエリ | 用途 | 関数 |
|---|---|---|
| `/checkinserver?req=time&tbl=checkin&prod=checkin_dev` | サーバー時刻 (GET) | `FUN_0027D9EC` |
| `/checkinserver?req=check&tbl=checkin&prod=checkin_dev&support_id=<u64>` | 登録の確認 (GET) | `FUN_0043A0A0` |
| `/checkinserver?req=bonus_tbl&tbl=checkin&prod=checkin_dev` | **配信する表** (GET) | `FUN_0043A698` |
| `/checkinserver` (POST、`req=create` / `update`) | プレイ記録の送信 | `FUN_0043A264` / `FUN_0043A7F4` (組み立ては `FUN_0026EA98`) |
| `/campaigncodeserver` (POST、`req=res` / `sre`) | コードの照会 | `FUN_00437F04` / `FUN_00439BA4` |
| `/gameserver?req=res_ver` | データの版 (GET) | `FUN_002A33D8` |
| `/gameserver?req=check|player_data|rank|rand3|top10|current_party|total|check_party&prod=ranking_dev&reg=0…` | Wi-Fi コロシアム (ランキング) | `0x4A2930` 付近の文字列 |
| `/ctr_state/gs`、`gs_c` / `gs_j` / `gs_r` / `gs_u`、`/ctr_ec/` | ジュエルの購入 (nn::ec) と推定 | 未解析 |

- `prod=checkin_dev` / `ranking_dev` は製品版のコードにそのまま入っている。
- code.bin に `la1.denpamen.com` の証明書 (発行元 Nintendo Class 2 CA - G3、Genius Sonority Inc.) が入っている (`0x4A2C9A` 付近)。接続先の検証に使うと推定。

## 2. 共通の約束

### 共通: auth_token
- GET は URL の後ろに `&auth_token=<トークン>` を付ける (`FUN_0027CD9C`、書式 `%s&auth_token=%s`)。POST はフォームの欄 `auth_token` を足す (`FUN_0027CC6C`)。
- トークンは `0x5A87F4` (0x201 バイト) にあり、`FUN_004359EC` で取得する。
  - 取得の関数 `FUN_0034C624` に、32 桁の 16 進 `899c794614ed4195bec595b496c01aa4` と 0x15180 (= 86400 秒) を渡す。
  - 取得した後、`+` を `.`、`/` を `-`、`=` を `*` に置き換える (URL 用の base64)。
- 取得の仕組みは、NNID の independent service token (クライアント ID と有効期間を渡す API) と推定する。**サードパーティのサーバーに向けるとき、トークンの検査はサーバー側でしないことにできる。ただし取得そのもの (任天堂のアカウントのサーバーとの通信) が失敗したときにゲームがどう振る舞うかは未確認。**

### 応答の形
- HTTP の状態が 200 でないと失敗。
- 本文はテキスト。`,` で区切った欄として読む。最初の欄が `ERROR` なら失敗 (`ERROR,10` / `ERROR,400`〜`406` などの文字列がある)。成功は `SUCCESS`。

## 3. checkinserver

### req=time
応答 `<状態>,<日時>`。2 つ目の欄は 15 文字以上で、`年 4 桁` `月 2` `日 2` `(1 文字)` `時 2` `分 2` `秒 2` を位置で読む (+0、+4、+6、+9、+11、+13)。8 文字目の区切りは読まない (例 `SUCCESS,20160401 120000`)。

### req=check
URL に `support_id` (`%llu`) を付ける。応答の 2 つ目の欄が `true` なら登録済み。

### req=bonus_tbl (配信する表)
- 応答 (最大 0x3C00 バイト) が `ERROR` で始まらなければ、`SUCCESS,` の後ろを **base64 としてデコード** する (`FUN_002AF0DC`)。
- デコードした内容はチェックインの作業領域 (+0xAA8) に写し、`FUN_002EA8DC` で表の読み手に結び付ける。そこで lanai 形式の GS テーブルとして再配置する ([analysis.md §2](analysis.md#2-gs-テーブル-lanai-形式確定))。
- つまり **配信の中身は、ROM の Checkin 系と同じ形式の GS テーブル 1 個** と見られる。どの表の名前・行の形を期待するかは未確認。行の形は §5 の 0x54 バイトの行と推定する。

### create / update (POST)
欄の並び (`FUN_0026EA98`)。値はすべて文字列。

| 欄 | 中身 |
|---|---|
| `req` | `create` / `update` |
| `support_id` | u64 (`%llu`) |
| `region` | `0` |
| `create_date` / `update_date` / `prev_update` | `%d%02d%02d%02d%02d%02d` (年月日時分秒) |
| `total_num`, `num`, `buy_jewel`, `playtime`, `gold` | `%u` (チェックインの回数・ジュエルの購入・プレイ時間・ゴールドと推定) |
| `total_assets` | `%llu` |
| `continue_num`, `stamina_num_stage`, `stamina_num_ranking`, `rare_gacha`, `event_gacha`, `go_island`, `come_island` | |
| `local_battle_num` / `win` / `lose` / `players` | |
| `coliseum_battle_num` / `class` / `player_point` / `best_a`〜`best_e` | |
| `res_ver` | `%llu` |
| `bdat` | 文字列 (中身は未解析) |
| `auth_token` | §2 |

応答の最初の欄が `ERROR` でなければ成功。`ERROR,11` のときだけ作業領域 +0xAAC に 1 を書く (意味は未確認。メッセージ「お客様の記録がサーバーに見つかりませんでした。本日はチェックイン回数を記録できません。」と関係すると推定)。

## 4. その他のサーバー

- **campaigncodeserver** (POST): `req=res` は `version` (u64)・`response` (u64)・`kind` (`%x`)・`index` (`%u`)。`req=sre` は `version`・`kind`・`index`。ネットワーク経由のコード (CampaignCodeNetwork、`network::CampaignCodeUnique`) の照会・使用済みの記録と推定。応答の解釈は未解析。コードの形式は [codes.md](codes.md)。
- **gameserver?req=res_ver**: 応答 `SUCCESS,a.b.c` を `.` で分けて 3 つの u16 にする。データの版と推定。

## 5. チェックインの表 (確定した部分)

`A9DF0000` に、同じ行の形 (0x54 バイト、欄 `message` +0x34) の表が 7 個ある。

| 表 | 行数 | 中身 |
|---|---:|---|
| **Checkin_Rom** | 89 | 曜日ごとのイベントステージの公開 (「本日、水曜日の23:59までオープン！」)。**ROM の中にある配信の表** |
| CheckinData | 241 | 期間つきのイベント・報酬 |
| CheckinDeliVersion | 64 | 更新データ配信の記念など |
| CheckinEVCK18 / CheckinEVCK19 | 122 / 122 | イベント (EVCK = イベントチェックインと推定) |
| CheckinJewelBuy | 19 | ジュエル購入の特典 |
| CheckinCheckinCount | 19 | 通算チェックイン日数の記念 (100 日〜2150 日) |

ほかに `307C0000` の Checkin (`checkin_debug_JP`、「LanaiToolにてデータを選択し…」の開発用 1 行)、`25D60000` の CheckinOffsetTime (1 行: `0xA, 0`。日付の切り替えの時差と推定)。

### 5.1 行の形 (配信の報酬の構造)
コード入力の CampaignCodeLocal (0x58 バイト) も同じ構造で、+0x34 に「条件に合わないときのメッセージ」が 1 欄増え、以降が 4 バイトずれる。

| off (0x54 の行) | 型 | 内容 |
|---|---|---|
| 0x00 | u32 | 行の種類。0x80000008 = お知らせの見出し (メッセージを出す)、0x80000000 = 報酬だけ、0x80000001 / 7 / 9 / 0x10〜0x13 もある |
| 0x04 / 0x08 / 0x0C | u32, u32, u8 | 条件 1 = (a, b, 種類) |
| 0x10 / 0x14 / 0x18 | | 条件 2 |
| 0x1C / 0x20 / 0x24 | | 条件 3 |
| 0x28 / 0x2C / 0x30 | | 条件 4 |
| 0x34 | 文字列 | メッセージ |
| 0x38 | u32 | **報酬の種類** (`0x80000000 | 番号`、§5.2) |
| 0x3C | u32 | 値 (アイテム ID・フラグの番号など) |
| 0x40 | u32 | 数 |
| 0x44〜0x4C | | 種類ごとの追加の引数 |
| 0x50 | u16 | まとまりの番号 (0xFFFF = なし)。CampaignCodeLocal では +0x54 |

- 条件は `FUN_002FCD38(種類, a, b, …)` で判定する。種類は 0x00〜0x71 の 114 通りで、ジャンプ表で分かれる。Checkin_Rom の曜日の行は **種類 0x39、b = 曜日** (3 = 水、4 = 木、5 = 金)。そのほかの種類の意味は未解析。
- CampaignCodeLocal (`FUN_0017BEE8`) では、条件 1・2 はどちらかが合わなければ失敗、条件 3・4 は **両方とも合うと失敗** (除外の条件)。条件 3 だけ、最後の引数を 0 にして呼ぶ。

### 5.2 報酬の種類 (`FUN_003023E0` の分岐、0x00〜0x2D)

| 種類 | 処理 | 確度 |
|---|---|---|
| 0x00 | ゴールド (上限の確認 `FUN_00459378`) | 確定 |
| 0x01 | ジュエル (上限の確認 `FUN_004593F8`) | 確定 |
| 0x02 | アイテム (値 = アイテム ID `0x8000xxxx`、数) | 確定 |
| 0x03 | master の読み手 +0x1BC の表の行 (値) を数だけ渡す | 表は未特定 |
| **0x08** | **スイッチ (FlagData のキー 0x51、1 ビット × 25000) の [値] に (数 ≠ 0) を書く** (`FUN_002E8538`) | 確定 |
| 0x09 | キー 0x52 (8 ビット × 12500) の [値] に 数 & 0xFF を書く (`FUN_002FF114`) | 確定 |
| 0x0A | キー 0x53 (1 ビット × 700) の [値] に書く | 確定 |
| 0x17 | 電波人間 (上限の確認がボックスの空き) | 推定 |
| 0x1B | 値 (u16)・数・+0x44・+0x48 (u64) を時刻つきで `FUN_001AA954` に渡す。期間つきのステージの公開と推定 (Checkin_Rom の曜日の行が使う) | 推定 |

| その他 | 個別の処理 (未解析) | |

## 6. サービス終了後のオフラインチェックイン

**公式に案内されたとされるコード `A4J8Y13ML7TAWWE1` を、同梱の `lanaicode.py` でデコードした (確定)。**

結果:
- 種類 0 (通常のコード)
- 要る版 1.17.0
- CampaignCodeLocal の **行 49**

行 49 の中身:
- メッセージ「ジュエル販売所は終了しました。Wi-Fiコロシアムは終了しました。」
- 報酬の種類 **0x08、値 0x2A4、数 1**

つまり、このコードを入れると **スイッチ 0x51[0x2A4] が 1 になる**。

このスイッチを読む関数は `FUN_002E7DEC` (11 か所から呼ばれる)。分かった使われ方:
- チェックインの主処理 `FUN_00435BCC`: スイッチが立っていると、その後の通信の処理に進まずに 0 を返す (`0x435DA8` → `0x437428`)。
- `FUN_0027DDF8` / `FUN_002DBB98`: 通信の失敗時の「接続しなおしますか？」を出さない。
- `FUN_002A3968`: スイッチが立っていると、渡されたメッセージを出して真を返す (機能の案内と推定)。

- **チェックインの通信の本体 `FUN_003E9840`** (`req=time` / `bonus_tbl` / `check` / `create` / `update` をすべてここから呼ぶ): スイッチが立っていると `0x3E99C8` へ飛び、`FUN_00167800` を呼んで通信せずに戻る。`FUN_00167800` がオフラインのときの処理と推定 (中身は未解析)。

オフラインのときに、どの表 (Checkin_Rom など) でイベントを開くかの経路は未確認。ROM の中の Checkin_Rom が曜日ごとのイベントを持つので、これを使うと推定する。

### 6.1 スイッチを書く場所 (確定)
FlagData のキー 0x51 を書く関数 `FUN_002E8538` の呼び出しは 3 か所だけ。

| 場所 | 書く値 |
|---|---|
| `0x207964` | [0x2A4] = 1 (ある値が 6 でないとき。条件は未確認) |
| `0x302BDC` | 報酬の種類 0x08 の行: [値] = (数 ≠ 0) |
| `0x477C94` | [0xC] = 1 |

ほかに、キー 0x51 を `mov r1, #0x51` で直に渡して書く呼び出しは見つからなかった (`FUN_002E7DEC` 内の読み出しなどだけ)。サポート用コードの操作 1〜12 ([codes.md §5](codes.md#5-種類-2-サポートのコード-codesystemaction)) もキー 0x51 を書かない。

### 6.2 未改造のゲームでスイッチを 0 に戻せるか (結論: 戻せない)
- 0 に戻せるのは、**報酬の種類 0x08・値 0x2A4・数 0 の行**だけ (§6.1)。
- ROM の中の 0x54 / 0x58 バイトの表 (Checkin 系 7 個、CampaignCodeLocal、CampaignCodeNetwork) を全部調べた。値 0x2A4 を書く行は、CampaignCodeLocal の行 49 (数 1、1 にする行) しかない。
- コード入力 (種類 0) で選べるのは CampaignCodeLocal の既存の行 (0〜49) だけ。中身は行番号と版だけなので、**ROM にない行を指すコードは作れない**。行番号が行数以上だと「コードが間違っています」になる。
- サーバーが配る表 (`bonus_tbl`) に数 0 の行を入れれば戻せる形だが、スイッチが立っているとチェックインの通信そのものをしない (§6) ので届かない。
- したがって、**一度 `A4J8Y13ML7TAWWE1` を入れたセーブを、未改造のゲームとコード入力だけで元に戻す方法は見つからない**。戻すには次のどれかが要る (いずれも未検証)。
  1. 一時的な MOD: CampaignCodeLocal (`7BF7000A`) に「種類 0x08・値 0x2A4・数 0」の行を 1 行足した Update を作る。その行番号を指すコード (`lanaicode.py enc 0 50 0 1.17.0` など) を入れたあと、MOD を外す。スイッチはセーブに残るので、外した後も 0 のまま。
  2. code.bin の `FUN_002E7DEC` を、常に 0 を返すように書き換える (セーブは変えない)。
  3. セーブデータを直接書き換える (セーブの形式と改ざんの検査は未解析。「セーブデータの異常を検知」の処理がある)。
- まだコードを入れていないセーブは、スイッチが 0 のままなので戻す必要はない。
- どのみち、サードパーティのサーバーに接続するには接続先の書き換え (§7) が要る。完全に未改造のままでの準オンライン化は、DNS の向け先を変えたうえで HTTPS の検証を通せる場合に限られる (未確認)。

## 7. サードパーティのサーバーに向けるときの要点 (提案・未検証)

1. **接続先**: code.bin の URL を書き換える。URL の文字列は ro (`0x4A2078` 付近) と text のリテラル (`0x26EE50`、`0x437C74`、`0x439184`、`0x2A377C` など) の両方にあり、元の長さ以下にする。または DNS を向ける。HTTPS の証明書の検証を通すには、証明書の差し替え (§1)、HTTP への書き換え、本体の検証を外す、のどれかが要る。
2. **auth_token** を取れない場合の扱いを確認する (§2)。
3. **応答の形**: `SUCCESS,…` のテキスト。最低限 `req=time` (時刻) と `req=bonus_tbl` (base64 の表) を返せば、任意のイベント (§5 の行) を配れる見込み。
4. **サービス終了モード** (スイッチ 0x51[0x2A4]) が立っていると通信しないので、準オンラインにするにはこのスイッチを 0 に戻す。未改造のゲームでは戻せない (§6.2)。行を足した一時的な MOD とコードで戻すか、読み出しの `FUN_002E7DEC` を書き換える。
