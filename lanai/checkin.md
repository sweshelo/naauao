# チェックイン・通信・配信の表

対象: lanai Update v17408 の code.bin。サーバーは 2026 年時点で停止している。以下は **ゲーム側のコードから読んだ要求と応答の形**。実際のサーバーの応答を記録したものではない。

## 1. 通信先 (code.bin の文字列、確定)

ホストはすべて `https://la1.denpamen.com`。

| パス・クエリ | 用途 | 関数 |
|---|---|---|
| `/checkinserver?req=time&tbl=checkin&prod=checkin_dev` | サーバー時刻 (GET) | `FUN_0027D9EC` |
| `/checkinserver?req=check&tbl=checkin&prod=checkin_dev&support_id=<u64>` | 登録の確認 (GET) | `FUN_0043A0A0` |
| `/checkinserver?req=bonus_tbl&tbl=checkin&prod=checkin_dev` | **配信する表** (GET) | `FUN_0043A698` |
| `/checkinserver` (POST、`req=create` / `update`) | プレイ記録の送信 | `FUN_0043A264` / `FUN_0043A7F4` (組み立ては `FUN_0026EA98`) |
| `/campaigncodeserver` (POST、`req=res` / `sre`) | コードの照会 | `FUN_00437F04` / `FUN_00439BA4` |
| `/gameserver?req=res_ver` | データの版 (GET) | `FUN_002A33D8` |
| `/gameserver?req=check|player_data|rank|rand3|top10|current_party|total|check_party&prod=ranking_dev&reg=0…` | Wi-Fi コロシアム (ランキング) | `0x4A2930` 付近の文字列 |
| `/ctr_state/gs`、`gs_c` / `gs_j` / `gs_r` / `gs_u`、`/ctr_ec/` | ジュエルの購入 (nn::ec) と推定 | 未解析 |

- `prod=checkin_dev` / `ranking_dev` は製品版のコードにそのまま入っている。
- code.bin に `la1.denpamen.com` の証明書 (発行元 Nintendo Class 2 CA - G3、Genius Sonority Inc.) が入っている (§1.1)。

### 1.1 HTTPS の接続 (確定・一部推定)
- 通信は nn::http (`http:C`)。`FUN_002AF494(ctx, url, 方式)` で接続の文脈を作る (方式 1 = GET、2 = POST)。
- 文脈を作るたびに `FUN_002AF42C(ctx, 証明書, 長さ)` → `FUN_0038B010` を呼ぶ。証明書は `FUN_002AF458` が返す `0x4A2C60`、長さは `FUN_002AF464` が返す **0x536 バイト** (DER)。中身は `la1.denpamen.com` の末端の証明書 (Genius Sonority Inc.、発行元 Nintendo Class 2 CA - G3、CA:FALSE、有効期間 2014〜2039 年)。`FUN_0038B010` は nn::http の AddRootCA と推定する。
- 続けて `FUN_002AF470(ctx, 0)` → `FUN_0038AF20` を呼ぶ。SSL の設定 (検証の選択肢) を 0 にすると推定。
- 要求は別のスレッド (`0x437D80`) で実行し、60 秒 (0xDF8475800 ns) で打ち切る (`FUN_00438C5C`)。
- 推定: 信頼するのはこの 1 枚だけなので、別のサーバーに向けるには、証明書の差し替え・`http://` への書き換え・検証を外す、のどれかが要る ([サードパーティのサーバー](private-server.md#2-ゲーム側の-mod))。

## 2. 共通の約束

### 共通: auth_token
- GET は URL の後ろに `&auth_token=<トークン>` を付ける (`FUN_0027CD9C`、書式 `%s&auth_token=%s`)。POST はフォームの欄 `auth_token` を足す (`FUN_0027CC6C`)。
- トークンは `0x5A87F4` (0x201 バイト) にあり、`FUN_004359EC` で取得する。
  - 取得の関数 `FUN_0034C624` に、32 桁の 16 進 `899c794614ed4195bec595b496c01aa4` と 0x15180 (= 86400 秒) を渡す。
  - 取得した後、`+` を `.`、`/` を `-`、`=` を `*` に置き換える (URL 用の base64)。
- 取得の仕組みは、NNID の independent service token (クライアント ID と有効期間を渡す API) と推定する。**サードパーティのサーバーに向けるとき、トークンの検査はサーバー側でしないことにできる。ただし取得そのもの (任天堂のアカウントのサーバーとの通信) が失敗したときにゲームがどう振る舞うかは未確認。**
- 取得の失敗: 結果のモジュール 0x53 で、説明 0x70 なら状態 +0x207、0x2C8 なら +0x208 を立てる。状態の番号を `FUN_0026F9FC(master, 0〜4)` に渡す (エラー表示と推定)。code.bin に `failed_auth_token`・`unsend_auth_token`・`failed_auth_token_timestamp` の文字列がある。
- 応答の本文が **`ERROR,10`** のとき (`0x4EB4B0` の文字列と比べる)、トークンを取り直して (`FUN_00279500` / `FUN_002B33BC`) 1 回だけ要求をやり直す。GET は `FUN_0027CD9C`、POST は `FUN_0027C9F8` / `FUN_0027C9B8`。`ERROR,10` はトークンの期限切れと推定。

### 応答の形
- HTTP の状態が 200 でないと失敗。
- 本文はテキスト。`,` で区切った欄として読む。最初の欄が `ERROR` なら失敗 (`ERROR,10` / `ERROR,400`〜`406` などの文字列がある)。成功は `SUCCESS`。

### 2.1 チェックインの流れ (`FUN_003E9840`、確定)
入口は `FUN_0015FF88`。`FUN_00306FF0` がチェックインの日かを決める (セーブのキー 0x5F / 0x5B の日付とフラグ 0x60 を見て、本体の時計で 1 日以上たっていれば真)。
- 真: `FUN_003E9840` (以下の通信)。
- 偽: `FUN_003EAEDC`。お知らせの一覧 (件数はフラグ 0x5E) を出し直し、BOSS の作業 0x80000001 (§8) だけを動かす。チェックインの HTTP はしない。

`FUN_003E9840` の順序:
1. サービス終了のスイッチ (§6) が立っていれば `FUN_00167800` (オフライン、§6.3) を呼んで戻る。
2. ダイアログ 0x800000B1、`FUN_0027DDF8(2)` で接続する。別スレッドで BOSS の作業 0x80000001 (§8) を動かす。
3. `req=time` (`FUN_0027D9EC`)
4. `req=bonus_tbl` (`FUN_0043A698`)。失敗するとメッセージ 0x800001A2。
5. `req=check` (`FUN_0043A0A0`)。失敗すると `FUN_0027D9BC` / `FUN_0027D8D0` のあと 1 回だけやり直す。
6. セーブのフラグ 0x5D が 0 なら `req=delete` (`FUN_0043A43C`、POST: `req=delete`、`support_id=%llu`、`region=0`)。
7. 登録済みなら、サーバーの時刻とセーブの日付から連続日数 (作業領域 +0x24) と通算日数 (+0x20) を数えて `req=update` (`FUN_0043A7F4`)。未登録なら `req=create` (`FUN_0043A264`)。
8. 応答のあと、お知らせ 0x800002B6、ログインボーナスの選択 (`FUN_002FF488`) と付与 (`FUN_00473B08` / `FUN_002FF28C`)。セーブのキー 0x1BC〜0x1BF に日付を書き、フラグ 0x451〜0x4DD を消す。
9. BOSS の作業 0x80000002 で `checkin.dat` を読み、配信の行を評価する (§8)。

### 2.2 bdat (確定・一部推定)
`create` / `update` の欄 `bdat` は、作業領域 +0x98 の 0x8B84 バイト (`FUN_003E8DC8` が作る) を `FUN_0027D8B0` で変換した文字列。
- `FUN_00343660(…, 0x1F)` で圧縮して `0x502F10` (最大 0x11830 バイト) に置く。引数 0x1F (= zlib の windowBits 15 + 16) から gzip と推定。
- 続けて `FUN_002C1950` で文字列にする。base64 と推定。
- 0x8B84 バイトの中身 (プレイの記録と推定) は未解析。

## 3. checkinserver

### req=time
応答 `<状態>,<日時>`。2 つ目の欄は 15 文字以上で、`年 4 桁` `月 2` `日 2` `(1 文字)` `時 2` `分 2` `秒 2` を位置で読む (+0、+4、+6、+9、+11、+13)。8 文字目の区切りは読まない (例 `SUCCESS,20160401 120000`)。

### req=check
URL に `support_id` (`%llu`) を付ける。応答の 2 つ目の欄が `true` なら登録済み。

### req=bonus_tbl (ログインボーナスの表)
- 応答 (読む領域は 0x3C00 バイト) が `ERROR` で始まらなければ、先頭の `strlen("SUCCESS,")` = 8 バイトを飛ばし、残りを **base64 としてデコード** する (`FUN_002AF0DC`)。
- デコードした内容はチェックインの作業領域 (+0xAA8) に `memcpy` する。長さの確認は見当たらない。
- `FUN_002EA8DC(ctx+0xA84)` で表の読み手に結び付ける (まだ結び付いていないときだけ)。そこで lanai 形式の GS テーブルとして再配置する (`FUN_0018317C`、[analysis.md §2](analysis.md#2-gs-テーブル-lanai-形式確定))。表の名前を確かめる処理は見当たらない。
- **中身は通算日数ごとのログインボーナス** (確定)。§5 の 0x54 バイトの行ではない (以前の版の推定を訂正)。
  - `FUN_0043AA0C` が行数を返す。`FUN_002FF488` が、+4 の s16 が通算のチェックイン日数 (作業領域 +0x20) と同じ行を探す。
  - `FUN_002FF28C` が付与する。

| off | 型 | 内容 | 確度 |
|---|---|---|---|
| 0x00 | u32 | アイテム ID。0x80000000 ならなし。あれば `FUN_0031ED64(ID, 1)`、メッセージ 0x38 | 確定 (付与の処理) |
| 0x04 | s16 | 通算日数 | 確定 |
| 0x06 | u16 | `FUN_002F83B0` に渡す数。メッセージ 0x44 / 0x42。ゴールドと推定 | 推定 |
| 0x08 | u8 | `FUN_002E9400` に渡す数。メッセージ 0x43 (`%d`)。ジュエルと推定 | 推定 |

行の大きさは 0x0C 以上と推定 (未確認)。
- 表が無いときの既定 (オフラインと同じ処理): 通算 1・3・7 日目は +8 = 1、100 の倍数は 10、5 の倍数は 2、+6 = 300。

### create / update (POST)
欄の並び (`FUN_0026EA98`)。値はすべて文字列。

| 欄 | 中身 |
|---|---|
| `req` | `create` / `update` |
| `support_id` | u64 (`%llu`) |
| `region` | `0` |
| `create_date` / `update_date` / `prev_update` | `%d%02d%02d%02d%02d%02d` (年月日時分秒) |
| `total_num`, `num`, `buy_jewel`, `playtime`, `gold` | `%u` (チェックインの回数・ジュエルの購入・プレイ時間・ゴールドと推定) |
| `total_assets` | `%llu` |
| `continue_num`, `stamina_num_stage`, `stamina_num_ranking`, `rare_gacha`, `event_gacha`, `go_island`, `come_island` | |
| `local_battle_num` / `win` / `lose` / `players` | |
| `coliseum_battle_num` / `class` / `player_point` / `best_a`〜`best_e` | |
| `res_ver` | `%llu` |
| `bdat` | 文字列 (中身は未解析) |
| `auth_token` | §2 |

応答は作業領域 +0x800 に写し、`,` で切った欄の位置を +0x884 に並べる。最初の欄が `ERROR` でなければ成功。`req=delete` も同じ読み方。`update` は `ERROR,11` も成功として扱い、そのときだけ作業領域 +0xAAC に 1 を書く (意味は未確認。メッセージ「お客様の記録がサーバーに見つかりませんでした。本日はチェックイン回数を記録できません。」と関係すると推定)。

## 4. その他のサーバー

- **campaigncodeserver** (POST): `req=res` は `version` (u64)・`response` (u64)・`kind` (`%x`)・`index` (`%u`)。`req=sre` は `version`・`kind`・`index`。ネットワーク経由のコード (CampaignCodeNetwork、`network::CampaignCodeUnique`) の照会・使用済みの記録と推定。応答の解釈は未解析。コードの形式は [codes.md](codes.md)。
- **gameserver?req=res_ver** (`FUN_002A33D8`): 応答 `SUCCESS,a.b.c` を `.` で分けて 3 つの u16 にする。データの版と推定。自分の版 (`FUN_0031C4FC` で組み立てる 64 ビットの値) とくらべ、サーバーの版が新しいとメッセージ 0x8000030C を出す (更新を促す案内と推定)。呼び出しは 4 か所 (`FUN_0025BEEC`、`FUN_00434DA8`、`FUN_00435BCC`、`FUN_00438014`)。

## 5. チェックインの表 (確定した部分)

`A9DF0000` に、同じ行の形 (0x54 バイト、欄 `message` +0x34) の表が 7 個ある。

| 表 | 行数 | 中身 |
|---|---:|---|
| **Checkin_Rom** | 89 | 曜日ごとのイベントステージの公開 (「本日、水曜日の23:59までオープン！」)。**ROM の中にある配信の表** |
| CheckinData | 241 | 期間つきのイベント・報酬 |
| CheckinDeliVersion | 64 | 更新データ配信の記念など |
| CheckinEVCK18 / CheckinEVCK19 | 122 / 122 | イベント (EVCK = イベントチェックインと推定) |
| CheckinJewelBuy | 19 | ジュエル購入の特典 |
| CheckinCheckinCount | 19 | 通算チェックイン日数の記念 (100 日〜2150 日) |

ほかに `307C0000` の Checkin (`checkin_debug_JP`、「LanaiToolにてデータを選択し…」の開発用 1 行)、`25D60000` の CheckinOffsetTime (1 行: `0xA, 0`。日付の切り替えの時差と推定)。

### 5.1 行の形 (配信の報酬の構造)
コード入力の CampaignCodeLocal (0x58 バイト) も同じ構造で、+0x34 に「条件に合わないときのメッセージ」が 1 欄増え、以降が 4 バイトずれる。

| off (0x54 の行) | 型 | 内容 |
|---|---|---|
| 0x00 | u32 | 行の種類。0x80000008 = お知らせの見出し (メッセージを出す)、0x80000000 = 報酬だけ、0x80000001 / 7 / 9 / 0x10〜0x13 もある |
| 0x04 / 0x08 / 0x0C | u32, u32, u8 | 条件 1 = (a, b, 種類) |
| 0x10 / 0x14 / 0x18 | | 条件 2 |
| 0x1C / 0x20 / 0x24 | | 条件 3 |
| 0x28 / 0x2C / 0x30 | | 条件 4 |
| 0x34 | 文字列 | メッセージ |
| 0x38 | u32 | **報酬の種類** (`0x80000000 | 番号`、§5.2) |
| 0x3C | u32 | 値 (アイテム ID・フラグの番号など) |
| 0x40 | u32 | 数 |
| 0x44〜0x4C | | 種類ごとの追加の引数 |
| 0x50 | u16 | まとまりの番号 (0xFFFF = なし)。CampaignCodeLocal では +0x54 |

- 条件は `FUN_002FCD38(種類, a, b, …)` で判定する。種類は 0x00〜0x71 の 114 通りで、ジャンプ表で分かれる。Checkin_Rom の曜日の行は **種類 0x39、b = 曜日** (3 = 水、4 = 木、5 = 金)。そのほかの種類の意味は未解析。
- CampaignCodeLocal (`FUN_0017BEE8`) では、条件 1・2 はどちらかが合わなければ失敗、条件 3・4 は **両方とも合うと失敗** (除外の条件)。条件 3 だけ、最後の引数を 0 にして呼ぶ。

### 5.2 報酬の種類 (`FUN_003023E0` の分岐、0x00〜0x2D)

| 種類 | 処理 | 確度 |
|---|---|---|
| 0x00 | ゴールド (上限の確認 `FUN_00459378`) | 確定 |
| 0x01 | ジュエル (上限の確認 `FUN_004593F8`) | 確定 |
| 0x02 | アイテム (値 = アイテム ID `0x8000xxxx`、数) | 確定 |
| 0x03 | master の読み手 +0x1BC の表の行 (値) を数だけ渡す | 表は未特定 |
| **0x08** | **スイッチ (FlagData のキー 0x51、1 ビット × 25000) の [値] に (数 ≠ 0) を書く** (`FUN_002E8538`) | 確定 |
| 0x09 | キー 0x52 (8 ビット × 12500) の [値] に 数 & 0xFF を書く (`FUN_002FF114`) | 確定 |
| 0x0A | キー 0x53 (1 ビット × 700) の [値] に書く | 確定 |
| 0x17 | 電波人間 (上限の確認がボックスの空き) | 推定 |

- 報酬の種類 0x1B の処理 (`FUN_001AA954`、確定): `FUN_001AA954(master[0x4EAD08], +0x3C の u16, …, +0x40 の u8, +0x44 の u16, +0x48 の時, +0x4C の分)`。期間を (時 × 60 + 分) × 60 × 10^9 ns とし、日の差し引きを足して `FUN_003166C4(master+0x54, ID, 開始, 期間)` に渡す。期間つきの公開と推定。分岐の表は `FUN_003022EC` の中の `0x3023E0`。

### 5.3 行の評価 `FUN_003008BC` (確定)
チェックイン (§2.1、§8) とオフライン (§6.3) で同じ関数を使う。
- 条件 1・2 は両方とも合うこと、条件 3・4 は両方とも合うと除外 (`FUN_002FCD38`)。CampaignCodeLocal と同じ (§5.1)。
- +0x50 のまとまりの番号を、カウンター `FUN_0043D998(master, 0xC)` とくらべる。
- 報酬の種類 0x1F・0x20・0x2C・0x22・0x24・0x26・0x28 は個別に扱う。そのほかは `FUN_00164630` で与える。
- 行の種類が 0x80000000 / 1 / 8 / 9 / 0x10〜0x13 でメッセージを持つ行は、お知らせの一覧 (`0x4FF090`、1 件 0x320 バイト) に足す。
- `CheckinDeliVersion` の表は `FUN_00300FF0` が読む (呼び出しは条件の判定 `FUN_002FCD38` の中など 6 か所)。配信の版ごとの記念と推定。

## 6. サービス終了後のオフラインチェックイン

**公式に案内されたとされるコード `A4J8Y13ML7TAWWE1` を、同梱の `lanaicode.py` でデコードした (確定)。**

結果:
- 種類 0 (通常のコード)
- 要る版 1.17.0
- CampaignCodeLocal の **行 49**

行 49 の中身:
- メッセージ「ジュエル販売所は終了しました。Wi-Fiコロシアムは終了しました。」
- 報酬の種類 **0x08、値 0x2A4、数 1**

つまり、このコードを入れると **スイッチ 0x51[0x2A4] が 1 になる**。

このスイッチを読む関数は `FUN_002E7DEC` (11 か所から呼ばれる)。分かった使われ方:
- チェックインの主処理 `FUN_00435BCC`: スイッチが立っていると、その後の通信の処理に進まずに 0 を返す (`0x435DA8` → `0x437428`)。
- `FUN_0027DDF8` / `FUN_002DBB98`: 通信の失敗時の「接続しなおしますか？」を出さない。
- `FUN_002A3968`: スイッチが立っていると、渡されたメッセージを出して真を返す (機能の案内と推定)。

- **チェックインの通信の本体 `FUN_003E9840`** (`req=time` / `bonus_tbl` / `check` / `create` / `update` をすべてここから呼ぶ): スイッチが立っていると `0x3E99C8` へ飛び、`FUN_00167800` を呼んで通信せずに戻る。`FUN_00167800` がオフラインのときの処理と推定 (中身は未解析)。

オフラインのときに、どの表 (Checkin_Rom など) でイベントを開くかの経路は未確認。ROM の中の Checkin_Rom が曜日ごとのイベントを持つので、これを使うと推定する。

### 6.1 スイッチを書く場所 (確定)
FlagData のキー 0x51 を書く関数 `FUN_002E8538` の呼び出しは 3 か所だけ。

| 場所 | 書く値 |
|---|---|
| `0x207964` | [0x2A4] = 1 (ある値が 6 でないとき。条件は未確認) |
| `0x302BDC` | 報酬の種類 0x08 の行: [値] = (数 ≠ 0) |
| `0x477C94` | [0xC] = 1 |

ほかに、キー 0x51 を `mov r1, #0x51` で直に渡して書く呼び出しは見つからなかった (`FUN_002E7DEC` 内の読み出しなどだけ)。サポート用コードの操作 1〜12 ([codes.md §5](codes.md#5-種類-2-サポートのコード-codesystemaction)) もキー 0x51 を書かない。

### 6.2 未改造のゲームでスイッチを 0 に戻せるか (結論: 戻せない)
- 0 に戻せるのは、**報酬の種類 0x08・値 0x2A4・数 0 の行**だけ (§6.1)。
- ROM の中の 0x54 / 0x58 バイトの表 (Checkin 系 7 個、CampaignCodeLocal、CampaignCodeNetwork) を全部調べた。値 0x2A4 を書く行は、CampaignCodeLocal の行 49 (数 1、1 にする行) しかない。
- コード入力 (種類 0) で選べるのは CampaignCodeLocal の既存の行 (0〜49) だけ。中身は行番号と版だけなので、**ROM にない行を指すコードは作れない**。行番号が行数以上だと「コードが間違っています」になる。
- サーバーが配る表 (`bonus_tbl`) に数 0 の行を入れれば戻せる形だが、スイッチが立っているとチェックインの通信そのものをしない (§6) ので届かない。
- したがって、**一度 `A4J8Y13ML7TAWWE1` を入れたセーブを、未改造のゲームとコード入力だけで元に戻す方法は見つからない**。戻すには次のどれかが要る (いずれも未検証)。
  1. 一時的な MOD: CampaignCodeLocal (`7BF7000A`) に「種類 0x08・値 0x2A4・数 0」の行を 1 行足した Update を作る。その行番号を指すコード (`lanaicode.py enc 0 50 0 1.17.0` など) を入れたあと、MOD を外す。スイッチはセーブに残るので、外した後も 0 のまま。
  2. code.bin の `FUN_002E7DEC` を、常に 0 を返すように書き換える (セーブは変えない)。
  3. セーブデータを直接書き換える (セーブの形式と改ざんの検査は未解析。「セーブデータの異常を検知」の処理がある)。
- まだコードを入れていないセーブは、スイッチが 0 のままなので戻す必要はない。
- どのみち、サードパーティのサーバーに接続するには接続先の書き換え (§7) が要る。完全に未改造のままでの準オンライン化は、DNS の向け先を変えたうえで HTTPS の検証を通せる場合に限られる (未確認)。

### 6.3 オフラインのときの処理 `FUN_00167800` (確定)
- 通信のときと同じ作業領域を作り、+0 を 0 にする (ログインボーナスの表なし → §3 の既定のボーナス)。
- 日付は固定の **2021-07-14** (0x7E5, 7, 0xE) を使い、セーブのキー 0x1BC〜0x1BF に書く。フラグ 0x451〜0x4DD を消す。
- master (`[0x4EAE44]`) の +0x168 と +0x118 の表の行を `FUN_003008BC` (§5.3) で評価し、フラグ 0x5E / 0x5D を立てる。ROM の中の Checkin 系の表 (Checkin_Rom など) をこの経路で評価すると推定 (どちらの表がどれかは未確認)。

## 7. サードパーティのサーバーに向けるときの要点 (提案・未検証)

1. **接続先**: code.bin の URL を書き換える。URL の文字列は ro (`0x4A2078` 付近) と text のリテラル (`0x26EE50`、`0x437C74`、`0x439184`、`0x2A377C` など) の両方にあり、元の長さ以下にする。または DNS を向ける。HTTPS の証明書の検証を通すには、証明書の差し替え (§1)、HTTP への書き換え、本体の検証を外す、のどれかが要る。
2. **auth_token** を取れない場合の扱いを確認する (§2)。
3. **応答の形**: `SUCCESS,…` のテキスト。最低限 `req=time` (時刻) と `req=bonus_tbl` (base64 の表) を返せば、任意のイベント (§5 の行) を配れる見込み。
4. **サービス終了モード** (スイッチ 0x51[0x2A4]) が立っていると通信しないので、準オンラインにするにはこのスイッチを 0 に戻す。未改造のゲームでは戻せない (§6.2)。行を足した一時的な MOD とコードで戻すか、読み出しの `FUN_002E7DEC` を書き換える。

MOD とサーバー (Cloudflare Worker) の具体的な案、ROM にないステージを配る構想の実現性は [サードパーティのサーバー](private-server.md) にまとめた。

## 8. SpotPass (BOSS) で配る表 (確定・一部推定)

### 8.1 Boss の表
master `2135000A` の `boss.bin` (表の名前 `Boss`、4 行 × 0x10、読み手は master +0xCC)。

| 行 ID | +0 URL | +4 作業の名前 | +8 NsData の番号 | +0xC / +0xD |
|---|---|---|---|---|
| 0x80000000 | `https://npdl.cdn.nintendowifi.net/p01/nsa/bX6vTcQgC6ojhnM8/labos01/info.dat` | `labos01` | 0 | 0x18 / 0x64 |
| 0x80000003 | `…/labos02/info.dat` | `labos02` | 0 | 0x18 / 0x64 |
| 0x80000001 | `…/FGONLYT/resource.dat` | `FGONLYT` | 3 | 0 / 0 |
| 0x80000002 | `…/FGONLYT/checkin.dat` | `FGONLYT` | 2 | 0 / 0 |

- +0xC / +0xD は間隔 (時間) と回数と推定。`FGONLYT` は前面のときだけ動かす作業 (foreground only) と推定。作業は `FUN_0043BEB8` (URL と名前を写す) と `FUN_0043C5A0` (作業を作る) で登録する。
- 作業 0x80000001 (`resource.dat`) はチェックインの日でもそうでない日でも動かす (§2.1)。中身と読み手は未解析 (`FUN_002D99C4` が `FUN_0040CBAC` を包む。呼び出しは `FUN_0019D700`・`FUN_002FE1D0`・`FUN_002FE584`)。

### 8.2 checkin.dat の読み込み (`FUN_0040C93C` → `FUN_0040CBAC`)
1. nn::boss で NsData の一覧を取り、番号が Boss の行 +8 (= 2) のものを選ぶ。
2. 最大 1 MB を読む (`FUN_00388B90`)。
3. ヘッダーの情報の種類 0〜5 を `FUN_0027803C` で読む。情報の +0x18 がデータの版。
4. 版がセーブのフラグ 0xB (`FUN_0040DF40`) と違えば、フラグ 0x5E を 0 にする (お知らせの一覧の作り直し)。
5. 読んだ内容を GS テーブルとして結び付け (`FUN_0027D87C` + `FUN_002EA8DC`)、その行と master +0x118 / +0x11C の表の行を `FUN_003008BC` (§5.3) で評価する。
6. フラグ 0x5E / 0x5D を立て、版を `FUN_00312D64` で保存する。

つまり **checkin.dat の中身は §5 の 0x54 バイトの行の GS テーブル** (イベントの公開・報酬・お知らせ)。NsData は任天堂が署名・暗号化したもの (SpotPass の仕組みからの推定) で、第三者は作れない見込み。
