# RPG FREE! (lanai) の店 (Shop・ShopItem・「店の人」)

対象: lanai Base v0 + Update v17408。表の形式は [analysis.md §2](analysis.md#2-gs-テーブル-lanai-形式確定)、EventObject は [map.md §7](map.md#7-mapgroup-と-eventobject-確定)。RPG3 の同名の表は [oahu/shops.md](../oahu/shops.md) だが、行の大きさも欄も違う (流用しない)。

数え方: 全 127 コンテンツのアーカイブの `Shop` / `ShopItem` と、全 MapGroup の EventObject の表を ROM から読んだ (Panana の一時テスト、2026-10-18)。ShopItem の欄の使われ方は Update v17408 の code.bin を ghidra で読んだ (2026-10-18)。

## 1. 置き場所 (確定)

| 表 | エントリのハッシュ | 行の大きさ | 場所 |
|---|---|---|---|
| Shop | `0xD5CEF800` | 0x1C | 各コンテンツのアーカイブ (127 個すべて) |
| ShopItem | `0x67297400` | 0x2C | 同上 |

- ハッシュは RPG2 / RPG3 と同じ (同じ名前のファイル)。どちらの表にも欄の名前の表はない。
- 店が 1 つ (Shop 1 行) のコンテンツが 124 個。複数あるのは **コンテンツ 0 (島・町、8 行)**、**24 (25 行、釣り具の店)**、**97 (36 行)** だけ。
- master (`2135000A`) には別に `ShopIsland` (8 行 × 0x2C、+0x10 が説明文 `flavor_msg`) と `JewelShopInfo` (6 行 × 4) がある (§5)。
- 店員の決まり文句は言語のアーカイブ `FE74000A` の `MessageTalkShop` (125 行 × 0x0C、`message` / `voice`) (§3.1)。

## 2. ShopItem (0x2C / 行)

RPG3 と同じく「頭の行」と、それに続く「品物の行」が交互に並ぶ。

- **頭の行** = +0x00 が 0 で +0x24 が 1 の行 (193 行、Shop の行数と同じ)。ほかの欄は全行で同じ (+0x20 = `800001BF`、詰め物 0xD0)。
- 店の品物 = 頭の行の次から、+0x24 が 0 でない行 (次の頭) の手前まで。品物の数を持つ欄はない (確定: `FUN_002233EC` が品揃えのリストを作る。Shop の行の +0x00 の行 ID を行 ID の列 (`FUN_0031C0E0`) で探し、次の行から各行の 0x2C バイトをそのまま作業用の配列に写す。表の置き場はマスター `*0x004EAE44` の +0x1860 / +0x1864 (ShopItem)、+0x1838 (Shop))。
- 品物の行にアイテム 0 の行が混ざることがある (11 行: コンテンツ 0 の頭 `800001F0` の行、コンテンツ 13 の頭の直後、コンテンツ 24 の 9 店の 7 番目)。+0x25 が 0 なのでランダム枠 (§2.1) ではない。店でどう出るかは未確認。

| 位置 | 型 | 頭の行 | 品物の行 | 確度 |
|---|---|---|---|---|
| +0x00 | u32 | 0 | **アイテム ID** (ItemData の行 ID)。0x80000000 未満の値はランダム枠の種別 (§2.1) | 確定 |
| +0x04 | u32 | 0 | 大半は 0。0 でない値は 1〜5、0x64、1000、5000、0x2710、0xFFFFFFFF など | 確定: 値段を求める `FUN_001BEA84` / `FUN_001BF1CC` に品のアイテムと一緒に渡す (店の種類で関数が変わる)。推定: 値段の上書き (0 のときの意味は未確認) |
| +0x08 | u32 | 0 | 大半は 0。コンテンツ 0 は 2〜0x12、コンテンツ 24 は 0x27C … | 確定: **陳列の条件の番号** (下) |
| +0x0C | u32 | 0 | 0 か 1〜0x0D | 確定: **陳列の条件の比べる値** (種類 5 など。種類 1 では使わない) |
| +0x10 | u8 | 0 | 0 / 1 / 5 / 6 / 0x15 / 0x27 | 確定: **陳列の条件の種類** (下) |
| +0x14 | u8 | 0 | 8 行だけ 0xA1 (+0x1C が 0x16、+0x20 が `800002B7`) | 未解析 |
| +0x20 | u32 | `800001BF` | ほぼ `800001BF` | 未解析 (ItemData の行 ID としては「タンポポ」になるので、アイテムではないと推定) |
| +0x24 | u8 | **1** | **0** | 確定 (頭の行の印。コードは 0 でない行を次の頭とする) |
| +0x25 | u8 | 0 | 0 か 1〜0x23 | 確定: **ランダム枠の番号** (§2.1)。0 なら固定の品 |
| +0x26 | u8 | 0 | 0 か 1・2・3・4・5・8・0x10 | 確定: **買える数の上限** (+0x27 が 0 のとき。0 = 制限なし)。買った数は保存値 0x99 の [店の番号][リストの位置] (位置 < 50) に記録 |
| +0x27 | u8 | 0 | 0 か 1・8・0x0A・0x14・0x1E … | 確定: **買える数の上限** (0 でなければ +0x26 より優先)。買った数は保存値 0x9A の [+0x28] に記録 |
| +0x28 | u8 | 0 | 0 か 0x65〜0x87 (各 6 行) | 確定: +0x27 の買った数を数える番号 (+0x28 < 200 のときだけ記録。同じ番号の行で店をまたいで共有) |
| 詰め物 | | 0xD0 | 0xD0 | |

- 買える数 (`FUN_002AEED4` / `FUN_0045F008`): +0x27 ≠ 0 なら +0x27、+0x27 = 0 で +0x26 ≠ 0 なら +0x26、両方 0 なら上限なし (99)。MessageTalkShop の「購入個数が限定されているアイテムです。あと〈num〉個購入可能です」「購入上限数に達しているため…」に当たると推定。
- 陳列の条件 (`FUN_002A62D0` が汎用の条件判定 `FUN_002FCD38(+0x10, +0x08, +0x0C, 1, 0, 0)` を呼ぶ): +0x10 = 0 は常に並ぶ、1 = フラグ +0x08 が立っている (`FUN_002F4B58`)、2 = 立っていない、3 / 4 = `FUN_002E7DF4` (スイッチと推定) の真 / 偽、5 = `FUN_002FF158(+0x08)` が +0x0C と等しい。データにある 0x15・0x27 の分岐は未解析。
- 行 ID: コンテンツによって、行番号どおり (0x80000000 | 行) のもの、頭の行だけ ID を持ち品物の行は 0 のもの (コンテンツ 12〜21 など)、ばらばらの ID のもの (0・24・97) がある。

### 2.1 ランダム枠 (確定)

+0x00 が 0 でも行 ID でもなく (0x80000000 未満)、+0x25 が 0 でない行は**日替わりのランダム枠**。+0x00 の下位バイトが ItemDataCore +0x32 のアイテムの種別 ([items.md §6](items.md))、+0x25 が枠の番号。

- 品揃えを作るとき (`FUN_002233EC`)、保存値 0x97 の配列の [+0x25] (`FUN_0031C464`) が 0 か範囲外なら抽選する。候補は ItemData の全行のうち、ItemDataCore +0x30 の bit 0 が 1 (`FUN_001BDD1C`)、種別 (`FUN_0031EECC`) が同じ (0x55 と 0x56 は同じ扱い)、その店のリストにまだないもの (最大 300 個)。乱数 (`FUN_002ED8A4`) で 1 つ選んで 0x97[+0x25] に保存し (`FUN_0031C44C`)、その行の +0x00 を選んだアイテムの行 ID (`FUN_002D3F8C`) にする。
- 種別の求め方: ItemData +0x0C (u16) の ItemDataCore の行の +0x32。それが 1 (まとめ売り) なら、ItemDataCore +0x2C (u16) のアイテムに移って繰り返す。ItemData +0x0C が 0 の行は対象外 (`FUN_00313130`)。
- 抽選のやり直し: 保存値 0x96 の日付 (年・月・日) が今日と違うか、フラグ `0x80000066` (表 +0x57C、FlagData と推定) が立っていなければ、0x97 を全部 0 にして選び直し、0x96 に今日の日付を書いてフラグを立てる。つまり**毎日 1 回抽選し直す**。
- 抽選があったときはリストを並べ替える (`FUN_003FD198`): 種別が同じ品どうしは `FUN_002C7448`、次に `FUN_002A7EC4` の値の順。種別が違えば元の位置 (作業用に +0x29 / +0x2A に書いた通し番号) の順。このため、抽選された品は同じ種別の品の近くに並ぶ。
- ROM では**コンテンツ 0 の Shop 行 2 (頭 `800001D5`、家具・庭・たねの店) の 35 行だけ**。+0x04〜+0x10 は 0、+0x25 は 1〜0x23 の通し番号。種別ごとに 2 枠 (たねは 7 枠):

| 種別 | +0x25 | 中身 (候補の数、ItemDataCore からの計算。実機の抽選結果ではない) |
|---|---|---|
| 0x51 | 1・2 | 庭: いえ (41) |
| 0x53 | 3・4 | 庭: おきもの (31) |
| 0x54 | 5・6 | 庭: ランプ (7) |
| 0x55 | 7・8 | 庭: テーブル・いす (11、0x56 を含む) |
| 0x57 | 9・10 | 庭: もん (7) |
| 0x58 | 11・12 | 庭: かべ (9) |
| 0x59 | 13・14 | 庭: タイル (20) |
| 0x61 | 15・16 | 家具: しょくぶつ・おきもの (77) |
| 0x62 | 17・18 | 家具: テーブル (16) |
| 0x63 | 19・20 | 家具: いす (20) |
| 0x64 | 21・22 | 家具: ランプ (12) |
| 0x65 | 23・24 | 家具: ベッド (11) |
| 0x67 | 25・26 | 家の床 (60) |
| 0x68 | 27・28 | 家の壁 (63) |
| 0x34 | 29〜35 | 花のたね (67) |

- 注意: 小さい値を ItemData の行番号として読むと「ペイントしろ」(行 0x53) のように品揃えらしい名前になるが、偶然。行 0x53 は種別 0x17 で、0x53 の候補ではない。

## 3. Shop (0x1C / 行)

| 位置 | 型 | 内容 | 確度 |
|---|---|---|---|
| +0x00 | u32 | **品揃えの頭の行** (ShopItem の行 ID)。1 店のコンテンツは全部 `80000000` (頭の行 0) | 確定 (コンテンツ 24 の 25 店・97 の 36 店で、値がそれぞれ別の頭の行の ID に一致) |
| +0x04 | u32 | 店の部屋のモデル (例 `0x0B589C00`。RPG3 の `inside_01.bch` と同じハッシュ) | 推定 (RPG3 の Shop +0x00 と同じ値) |
| +0x08 | u32 | そのカメラ (`0x535AF800` など) | 推定 (同 +0x04) |
| +0x0C | u32 | 0〜0x16 の小さい値。93 行が 0、8 が 25 行 (コンテンツ 24 の全店) | 未解析 |
| +0x10 / +0x14 | u32 × 2 | `80000010` / `80000011` (184 行)、`80000016` / `80000017`、`80000014` / `80000015`、`80000018` / `80000019`。+0x14 は常に +0x10 + 1 | 未解析 (MessageTalkShop の行 ID としては「…個 たしかに。」などになり、組として意味が合わない) |
| +0x18 | u8 | 1 (170 行)、6 (コンテンツ 97 の 18 行)、2〜7 (コンテンツ 0) | 未解析 (RPG3 の +0x34 口調 / +0x37 支払いに当たると推定) |
| +0x19 | u8 | 0x17 = 23 (192 行)、0x32 = 50 (コンテンツ 6) | 推定: 店員の高さ (RPG3 の Shop +0x36 が 23 か 50) |
| +0x1A / +0x1B | | 0xD0 0xD0 | |

- Shop の行 ID はコンテンツごとにばらばら (1 店でも `80000000`〜`80000003`)。行 ID が何に使われるかは未確認。

### 3.1 MessageTalkShop (`FE74000A`、125 行)

行 0 は「ダミー」。行 1〜は 9 行ずつの組 (いらっしゃい・どうする・買う数・売る数・もう買えない・買ったあと・売ったあと・売る物がない・ここで装備するか) が口調ごとに続く (例 行 1〜10 は地底人の片言、行 47〜55 は心の声つき)。行 83〜121 は 5 行の短い組。行 122〜124 は「1 個だけ」「買える数の上限」の文。どの店がどの組を使うかは未確認 (Shop に組の欄が見当たらない)。

## 4. 「店の人」(動作の型 0x80000032) と店の対応

EventObject の動作の型 `0x80000032` (Panana では「店の人」) は、引数 1 の台詞 (MapGroup の talk table の行。[map.md §7](map.md#7-mapgroup-と-eventobject-確定)) を言ったあと店を開く。全 200 表で **60 行** (49 コンテンツ)。

- **どの店を開くか: そのコンテンツの Shop の行 0 (推定)**。
  - 型 0x32 の行がある 49 コンテンツは、どれも Shop が 1 行だけ。店が複数あるコンテンツ 0・24・97 には型 0x32 の行がない (島の店・釣り具の店などは CRO のスクリプトやメニューから開くと推定)。
  - 引数に店の番号はない: 引数 2・3・5 は全行 0、引数 4 は 0 か 1 (意味は未解析)。
  - 開く処理 (型 0x32 のクラス) のコードはまだ見つけていない (型の値はコードの中で即値で比べられ、表の名前・ハッシュの即値も見当たらない)。
- 区画 5 (キャラクター) の EventObject の行 (+0x04) がその行を指す。1 つのコンテンツの 2 つのマップに同じ店員がいることがある (例 コンテンツ 23・25〜27・29〜32・120〜122 の `D01001xxx` と `D01002xxx`)。2 つの店員は同じ店 (同じ Shop の行) を開く。

## 5. master の ShopIsland と JewelShopInfo

- `ShopIsland` (8 行 × 0x2C): 島の店の一覧と推定。+0x10 `flavor_msg` が説明文 (期間限定の店・福袋の店・基本のアイテムの店・服や装備の店・インテリアの店・ジュエルの店・買い取りの店)。コンテンツ 0 の Shop も 8 行で、数が一致する。欄の対応は未解析。
- `JewelShopInfo` (6 行 × 4、`amount`): 0x40、0x4A、0x54、0x5E、0x6C、0x7A。ジュエルの買い物の数と推定。

## 6. 分からないこと

- 型 0x32 が開く店の決め方のコード (§4 の「行 0」は ROM のデータの対応からの推定)。
- ShopItem の +0x04 の値の扱い (0 のとき)、+0x14・+0x20、陳列の条件の種類 0x15・0x27。Shop の +0x0C・+0x10 / +0x14・+0x18 の意味。
- 品物の行のアイテム 0 の扱い (飛ばすのか、空の行として出るのか)。
- 店員の決まり文句 (MessageTalkShop) の組の選び方。
