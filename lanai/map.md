# 電波人間のRPG FREE! (lanai) のマップのデータ構造

対象: lanai Base v0 + Update v17408。ステージ (MapStage / コンテンツ) のマップを Panana で開くための調査。初版はデータ (RomFS) だけで調べた (code.bin で確かめた欄は `FUN_` / `@0x` のアドレスを添える。アドレスは Update の code.bin)。**RPG3 (oahu) の形式 ([oahu/map.md](../oahu/map.md) と [oahu/map-models.md](../oahu/map-models.md)、RPG2 は [kahara/map.md](../kahara/map.md)) と同じと仮定して実データで検証し、違うところを洗い出した**。

確度の表記:
- **確定** = 全マップ (565 件、うち地図が通常の 553 件) の実データで矛盾なく成り立つ、またはゲーム内の意味と照合できたもの。
- **推定** = 統計や他作との類似から見えるが、コードやゲーム内で確認していないもの。
- **未解析** = 手を付けていないもの。

検証に使った道具は一時スクリプト (scratchpad、コミットしていない)。検証数は各所に書いた。コンテンツ番号 N は [contents.md](contents.md) の `Contents` の行番号。

## 0. 全体像

```
コンテンツ N のアーカイブ (Contents の行 N のルートファイル、例 59B00000)
  ├─ type 3  C9F79000  マップ DB       (LZ10、名前なし。127 コンテンツすべて同じハッシュ)  ← MapDataResource 行 0
  ├─ type 3  131C5000  マップ表        (LZ10、名前なし、n × 0x4C。同上)                    ← MapDataResource 行 1
  ├─ type 12 MapGroup / MapData / MapResource / MapPartsType / MapEnv / MapCamera / MonsterGroup / TreasureGroup …
  ├─ type 11 MapPartsCaveB, MapPartsRuinsB …  (タイルセットごと、67 × 0x40)
  ├─ type 1  D01_EventObject.bin / D01_StaticEvent.bin  (MapGroup ごと、100 B × n)
  └─ type 1  contentsNNNN.cro                          (イベントのスクリプト)

マップ名 "D01001B01" ── マップ表の行 (0x4C)
   ├─ +0x00〜+0x24  区画のハッシュ × 10 (スロット 0〜9) ──> マップ DB の区画のデータ
   ├─ +0x28  MapData の行 ID (0 / 0x80000000 = MapGroup の既定)
   ├─ +0x2C  MapGroup の行                       ── +0x00 名前 (MessageMapName の行 ID)
   │                                               +0x08 / +0x0C MapData の行 ID (屋外 / 屋内)
   │                                               +0x14 / +0x18 最初のマップ・地点
   │                                               +0x1C EventObject の表のエントリ
   └─ +0x34  階

MapData の行 ──> A: MapPartsType の行 (タイルセット) ──> MapParts<名前> の表 [タイル種類 + 1][文字] = {アーカイブ, エントリ (GSC)}
             ├─ B: MapResource の行 (テクスチャ・空・土台)
             ├─ C: MapCamera の行   D: MapEnv の行
```

oahu の「マップ DB・マップ表・区画・タイル・EventObject」の作りがそのまま移った。違いは、**これらが全体で 1 つではなく、コンテンツ (ステージ) ごとに 1 組ずつある**ことと、タイルのモデルが MapParts の表 (タイルセットごと) に分かれたこと、タイルや向きの記録が**ビットマスク**になったこと、座標の単位が一部 RPG2 に戻ったこと。

## 1. マップ DB とマップ表の場所 (確定)

- 127 コンテンツすべてのアーカイブに、type 3 のエントリ `C9F79000` (マップ DB) と `131C5000` (マップ表) がある。コンテンツの `MapDataResource` (2 行 × 4 B) の行 0 / 行 1 がこの 2 つのハッシュ (127 件すべて同じ値)。
- マップ DB の形式は oahu / RPG2 と同じ (確定): `u32 件数, 件数 × {u32 ハッシュ, u32 オフセット, u32 サイズ}` (ハッシュの昇順) + データ (オフセットはデータの先頭から)。Panana の `src/game/mapdb.ts` の `MapDb` でそのまま読める (全 127 コンテンツで確認)。
- 同じ名前のマップは、コンテンツが違ってもマップのハッシュが同じ (例 `D01001B01` は A2B01CE4)。DB と区画のハッシュ値はコンテンツごとに独立で、別コンテンツの DB を混ぜない。
- 全体: マップ表の行 565 (うち地図が通常のものは 553、`W01` = ワールドマップが 12)。区画のハッシュが DB にないマップが多い (空の区画 = 0 件)。

## 2. マップ表 (確定)

1 行 0x4C バイト (oahu は 0x44)。コンテンツの中の行数は 1〜99 くらい。

| 位置 | 型 | 内容 | 確度 |
|---|---|---|---|
| +0x00〜+0x24 | u32 × 10 | 区画のハッシュ (スロット 0〜9、§3)。スロット 0 = マップのハッシュ = タイルの区画 | 確定 |
| +0x28 | u32 | MapData の**行 ID** (0 または 0x80000000 = MapGroup の既定。§6) | 確定 |
| +0x2C | u32 | MapGroup の行番号 (コンテンツ内の `MapGroup`) | 確定 |
| +0x30 | s32 | 敵の出方 3 / 4 / 5 (一部 0)。oahu §11.1 と同じ値域 | 推定 (値域のみ) |
| +0x34 | s32 | 階 (地下は負)。階段の行き先の階と一致 (§8) | 確定 |
| +0x38 | u32 | 0。W01 だけ 0x80000002〜0x80000008 などの行 ID | 未解析 |
| +0x3C | u32 | 全マップで 1 | 未解析 |
| +0x40 | char[12] | マップ名 | 確定 |

- 名前の付け方は oahu と**並びが違う**: `{種類 1 文字}{2 桁}{番号 3 桁 or OUT or H01 …}{B|F}{階 2 桁}` (例 `D01001B01` = D01 の 001 番目の地下 1 階、`M02001F01`、`F01OUTF01`、`S01H01F01`、`H01001F01`、`W01`)。oahu は `D01B02001` (種類 + B/F + 階 + 番号)。
- 種類と数 (565 行): D (ダンジョン)、M (島のフィールド)、F (村)、S (小さな建物・店)、H、W (ワールドマップ)。

## 3. 区画 (確定)

区画の番号と記録の形は oahu とほぼ同じ。**スロットの並びだけが違い、区画 k = スロット k になった** (oahu は `[0,1,6,2,8,5,4,3,9,7]`)。ただし区画 7 (oahu でもなし) は飛ばし、oahu の区画 8 と 9 はスロット 7 と 8 に詰まった。

| 区画 (oahu と同じ番号) | lanai のスロット | 1 件 | 内容 | oahu との違い |
|---|---|---|---|---|
| 0 | 0 | 20 B | タイル (§4) | 形は同じ。向きの欄が違う |
| 1 | 1 | 16 B | 床のギミック | 同じ。`(x, y)` = セル +0 / +2。種類 +0x0D = 0〜3 |
| 2 | **2** | 20 B | 置物 | 同じ (mapObject の行 + 細かい座標) |
| 3 | **3** | 24 B | 出入口・階段・扉 | 同じ。向きの欄が違う |
| 4 | **4** | 24 B | 宝箱 | **座標が 100 単位**(oahu は 125 単位) |
| 5 | 5 | 32 B | キャラクター・オブジェクト | **座標が 100 単位**。向きの欄が違う |
| 6 | **6** | 8 B + 8 B × n | 出現する敵 | セルの値が行 ID (§10) |
| 7 | (なし) | | | oahu と同じくない |
| 8 | **7** | 32 B | イベントの範囲 | スロットが違うだけ |
| 9 | **8** | 24 B | 地点 | スロットが違うだけ |
| (W01 のみ) | 9 | | ワールドマップ | oahu と同じく別の形 |

全マップ (W01 を除く 553) でサイズを調べた結果: スロット 0 は 20 の倍数、1 は 16、2 は 20、3 は 24、4 は 24、5 は 32、6 は 8 の倍数、7 は 32、8 は 24 の倍数。スロット 9 は W01 以外にはデータがない (すべて DB にない)。

### 3.1 区画 0: タイル (20 B、確定)

oahu §3.1 と同じ: `+0 u32 種類 (0〜65、実データ 0〜65)`、`+4 s16 x`、`+6 s16 y` (セル)、`+8〜+0xF` は 0 (全マップで 0)、`+0x10 u8 向き`、`+0x11 u8 文字`、`+0x12 u16` は 0。

- 文字: `'z'` (0x7A) = 既定 (25134 件)、`'a'`〜`'g'` = 1〜7。oahu と同じ。
- **向き (+0x10) は 1 / 2 / 4 / 8 の 1 ビット (oahu は 0〜3)**。全 31777 件がこの 4 値だけで、0 や 3 はない。
- 範囲: x は 1〜25、y は 0〜25 (oahu の 30 × 30 のグリッドに収まる)。

### 3.2 向きのビットマスク (確定)

oahu の向き `r` (0〜3、Y 軸回りに −r × 90°) と lanai の値の対応は、**3×3 の部屋の縁 (種類 7 / 9) が中央 (種類 5) の方を向く向き**で 5000 件以上を照合して決めた。矛盾はない。

| 部屋の中央が縁から見て | oahu の r | lanai の値 |
|---|---|---|
| 南 (S) | 0 | **4** |
| 西 (W) | 1 | **2** |
| 北 (N) | 2 | **1** |
| 東 (E) | 3 | **8** |

`lanai 値 = 4 ビットを r 回、右回転した値` (4 → 2 → 1 → 8)。ビットの意味は N = 1、W = 2、S = 4、E = 8。

- 同じ表現が、区画 3 の +0x14 (向き)、区画 4 の +0x14 (全 1533 件のうち 1532 件が 4 = oahu の 0)、区画 5 の +0x1C、区画 2 の +0x10 にもある (1 / 2 / 4 / 8 だけ)。度数の並びが oahu の 0 / 1 / 2 / 3 と**同じ対応**になる (例: 区画 2 は oahu で 0 が最多、lanai で 4 が最多) ので、同じ変換と推定する (区画 2〜5 の向きは**推定**、タイルは**確定**)。
- Panana の `src/game/sections.ts` の `parseTiles` は `r & 3` と `r & ~3` に分けるので、lanai の 4 と 8 は rot 0 + rotHi 4/8 になる (書き戻しは壊れないが、向きの読みが違う)。§12 参照。

## 4. 座標の単位 (確定)

各区画の位置の欄が、**そのマップのタイルの上にあるか**で調べた (W01 を除く 553 マップ)。

| 区画 | 欄 | 単位 | タイルの上にある割合 |
|---|---|---|---|
| 1 床のギミック | +0 / +2 s16 | セル | 439 / 439 |
| 2 置物 | +4 / +6 s16 (+ f32 +8 / +0xC) | 細かい単位: ワールド = 50 + v × 100 | 12147 / 12200 (99.6%)。oahu と同じ |
| 3 出入口 | +8 / +0xA s16 (+ f32 +0xC / +0x10) | セル | 2249 / 2258 (99.6%) |
| 4 宝箱 | +8 / +0xA s16 (+ f32) | **細かい単位 (100)** | 1534 / 1534 (100%)。125 単位だと 38% |
| 5 キャラ・オブジェクト | +8 / +0xA s16 (+ f32) | **細かい単位 (100)** | 1457 / 1523 (96%)。125 単位だと 39% |
| 6 敵のセル | +4 / +6 s16 | セル | 6295 / 6301 |
| 7 (oahu の区画 8) 範囲 | +8 / +0xA s16 (+ f32) | 細かい単位 | 733 / 795 (92%)。外側の範囲の分 |
| 8 (oahu の区画 9) 地点 | +0xC / +0xE s16 | 細かい単位 (推定) | タイルの外枠の中に 100%、タイルの上は 1300 件中 1094 |

- f32 のずれ (+0xC / +0x10 など) の掛け方 (× 100) は oahu のものを流用した。ずれの有無ではタイル上の割合が変わらないので、**ずれの掛け方は未確認** (推定)。
- 1 セル = 500 は oahu と同じと推定 (数字を確かめる材料は上の割合だけ)。

## 5. 区画ごとの記録

### 5.1 区画 3: 出入口・階段・扉 (24 B、確定)

oahu §3.4 と同じ: `+0 u32 地点の ID`、`+4 u32 EventObject の行`、`+8 s16 x`、`+0xA s16 y` (セル)、`+0xC / +0x10 f32 ずれ`、`+0x14 u8 向き (§3.2)`、`+0x15 u8 種類`。

- **EventObject の行は全 2258 件が、マップの MapGroup の表の範囲に入る**。
- **行き先は EventObject の +0x10 (u32) が 0x80000013 のとき、+0x14 = 行き先のマップのハッシュ、+0x18 = 行き先の地点 ID** (確定。oahu の「出入口の種類は EO +0x10/+0x14 が行き先」と同じ作り。lanai では +0x10 が動作の型の行 ID)。
- **種類 (+0x15) 5 = 上り階段、6 = 下り階段** (確定): 行き先 (EO の +0x14) の階がこちらより上 / 下かを 129 件ずつで確認し、全件が一致。**oahu の 4 / 5 から 1 つずれている**。
- 種類の度数 (W01 を除く 553 マップ、計 2258 件): 11 = 656、6 = 555、12 = 191、5 = 142、0 = 101、2 = 91、8 = 77、4 = 75、10 = 67、7 = 54、3 = 46、…、100 = 25。oahu で 0x64 (100) が壁の扉なのは同じ (25 件)。11 の EO は動作の型が 0x80000000 (動作なし)、12 の EO は 0x80000017 が大半、6 の EO は 0x8000002D (スクリプト) が大半 (426) と 0x80000013 (129)。**5 / 6 / 100 以外の種類の意味は未確認** (推定: 種類の並びは RPG2/RPG3 の変換表 `FUN_0021f9f4` の流れで、一部ずれている)。
- 各 EO の動作の型 (+0x10) の度数: 0x80000013 (ワープ、階段) 258、0x80000017 (扉・門) 約 240、0x80000011 / 12 / 14 / 15 / 16 / 19 / 2D / 31 / 34 / 3B など。各型の意味は未解析。

### 5.2 区画 4: 宝箱 (24 B、確定)

`+0 u32 宝箱の見た目 (0〜3、oahu は 0〜2)`、`+4 u32 EventObject の行`、`+8 / +0xA s16 x, y (100 単位)`、`+0xC / +0x10 f32 ずれ`、`+0x14 u8 向き (4 のみ = oahu の 0)`。中身は EventObject の行が指す TreasureGroup の行 (コンテンツの `TreasureGroup` 表、行 ID 形式。**EO 側の欄は未解析**)。

### 5.3 区画 5: キャラクター・オブジェクト (32 B、確定)

`+0 u32 種類 (0 / 1 / 2 / 4 / 6 / 9 / 10 / 11 / 13 / 14 / 15)`、`+4 u32 EventObject の行`、`+8 / +0xA s16 x, y (100 単位)`、`+0xC / +0x10 f32 ずれ`、`+0x1C u8 向き (§3.2)`。種類 0 が 777 件で最多。種類ごとの作る関数・ハンドラは oahu §3.6 の表を参考にできるが、**番号の対応は未確認**。

### 5.4 区画 2: 置物 (20 B、確定)

`+0 u32 mapObject の行 (118〜778、master の MapObject 784 行の範囲内)`、`+4 / +6 s16 x, y (細かい単位)`、`+8 / +0xC f32 ずれ`、`+0x10 u8 向き (§3.2)`。mapObject は master `MapObject` (784 行 × 0x30、行 ID 付き)。`+0 アーカイブ, +4 エントリ, +0x10 f32 半径` (確定: 値の形のみ)。

### 5.5 区画 7 (oahu の区画 8): イベントの範囲 (32 B、確定)

`+0 u32 種類 (0 / 1 / 2 = 範囲、100 / 101 / 102 = 置物 (oahu と同じ))`、`+4 u32 EventObject の行`、`+8 / +0xA s16 x, y`、`+0xC / +0x10 f32 ずれ`、`+0x14 / +0x18 f32 範囲の大きさ`、`+0x1C u8 向き`、`+0x1D u8 0 = 円 / 1 = 矩形`。種類 1 + 矩形 (+0x1D = 1) の例: 幅 3.0 高さ 1.0。795 件、EventObject の行は全件が範囲内。

### 5.6 区画 8 (oahu の区画 9): 地点 (24 B、推定)

`+0 u32 種類 (1 = 1300 件、2 = 174 件)`、`+4 u32 0`、`+8 u8 値 (1 / 5 / 9 …)`、`+0xC / +0xE s16 x, y`。M02 (島のフィールド 11 件)・F01・S01 だけにある (21 マップ)。PlantPoint / FishingPoint の地点と推定 (oahu と同じ見立て、未確認)。

### 5.7 区画 6: 出現する敵 (確定)

`ヘッダー 8 B {u32 MonsterGroup の行 ID or 0, u32 0xFFFFFFFF}` + `{u32 行 ID, s16 x, s16 y} × n` (セルの値 0x80000000 = マップの既定)。ヘッダー 281/281 とセル 3377/3377 (0x80000000 を除く) が、コンテンツの `MonsterGroup` (行 ID 付きの表) の行 ID と一致。**oahu はハッシュだった欄が、行 ID に変わった**。

## 6. タイルのモデル (タイルセット → MapParts → GSC)

### 6.1 MapData の選び方 (確定)

1. マップ表の +0x28 が 0 でも 0x80000000 でもなければ、その**行 ID**で `MapData` の行を引く (行 ID は `0x80000000 | 番号` の形、`LanaiTable.find`)。
2. そうでなければ MapGroup の +0x08 (屋外・ダンジョン用の行 ID)。**マップに屋内のタイル (種類 15〜27) があり、MapGroup +0x0C が 0 でなければ、+0x0C** (屋内用の行 ID)。oahu の「屋内なら mapGroup +0x2F」と同じ判定 (種類 + 1 が 0x10〜0x1C)。

この規則で、553 マップすべてのタイルに (種類 33 を除いて) モデルが見つかる。屋内の判定を入れないと 5 マップが外れる (屋内 46 マップ中、屋内用の行で 46 件すべて成立)。

### 6.2 MapData (16 B / 行、確定・推定)

| 位置 | 内容 | 確度 |
|---|---|---|
| +0x00 u8 | 0 または 1 (多くの行は 1)。+0x01 = 0x1A | 未解析 |
| +0x04 u8 | 0x11〜0x30 ほか (BGM らしき) | 未解析 |
| +0x06 u8 | 0〜7 | 未解析 |
| +0x08 u8 | 0x6B / 0x6C ほか (足音らしき) | 未解析 |
| **+0x0A u8** | **タイルセット = `MapPartsType` の行番号 (0 始まり)** | **確定 (553 マップ中 507 + 屋内 46 で、全種類にモデルがある)** |
| **+0x0B u8** | **`MapResource` の行 (多くは +0x0A + 1)**。MapResource の +0 / +4 のテクスチャの名前 (`tex_02_caveB.bch` など) がタイルセットと合う (屋内のとき `tex_01_room` など別名) | 確定 (範囲 325/325) / 名前の一致は推定 |
| +0x0C u8 | `MapCamera` の行 (範囲 325/325) | 推定 |
| +0x0D u8 | `MapEnv` の行 (範囲 325/325。空・光) | 推定 |

(`+0x0A`〜`+0x0D` は 1 つの u32 `0xD0D0 ...` の一部。先頭 2 バイト `01 1A` も含め、残りの欄は「BGM・足音・フラグ」と推定するが、実データで照合していない。)

### 6.3 MapPartsType と MapParts<名前> (確定)

- `MapPartsType` (コンテンツごと、n × 4 B): 各行 = そのコンテンツの `MapParts<名前>` の表 (type 11 のエントリ) のハッシュ。行番号 = MapData の +0x0A。同じ表が複数行にあってもよい。
- `MapParts<名前>` (`MapPartsCaveB` / `RuinsB` / `Temple` …、**67 行 × 0x40**): 行 = **タイルの種類 + 1** (行 0 は空)、1 行 = `{u32 アーカイブ, u32 エントリ} × 8` (文字 `z`/0 = 0、`a`〜`g` = 1〜7)。値 0 は「その文字のモデルがない」。
  - 例 (`MapPartsCaveB`): 行 6 (種類 5) の文字 0 = `A6D70000` の `D922A800` = `bg_02_caveB_01.gsc`、文字 1 ('a') = `4E49400` = `bg_02_caveB_01_a.gsc`。
  - 種類 + 1 が 16〜33 の行 (種類 15〜32) は文字 0 のモデルだけ持つことが多い (屋内の部品、別アーカイブ `B2AD0000` など)。
- **種類 33 (行 34) は CaveB / ForestA / Green の表で空** (全体で 484 件、D01001B01 の枠の内側など)。モデルなし (見えない / 空) と推定する。
- 種類 15〜27 (屋内の部品) は、屋外のタイルセット (CaveA など) の表にモデルがない。屋内の MapData (§6.1) が選ぶ別の表にある。
- master の `MapPartsCommon` (67 × 12 B): 種類ごとの共通値。`{u32 a (0x12 刻み), u32 b (a + 4 か +0x0A), u32 末尾}` (oahu の mapParts の a / b / +0x188 の 4 ビットに当たる。モデルのハッシュは含まない)。

### 6.4 モデルの実体 = GSC (確定)

- タイルのモデルのエントリは **type 10 の `.gsc`** (アーカイブ `A6D70000` = CaveB の 47 エントリなど)。`bg_02_caveB_01.gsc` のようなエントリ名がファイル名として付く。
- GSC の中身は oahu の type 8 (0x180 バイトのヘッダー + BCH) と同じ作り: ヘッダー内に `rom:/cg/model/map/map_parts/bgpt_02_caveB/bgpt_02_caveB_01.bch` の UTF-16 のパス、`+0x38 = 0x180` (BCH の位置)、`+0x3C` = BCH のサイズ (oahu の +0x3C / +0x40 より 4 バイト前)。0x180 の位置に `BCH` がある。
- **Panana の `src/bch/bch.ts` の `unwrapBch` が 47 / 47 エントリで通る** (BCH の位置を探している)。`bchSummary` も読める。
- テクスチャは別: `MapResource` の行の +0x00 = テクスチャのアーカイブ (`3DC60000` の type 4 エントリ `tex_02_caveB.bch` など)、+0x04 = そのエントリ。+0x08 / +0x0C = 空 (sky) の GSC、+0x14 / +0x18 = 土台 (base) の GSC (アーカイブ + エントリ。例 `A6D70000` / `B3D26C00` = `bg_02_caveB_base.gsc`)。残りの欄は未解析。

## 7. MapGroup と EventObject (確定)

`MapGroup` (コンテンツごと、1 + (ダンジョン数) 行 × 0x30、行 0 は空):

| 位置 | 型 | 内容 | 確度 |
|---|---|---|---|
| +0x00 | u32 | MessageMapName (master、193 行) の行 ID。ダンジョン名 (例 `水源どうくつ`、`幻帝のどうくつ`)。0 は行番号 0 | 確定 |
| +0x08 | u32 | MapData の行 ID (屋外・ダンジョン) | 確定 |
| +0x0C | u32 | MapData の行 ID (屋内)。0 = なし | 確定 |
| +0x10 | u32 | 0x06000001 / 0x06000002 | 未解析 |
| +0x14 / +0x18 | u32 | 最初のマップのハッシュ / 最初の地点 ID | 確定 (DebugMapJump と照合: 58/127 一致、残りは別の入口) |
| +0x1C | u32 | EventObject の表のエントリ (`D01_EventObject` など) | 確定 |
| +0x20 / +0x24 | u32 | StaticEvent の表 / `*_msg` のエントリ | 推定 |
| +0x28 / +0x2C | u32 | 状態の枠の先頭・個数 (oahu の mapGroup +0x22 / +0x24 に当たる) らしき値 | 未解析 |

- 区画の EventObject の行 (区画 3 / 4 / 5 / 7 の +4) は、**マップの MapGroup の EventObject の表の行番号**。範囲外は 0 件 (3 / 4 / 5 / 7 の計 6110 件)。
- EventObject は **100 B** (oahu は 0x58)。`u32[0..3]` = 出る / 消える条件らしき値、`u32[4]` = 動作の型の行 ID (0x800000xx)、`u32[5..]` = 動作の引数 (ワープの行き先は §5.1)、末尾付近に状態の枠 (u16、0xFFFF = 行番号) と 0xD0D0D0 の詰め物。**欄の細かい意味は未解析**。
- コンテンツの `contentsNNNN.cro` が EventObject / 区画の ID ごとのスクリプトを持つ ([contents.md §4 CRO と CRR](contents.md#4-cro-と-crr))。

## 8. ステージからマップへの引き方 (確定)

1. ステージ (MapStageIntegration) の +0x34 = コンテンツ番号 N。
2. Contents の行 N → ルートのアーカイブ → エントリ `131C5000` (マップ表) と `C9F79000` (マップ DB)。
3. マップ表の全行がそのコンテンツのマップ。`+0x2C` の MapGroup ごとに分けられる (例 コンテンツ 58 の `D01001B01` … `D08011B06` は MapGroup 2〜9、`F01OUTF01` は MapGroup 1)。
4. ステージの開始マップ: `DebugMapJump` (1 行 48 B、`{u32 マップのハッシュ, u32 地点 ID, u32, u32 …}`) の先頭が、そのコンテンツで入る町・入口を指す (127 件中 65 件が同じコンテンツのマップ表に入る。それ以外は別コンテンツ (島・町) の入口で**推定**)。MapGroup +0x14 / +0x18 も最初のマップ。
5. 同じコンテンツに町 (F01、S01 …) とダンジョン (D01 …) が両方入ることもある。

## 11. 文字・タイル種類の大きな見立て (推定)
