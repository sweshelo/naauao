# 新しいマップの追加 (code.ips で表を拡張する方式) 設計メモ

> 対象: 電波人間のRPG2 (`kahara`) v1.1.0。分類: Panana / elpulse が導入する MOD 設計・実装記録。
> 根拠: [再編前の解析記録](https://github.com/sweshelo/naauao/blob/27cc7ec6682589c764906ada88e78f5d04d57cc2/new-map.md) と本文に記す関数・実データ。従来の「確定」は元の解析で確認した範囲を指し、今回の再編で ROM 全体を再検証した意味ではない。
> アドレスは特記なき限り実行時/Ghidra アドレス (code.bin の位置 = アドレス − `0x100000`)。RPG3 には適用しない。

panana issue #19 の方式 B (code.bin のマップの表を code.ips で拡張する) の下調べと設計です。対象は v1.1.0 の code.bin。アドレスは Ghidra 上のもの (ファイル位置 = アドレス − 0x100000)。
前提の構造は [map.md](../../kahara/map.md) (§0〜§2、§6、§7)。

確度の表記: **確定** = コードで読み方を確認し、実データで裏付けが取れたもの。**推定** = 呼び出し元とデータの形から推測したもの。


## 0. 結論

- 新しいマップは「既存のダンジョンの新しい階」として足す。新しいダンジョン (mapGroup の行) を足すのは対象外 (§7)。
- code.bin の変更は 2 つだけで済む (確定)。
  1. **区画の表**: 検索関数 `FUN_002d9b18` の「見つからない」経路 (0x2D9B70) を 1 命令だけ差し替え、追加の表を探すコードへ飛ばす。
  2. **ダンジョンの表**: 足す先のダンジョンの行 (0x4C3AFC) の「マップ数」と「マップの行の配列へのポインタ」を書き換え、既存の行を写した配列 + 新しい行を指させる。フックは要らない。
- 行数の即値の書き換えは要らない。0xCD は区画の表の検索 1 か所だけで、フックで回避する。0x38 はダンジョンの行数で、ダンジョンを足さないので変わらない。
- マップの数に依存するセーブの固定長配列はない。マップごとのセーブはオートマップだけで、これはマップのハッシュで引く「ダンジョンごと 14 枠」の方式 ([kahara/new-map.md §3](../../kahara/new-map.md))。
- 追加の表は .rodata の末尾の余白 (0x510490〜0x511000、2928 バイト) に、フックのコードは .text の末尾の余白の最後 (0x4BFF80〜) に置く。
- マップ DB は索引を hash の昇順 (符号なし) に並べ直せば、ゲームの二分探索で見つかる ([kahara/new-map.md §5](../../kahara/new-map.md))。

## 2. 足し方 (設計)

### 2.1 区画の表: `FUN_002d9b18` のフック

0x2D9B70 の `mvn r0, #0` (見つからない) を `b sect_ext` に変える。そのほかの命令は変えない。
`sect_ext` は追加の区画の表を探す。見つかれば r3 = その行、r0 = 0 にして元の処理 (0x2D9B74、区画 k の hash を取り出す) に戻る。
関数の後半は r3 と r5 を使わない (確認済み) ので、両方を壊してよい。

```
sect_ext:                       ; r1 = マップの hash, r2 = 区画の番号 (触らない)
    ldr   ip, =EXT_HEADER
    ldr   r0, [ip, #8]          ; 追加の区画の行数
    ldr   ip, [ip, #12]         ; 追加の区画の表
1:  subs  r0, r0, #1
    bmi   2f
    ldr   r5, [ip], #40
    cmp   r5, r1
    bne   1b
    sub   r3, ip, #40           ; r3 + 0 * 40 = 見つけた行
    mov   r0, #0
    b     0x2D9B74
2:  mvn   r0, #0                ; 元と同じ (見つからない)
    b     0x2D9B74
```

13 命令 + リテラル 1 語 = 56 バイト (keystone でアセンブルを確認)。既存のマップは今までどおり元の表で見つかるので、振る舞いは変わらない。

### 2.2 ダンジョンの表: 行の配列を移す

新しいマップを足すダンジョン D の行 (0x4C3AFC + D の行 × 16) について:

1. 追加の領域に「D の既存の行の写し + 新しい行」の配列を作る。
   - 写しの +0x10 には、元の行番号 k のキー (0x4C1738 + k × 4) を入れておく。実行時の値と同じになる。
2. D の行の +0x08 (マップ数) と +0x0C (配列へのポインタ) を、新しい配列に書き換える。

- 元の行 (0x5204F4 の中) はそのまま残る。静的初期化は元の行に書き続けるが、もう読まれない。既定値 (行 0) を返す 2 関数は元の行を返すので、これも問題ない。
- 新しい配列は .rodata (読み出し専用) に置く。マップの行を書き換える処理は静的初期化のほかに見つからない (推定。§7 のリスク)。

### 2.3 置き場所と形式

| 何 | 場所 | 大きさ |
|---|---|---|
| フック (`sect_ext`) | .text の余白の最後 0x4BFF80〜0x4BFFB8 | 56 B |
| 追加の表の見出し + データ | .rodata の余白 0x510490〜0x511000 | 2928 B |

- .text の余白 (0x4BF020〜0x4C0000) は、アイテム MOD と汎用スイッチ (`PNSW`) が先頭から詰めて使っている (elpulse のビルドでは 0x4BF9C8 まで)。フックは衝突しないように末尾に置く (0x4BFF80〜0x4C0000 の 128 バイトを新しいマップ用に予約する)。
- .rodata の余白 (0x510484〜0x511000) は、ファイルの中にあり (code.bin はページ単位に埋めてある) 全部 0。実行時は読み出し専用でマップされる (exheader: .rodata 0x4C0000、0x51 ページ)。今はだれも使っていない。
- code.bin は伸ばせない。.data の直後 (0x5E5D3C〜) は .bss (0x59778 バイト) で、ゲームが使う。exheader を変えれば伸ばせるが、Luma / Azahar で exheader の差し替えが要り、配布が面倒になるので採らない。
- 見出し (0x510490):
  ```
  +0x00  "PNMP"            目印 (panana が有無を判定する。汎用スイッチの "PNSW" と同じ考え方)
  +0x04  u32 版            1
  +0x08  u32 区画の行数     n
  +0x0C  u32 区画の表       → n × 40 B {map hash, 区画 1〜9 の hash}
  +0x10  u32 マップの行数   m (panana が読み戻すため。ゲームは使わない)
  +0x14  u32 行ポインタ配列 → m × u32 (各要素が追加マップの 0x1C B 行を指す)
  +0x18〜               データ (区画の表、ダンジョンごとの配列、マップのコードの文字列)
  ```
- 容量の目安: 新しいマップ 1 枚 = 区画の行 40 B + マップの行 28 B + 名前 12 B ≒ 80 B。これに、足す先のダンジョンごとに 1 回、既存の行の写し (最大 D02 / D03 / D08 の 12 行 = 336 B) が加わる。1 つのダンジョンに足すなら 30 枚ほど入る。
- 足りなくなったら、使われていない複製を使える: ダンジョンの表の複製 0x4C41C0 (896 B)、キーの配列の複製 (.rodata に 127 個 × 0x334 B)。キーの配列の複製を上書きすると、その静的初期化が使われていない行の複製にごみを書くが、害はない。

## 6. 新しいマップ 1 枚に要るもの

1. **hash を決める**。マップの hash 1 個 + 区画 1〜9 の 9 個。マップの hash 関数は分かっていないが、ゲームは名前から hash を計算せず、どこも hash で参照するので、任意の値でよい。
   - 決めた値は、マップ DB の索引、区画の表 (元 + 追加)、code.bin の表のどの hash とも重ならないことを確かめる。
2. **code.ips** (§2):
   - 追加の区画の行 `{hash, 区画 1〜9}`。
   - マップの行 `{hash, 階, 0, 0, mapData のキー, +0x14, 名前へのポインタ}`。mapData のキーと +0x14 は、同じダンジョンの似た階から写す。キーを持たないなら 0xF23EB9BB (「なし」、0x4C681C の値)。
   - 名前の文字列 ("D01B03001" など。見た目だけのもの)。
   - ダンジョンの行の配列の移し替えと、マップ数・ポインタの書き換え。
   - フック (0x2D9B70 → `sect_ext`)。1 回だけ。
3. **マップ DB** に 10 個のエントリ (区画 0 = タイル、3 = 出入口、…)。
   - Panana はタイルを x / y とも 0〜29 に制限する。旧案の y 0〜39 はオートマップの保存範囲であり、実行時配列の安全性を保証しない ([ゲーム側の制約](../../kahara/new-map.md) §6)。
4. **入口と出口**。既存のマップの区画 3 の地点の行き先 (+0x04 マップ、+0x08 地点 ID) を新しいマップに向ける。新しいマップの区画 3 には、その地点 ID の着地点と、戻る出口を置く。
5. 宝箱・イベントは、ダンジョンの EventObject の空いている行を使う (必要なら、ダンジョンのアーカイブに行を足す)。

## 7. 対象外・リスク

- **新しいダンジョン** (mapGroup の行を足す) は対象外。ダンジョン ID は `FUN_002f8de0` (ワープ・オートマップの枠)、変数 0x8D (57 個)、0x92 の枠、mapGroup の各欄、EventObject のアーカイブ、ダンジョンの表の行数 0x38 など、あちこちで決め打ちされている。
- **マップの行が読み出し専用になる** (推定の安全): 移した配列は .rodata にある。静的初期化のほかにマップの行へ書く処理は見つからなかったが、見落としがあればデータアボートで止まる。Azahar で、足したダンジョンの全部の階に出入りして確かめる。
- **パッチを外したセーブ**: 新しいマップにいる状態でセーブし、パッチを外して起動すると、そのマップの hash が見つからず、ごみの区画を読む。配布するときは注意書きが要る。
- **マップ DB の大きさ**: アーカイブの読み込み先の大きさに上限があるかは未確認。大きく増やす前に確かめる。
- **+0x14 の意味**が未確定。似た階の値を写すのが安全。
- **.text の余白の取り合い**: アイテム MOD・汎用スイッチ・新しいマップのフックが同じ余白を使う。フックを末尾の予約 (0x4BFF80〜) に置き、既存のビルドの `assert addr <= CAVE_END` を 0x4BFF80 に下げて衝突を防ぐ。
- **複製**: 128 個の複製のうち、生きているのは 0x5204F4 / 0x4C3AFC / 0x4C1738 だけ、という判定は、リテラルの走査によるもの (レジスタで作ったアドレスは見えない)。今回の変更は、この 3 つと区画の表しか触らない。

## 8. panana の実装

- `src/game/mappatch.ts`: code.ips の記録を作る (`buildMapPatch`)。
  - 新しいマップの一覧から、§2 の表 (PNMP)、フック、ダンジョンの配列の移し替えを作る。
  - 土台の code.bin に古い PNMP があれば作り直す。マップが 0 枚なら、元の code.bin のバイトに戻す (テストで一致を確認)。
  - 置き場所: まず .rodata の余白。ダンジョンの配列が入らなければ、使われていないキーの配列の複製 (24 個まで) に置く。
    - 区画の表と行ポインタ配列は余白 (2928 B) に入れる必要がある。ヘッダー 24 B + 1 枚あたり 44 B だけでも上限は 66 枚 (旧記述の約 70 枚は行ポインタ配列を含めていなかった)。ほかの配置によって実際の上限は減る。
    - 予備に使わなかった複製は、元のキーの配列に戻す。
- `src/game/codebin.ts`: PNMP があれば、その区画の表を読み込む。新しいマップには `added` の印を付ける。移した行の mapData のキーは +0x10 から読む。
- `src/game/mapdb.ts`: `add(hash, bytes)` を足した。
- `src/game/newmap.ts`: 新しいマップを作る (hash 10 個、コードの案、写す元のマップから区画 6 の見出しと mapData のキー・+0x14、必要ならタイルを写す)。
- `src/export/pack.ts`:
  - 新しいマップの区画 10 個をすべて DB に足す。
  - code.ips は「土台の code.ips + 新しいマップの記録」にする (後ろの記録が勝つ)。
- 画面: マップ編集のヘッダーの「＋ マップを追加」(`src/editor/newmapdialog.ts`)。
  - 追加したマップは編集内容と一緒に IndexedDB に保存する。
  - 検証 (`validate.ts`) で、次のものを知らせる。
    - タイルがない、区画 6 がない
    - 出入口がない、ほかのマップから来る出入口がない
    - オートマップの枠 (14) を超える
- elpulse の `mod/build_code.py`: .text の余白の終わり (`CAVE_END`) を 0x4BFF80 に下げた。

## 9. 再編時の実装照合 (2026-10-08)

[Panana mappatch.ts](https://github.com/sweshelo/panana/blob/c48b0baaffab5d021625183dce4ec69e62afc37f/src/game/mappatch.ts) の `HOOK_CODE`、`readExtension`、`buildMapPatch` と照合し、命令数と PNMP +0x14 を訂正した。旧記録の「16 命令・56 バイト」「+0x14 → m × 0x1C B」は形式の説明として誤り。 `MapDb.build` は `a.hash - b.hash`、`u32()` は符号なしで、ゲームの索引順序に対応する。これは Panana 実装の確認であり、ROM の新規逆解析ではない。
