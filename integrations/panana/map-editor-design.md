# マップエディタ 設計書

> 対象: 電波人間のRPG2 (`kahara`) v1.1.0。分類: Panana の初期設計記録 (現行ゲーム仕様の根拠にしない)。
> 根拠: [再編前の解析記録](https://github.com/sweshelo/naauao/blob/27cc7ec6682589c764906ada88e78f5d04d57cc2/map-editor-design.md) と本文に記す関数・実データ。従来の「確定」は元の解析で確認した範囲を指し、今回の再編で ROM 全体を再検証した意味ではない。
> アドレスは特記なき限り実行時/Ghidra アドレス (code.bin の位置 = アドレス − `0x100000`)。RPG3 には適用しない。

電波人間のRPG2 (v1.1.0, TID 00040000000A7900) のダンジョンのマップを、ブラウザ上で 3D を見ながら編集し、LayeredFS 用の MOD として書き出すアプリの設計です。実装は別のセッションで行います。

この設計書は方針と要点だけを書きます。データ構造の詳細は次を参照してください。
- [map.md](../../kahara/map.md) (マップ DB・タイル・区画・座標・タイルセット)
- [RomFS](../../kahara/romfs.md)・[共通アーカイブ形式](../../common/formats.md)

また、Python の参照実装が次にあります。
- `tools/gsarc.py` (アーカイブの展開・再パック、LZ10)
- `tools/gstable.py` (GS テーブル)
- `tools/mapdump.py` (マップ DB の読み取りと、各区画の解釈)

> **後続調査との差分:** 以下のフェーズ分け・未解析欄は初期設計当時のもの。新規マップ追加は [new-map.md](new-map.md) に実装記録があり、屋内・扉モデル・回転・区画の意味・mapData の上書きは [kahara/map.md](../../kahara/map.md) の後続解析を優先する。30 × 30 はエディタ側の制限で、ROM 全体の上限が確定した意味ではない。

## 1. 目的と範囲

- **フェーズ 1 (この設計の中心)**: 既存のフロアの編集。
  - タイル (区画 0)、扉・階段・ワープホール (区画 3)、宝箱 (区画 4)、オブジェクト (区画 5 / 8) の配置を変える。
  - 3D (ゲームのモデル) と 2D (真上) で表示する。
- **フェーズ 2 (将来)**: 新しいマップの追加。
  - code.bin の表 (0x4C1A74 の 205 件、0x4C3AFC) を広げる code.ips が必要になる。
  - `mod/build_code.py` 側の作業なので、エディタは「マップ DB に新しい区画を足す」ところまでに留める。
- **対象外**: ワールドマップ (構造は [worldmap.md](../../kahara/worldmap.md))、町の屋内、イベントスクリプト、モデル自体の編集。

## 2. ブラウザ (TypeScript) で ROM を扱えるか

結論: **扱える。ただし入力は復号済みのダンプに限る。**

- 今回の CIA は `NCCH Crypto: None` (暗号化なし)。
  - CIA → NCCH → RomFS / ExeFS の解析は 3dbrew に仕様が公開されていて、どれも数百行程度で実装できる。
  - ファイル (約 170 MB) は `File.slice()` で必要な範囲だけ読めばよいので、全体をメモリに載せる必要はない。
- 暗号化されたダンプ (製品版そのまま) は鍵が必要なので、**対応しない**。
  - 利用者には GodMode9 などで復号したダンプを使ってもらう (エラー文で案内する)。
- 受け付ける入力:
  1. 復号済み CIA (`.cia`)
  2. 復号済みの `.3ds` / `.cxi` (NCCH)
  3. 展開済みの RomFS フォルダと code.bin (フォルダの読み込み: File System Access API またはドラッグ&ドロップ)
- 必要な処理と実装のめど:

| 処理 | 仕様 / 参照 | 規模 |
|---|---|---|
| CIA ヘッダー → コンテンツ 0 の位置 | 3dbrew "CIA" (各部分 64 バイト境界) | 小 |
| NCCH ヘッダー → ExeFS / RomFS の位置 | 3dbrew "NCCH" (メディア単位 0x200) | 小 |
| RomFS (IVFC レベル 3、ディレクトリ / ファイルのメタデータ表) | 3dbrew "RomFS" | 中 |
| ExeFS `.code` の展開 (BLZ = 後ろから読む LZ) | 3dbrew "ExeFS"、ctrtool の実装 | 小 |
| RomFS ルートの独自アーカイブ | `tools/gsarc.py` / [アーカイブ形式](../../common/formats.md) | 小 |
| LZ10 (展開・圧縮) | `tools/gsarc.py` | 小 |
| ZIP (deflate) | `DecompressionStream('deflate-raw')` か fflate | 小 |
| GS テーブル | `tools/gstable.py` | 小 |
| CGFX (bcmdl) → three.js | §5 | 大 |

- ROM 由来のデータは、アプリにもリポジトリにも含めない。
  - すべて利用者のダンプから、ブラウザの中だけで取り出す (アップロードしない)。
  - 取り出した結果は IndexedDB にキャッシュしてよい (その端末の中だけ)。

## 3. 構成

Vite + TypeScript + three.js の静的サイト (サーバー不要)。モジュールの分け方:

```
src/
  rom/        cia.ts, ncch.ts, romfs.ts, exefs.ts, blz.ts      … ダンプ → ファイル
  archive/    gsarc.ts, lz10.ts, zip.ts, gstable.ts            … 独自アーカイブ・表
  game/       codebin.ts   (0x4C1A74 / 0x4C3AFC などの表)
              mapdb.ts     (マップ DB の読み書き)
              sections.ts  (区画 0 / 3 / 4 / 5 / 8 の型と変換)
              tileset.ts   (mapParts / mapData / mapResource / mapGroup → モデル)
  cgfx/       cgfx.ts, pica.ts (頂点・インデックス), texture.ts (ETC1 など) → three.js
  editor/     state.ts (編集モデル・Undo), view3d.ts, view2d.ts, palette.ts, inspector.ts
  export/     pack.ts (マップ DB → A90C8038 → LayeredFS の zip)
  test/       Python の参照実装と照合する golden テスト
```

## 4. ゲームデータの読み込み (起動時)

[map.md](../../kahara/map.md) の図のとおりにたどる。

1. code.bin (ExeFS `.code` を BLZ で展開。**ベースアドレス 0x100000 のフラットなバイナリ**)
   - 0x4C1A74: 205 件 × `{マップハッシュ, 区画 1〜9 のハッシュ}`
   - 0x4C3AFC: 56 件 × `{ダンジョン, 名前ポインタ, 件数, マップ配列}`。マップ配列の 1 件は 0x1C バイトで、+0 ハッシュ、+4 階、+0x18 名前 (文字列、code.bin 内のポインタ)
   - アドレスは v1.1.0 固定。起動時にバージョンを確かめる (TitleVersion 1040、または既知の値で照合) 。
2. RomFS `A90C8038` → エントリ `A2C14C00` (LZ10) = マップ DB。
3. RomFS `56562135` (マスター) → mapParts / mapData / mapResource / mapGroup (GS テーブル。エントリの名前で探す)。
4. タイルセット (§6) に必要なモデルのアーカイブ (mapResource の行 [0]。例 `46910AB6`) → t8.bin (LZ10)。各エントリは 0x180 バイトのヘッダー + CGFX。

## 5. CGFX (bcmdl) の読み込み

- 形式: 標準の CGFX (リビジョン 5)。t8.bin の +0x180 から始まる (`CGFX` マジック)。
  - 1 モデルは約 25 KB (テクスチャ込み)。山のどうくつのタイルセットは 33 ファイルで約 1 MB。
- 必要な部分だけ読む:
  - DATA → DICT → CMDL (モデル)
    - SOBJ: 形状 (頂点バッファ、PICA の属性の形式・スケール、インデックス、サブメッシュ)
    - メッシュ → マテリアル
  - TXOB (テクスチャ): PICA の形式 (RGBA8 / RGB8 / RGB565 / RGBA4 / LA8 / ETC1 / ETC1A4 など)。3DS 独自のタイル並び (Z 順) を並べ直す。
- マテリアルは、ディフューズのテクスチャ 1 枚と頂点カラー程度に簡略化する (フラグメントライティングとコンバイナは近似)。
- 変換は Web Worker で行い、結果 (three.js の BufferGeometry の元データと RGBA のテクスチャ) を IndexedDB にキャッシュする。
- 参考資料: 3dbrew "CGFX"、オープンソースの SPICA / Ohana3DS のソース (読み方の確認用)。
- **最初の検証**: `bgpt_01_caveA_08` (ハッシュ 24C78800) を 1 つ表示して、形・向き・大きさ (1 マス = 500) を確かめる。

## 6. マップの 3D での組み立て

[map.md](../../kahara/map.md) §3・§4 の要約。

- タイルセット = mapData[mapGroup[ダンジョン] の +0x26] の [0]。
  - マップ表 (0x4C3AFC) の行 +0x10 による上書きは、ゲームの `FUN_001c4ec4` の分岐を再現する (未確定の部分は、ダンジョンの既定で代用してよい)。
- モデル = mapParts[種類 + 1] の `+8 + タイルセット × 0x20 + 文字の番号 × 4` のハッシュ。文字の番号は 'z' → 0、'a'〜'g' → 1〜7。
  - ハッシュが 0 の組み合わせは置けない (パレットに出さない)。
- 位置: セル (x, y) の中心 = ((x + 0.5) × 500, 0, (y + 0.5) × 500)。回転 = 向き × 90° (符号・基準は §5 の検証で決める)。
- 区画 3 の地点があるセル (扉・階段) は、ゲームでは別の表 (マスター +0x39C) のモデルになる。フェーズ 1 では記号で表示する。
- 細かい座標 (区画 4 / 5 / 8): ワールド = 50 + 値 × 100。

## 7. 編集モデル

```ts
interface MapDoc {
  hash: number; name: string; dungeon: number; floor: number; tileset: number;
  tiles: Tile[];               // 区画 0
  points: Point[];             // 区画 3 (28 B。未知の欄は raw として保持)
  treasures: Placement[];      // 区画 4
  objects5: Placement[];       // 区画 5
  objects8: Placement[];       // 区画 8
  rawSections: Map<number, Uint8Array>;  // 1, 2, 6, 7, 9 などの未対応の区画はそのまま保持
}
interface Tile { kind: number; x: number; y: number; rot: 0|1|2|3; letter: number /* 0x7A or 0x61..0x67 */ }
```

- 操作: タイルの配置・削除・回転・文字の変更、範囲の選択・コピー、区画 3〜8 の点のドラッグ移動、Undo / Redo。
- パレット: そのタイルセットで使える (種類, 文字) の組をモデルのサムネイルで並べる。役割の分かっている種類 (5 床 / 7 辺 / 9 出入口 / 14 角 / 1〜4 通路) は名前も付ける。
- 2D ビュー: 真上から見た図。ゲーム内のミニマップ風の表示 (部屋・通路・扉・宝箱) を補助にする。
- 未知の欄は必ず元の値を保つ (ラウンドトリップで壊さない)。

### 検証ルール (書き出し前の警告)

- 範囲: 0 ≤ x, y。y < 30 (セルの配列は x 1 列あたり 30)。x の上限は未確定 (既存の最大は 29)。まずは 30 × 30 に制限する。
- 区画 4 / 5 / 8 の値は 0〜299 (範囲外はゲームが 0 に丸める)。
- 区画 3 の地点は、タイルのあるセルに置く。行き先の地点 ID が、行き先マップに存在すること。階段は元の組を残すこと。
- 部屋・通路の見た目の整合 (例: 7 の向き) は警告だけにする (ゲームは自動では直さない)。

## 8. 書き出し

1. マップ DB を作り直す。
   - 変更した区画のバイト列を差し替える。
   - 索引 `{hash, offset, size}` をハッシュの昇順で並べ直し、オフセットを詰めて再計算する。
   - 区画のハッシュは変えない。
2. LZ10 で圧縮し、アーカイブ `A90C8038` の該当エントリだけを差し替える (`gsarc.rebuild` と同じ: ほかのエントリはバイト列をそのまま写し、ヘッダーのオフセット・サイズを直す)。
3. 出力: `00040000000A7900/romfs/A90C8038` の zip をダウンロードする。
   - Azahar: `%APPDATA%/Azahar/load/mods/`
   - Luma3DS: `/luma/titles/`
   - Chrome などでは、File System Access API で MOD のフォルダに直接書き込む機能も付けてよい。
4. 既存の MOD との関係: elpulse の MOD (`mod/deploy.ps1`) は `A90C8038` を触らないので、同じ romfs フォルダに並べて置ける。将来、マスター (56562135) を触る場合は統合が必要になる。

## 9. テスト

- **Golden テスト**: 同じダンプに対して、Python (`tools/mapdump.py`, `tools/gsarc.py`) と TypeScript の結果を照合する。
  - 全 205 マップの区画のサイズ、D01B02001 のタイル一覧、区画 3〜8 の値。
  - Python 側で JSON を出力するスクリプトを追加してよい。
- **ラウンドトリップ**:
  - 何も編集せずに書き出したマップ DB は、展開後のバイト列が元と一致すること。
  - アーカイブも、差し替えたエントリ以外は一致すること。
- **ゲームでの確認** (Azahar):
  - D01B02001 のタイルを 1 枚変えて、見た目と当たり判定が変わること。
  - 宝箱を 1 つ動かすこと。
  - 扉の位置は動かさずにタイルだけ変えても、扉が正しく動くこと。

## 10. 未確定の点とリスク

| 項目 | 影響 | 対処 |
|---|---|---|
| CGFX の細部 (マテリアル、スキン、可視性アニメ) | 見た目の再現度 | 近似でよい。まず形と位置 |
| 回転の向きと、モデルの原点 | 置き方 | §5 の最初の検証で決める |
| 区画 1 / 2 / 6 / 7 / 9 の意味 (敵の出現範囲など) | タイルを消すと、残った区画の点が浮く | raw として保持。区画 6 はセルの一覧なので、タイルと一緒に編集できるようにするのが望ましい (要調査) |
| マスター +0x39C (扉・階段のモデル) | 3D 表示だけ | 記号で代用 |
| マップ表 +0x10 によるタイルセットの上書き | 一部のマップ | 既定で代用し、[map.md](../../kahara/map.md) の追加調査 |
| x の上限、最大のタイル数 | 大きいマップ | 30 × 30 に制限し、実機で確かめる |
| LZ10 の代わりに無圧縮 (comp 0) で書けるか | 圧縮の実装を省けるか | 未検証。圧縮を実装する (難しくない) |
| 新しいマップの追加 (フェーズ 2) | code.ips が必要 | エディタは区画の追加まで。表の拡張は `mod/build_code.py` で行う |

## 11. 段階

3. CGFX を 1 モデル表示し、1 フロアを丸ごと 3D で組み立てて、スクリーンショットと比べる。
4. パレット・サムネイル・3D 上での編集・検証ルールを加える。
