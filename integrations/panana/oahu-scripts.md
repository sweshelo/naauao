# RPG3: データで書けるスクリプト (設計案)

対象: RPG3 (oahu) Update v4096 の `code.bin`。Panana の Issue [#90](https://github.com/sweshelo/panana/issues/90) の設計案で、まだ実装していない。ゲームの仕様は [oahu/events.md](../../oahu/events.md) §3.1「スクリプト (0x2E) のクラスと、呼び出す関数」と [oahu/story.md](../../oahu/story.md) §2.1 に拠る。ここに書く作りは提案で、実機・エミュレータでは確かめていない。

## 1. ねらい

#87 の案 A (既存のスクリプトのメッセージ ID と書き込みの即値を差し替える) では、会話の流れの形が元のスクリプトに縛られる。種類 0x2E の行に「Panana のスクリプト」の印を付けると、決まったクラスの代わりに、コマンドの列を上から順に実行する汎用のクラスが動くようにする。

## 2. 全体の形

1. **行の印**: 0x2E の行の +0x30〜+0x4B は、元のデータで使われていない (+0x34 の 1 行を除く)。ここに印 (+0x30 = `'PNSC'`) と、コマンドの列の始まりの行 (+0x34、u16) と数 (+0x36、u16) を置く。+0x57 は完了の 2 → 3 を決めるので使わない。
2. **入口のパッチ**: `FUN_004bc7c8` の 0x2E の分岐 (@0x4BCBFC、ダンジョンで表を引く前) を、cave の短い関数への分岐に替える。その関数はハンドラ +8 の行の +0x30 を見て、印があれば汎用のクラスを作って返し、なければ元の分岐の命令を実行して戻る。
3. **汎用のクラス**: 基底 `FUN_001F927C(obj, 行)` (0x10 バイト) を呼んだあと、vtable を cave に置いた表 (8 語) に差し替える。[1] 解放・[3]・[5] は基底の vtable 0x57DF94 のものをそのまま、[4] は完了 `FUN_001F91A8`、[2] だけを cave の実行器にする。クラスの大きさは 0x18 (基底 0x10 + 列の始まりと数)。
4. **実行器 ([2])**: 列を上から読み、コマンドごとに既存の関数を呼ぶ。待つ関数 (メッセージ・はい / いいえ) はその中で `FUN_0010F860` でフレームを譲るので、実行器は状態を持たない普通のループでよい。最後に vtable[4] (完了) を呼んで戻る。
5. **コマンドの列の置き場所**: master (21350000) の表の行。新しい表には読み手ができない (`FUN_001D9BBC` が決まったハッシュでつなぐ) ので、使われていない読み手の表 (候補: vendor・innSetting・W01_ground・denpaHash。使われていないかは未確認) の中身を、行の大きさが 0x10 の Panana のコマンドの表に置き換える。実行器は `FUN_0022C084(読み手, 行)` で行を引く。

## 3. コマンド (1 行 = 0x10 バイト)

+0x00 = コマンド (u8)、+0x01 = 飛び先の調整など、+0x04〜+0x0F = 引数。分岐の飛び先は列の中の行番号。

| コマンド | 呼ぶ関数 | 引数 |
|---|---|---|
| メッセージ | `FUN_001EF218(ID, a1, a2, 0, 1.0, 0)` | MessageField の ID (新しいメッセージは `MessageMod_JP`)、文中の値 2 つ |
| はい / いいえ | `FUN_001EFA00(ID, 0, 0)` | 「いいえ」の飛び先。3 択以上は、ゲームと同じく はい / いいえ を続けて作る |
| 値の判定 | `FUN_001EE8B8` / `FUN_001EE7DC` / `FUN_001EDFEC` / `FUN_00212FB8` | どれを読むか (0xF9・0xFA・今のダンジョンの値・段階)、番号、比べ方、値、成り立たないときの飛び先 |
| 値を書く | `FUN_001EE8F8` / `FUN_001EE850` / `FUN_001EE30C` / `FUN_001EDE48` | どれに書くか、番号、値 |
| 段階を書く | `FUN_00213010(段階)` | 段階。「今より小さいときだけ」のフラグ |
| アイテム | `FUN_001EFD00(アイテム, 増減, 1)` | 負の数で取り上げる。持っているかの判定は `FUN_001ECC48` |
| ゴールド | `FUN_001EE9D4(増減)` | 判定は `FUN_001EE9F0` |
| 話す動き | `FUN_0020F954(obj+0x10, 動き, 0)` | NPC の部品がある基底のときだけ (§5) |
| 戦闘 | `FUN_001EE958(ID)` → `FUN_00211228(群れ, BGM)` | 戦闘のあとに続ける ID。ここで列は終わる |
| マップの移動 | `FUN_00212F88(マップのハッシュ, 地点)` | ここで列は終わる |
| 終わり | vtable[4] (完了) | — |

戦闘とマップの移動は場面を切り替えるので、列の最後にだけ置ける。戦闘のあとに続きを書く仕組み (セーブ +0x1860 の ID を読むクラス) は、元のゲームの戻り先を調べてから足す (未確認)。

## 4. 大きさの見積もり

cave は 0x740 バイト。入口の関数 (0x30 前後)、vtable (0x20)、実行器のループとコマンドの表 (コマンドごとに 0x10〜0x30、11 個で 0x200〜0x300) で、0x400 以内に収まる見込み (推定)。Panana の既存のパッチ (ボス戦・追加したアイテムのアクションなど) も同じ cave を使うので、同時に使えるかは書き出しのときに確かめる (`OahuCode.caveSize`)。

## 5. 決めていないこと

- 話す NPC (`FUN_0026AFB8` の基底、+0x10 の NPC の部品) の動きを使うには、汎用のクラスもその基底で作る必要がある。最初の版は基底 `FUN_001F927C` だけにして、NPC の向きと動きは使わない。
- 借りる読み手の表が本当に読まれていないか (コードの参照と、実機で触れたときの動き)。
- [2] を走らせるスレッドの作り手 (待つ関数の中で譲る前提が成り立つか)。
- 3 つ以上の選択肢のウィンドウ (`FUN_00254008` の種類)。

## 6. Panana の UI

- イベントのページで 0x2E の行に「Panana のスクリプトにする」を足し、コマンドの列を行ごとの表で編集する (飛び先は行への矢印)。
- 値の判定と書き込みは、ストーリーのページ (#87) の値の名前を使う。マップのプレビューの「物語の状態」で、列を上から試しに動かして、どの分岐を通るかを見せる。
- 書き出しは、code.ips に入口のパッチと実行器、master にコマンドの表、EventObject の行に印を入れる。

## 7. 確かめる方法

1. Panana の ARM 実行器 (`src/game/arm.ts`) で、実行器を呼ぶ関数をスタブにして動かし、コマンドごとに正しい関数と引数が呼ばれるかをテストにする (ROM のテストで、組み立てた cave を実際の code.bin に重ねて走らせる)。
2. Azahar (Citra) で、会話 → はい / いいえ → 値を書く → アイテム → 段階、の列を 1 本作って動きを見る。
3. 戦闘・マップの移動は、そのあとの戻り先を確かめてから。
