# 電波人間のRPG (honolulu): マップ・宝箱

対象: 日本版 Base Title ID `0004000000077E00`、TitleVersion 1024 (1.0.0)。アドレスは展開済み code.bin の仮想アドレス (base `0x100000`)。[解析の入口](analysis.md) / [モンスター・群れ](monsters.md)。

確度の表記は [monsters.md](monsters.md) と同じ (確定 / コード / データ / 推定)。

区画の大きさの一覧は `python3 roms/tools/honolulu.py maps <code.bin> <A90C8038>`、宝箱の中身は `honolulu.py chests <master>`、階の定義 (出口・宝箱・群れ・人物) は `honolulu.py floors <master> <A90C8038> [エントリ番号]` で出せる ([ツール](../roms/tools/honolulu.py))。

## 1. 全体像と RPG2 との違い

```
マップ (ハッシュ、csvMap の 97 件)
  │
  ├─ code.bin 0x2FF6D8  {マップ, 2 つ目の区画} × 98 件 ─┐
  │                                                     └─> マップ DB (A90C8038 / A2C14C00) の 2 つのエントリ
  │        タイル: 種類 → 部品名ファイル 63165400 → mapParts の行・変種 → モデル (§3.3)
  │        置物: 種類 = mapObject の行 (§3.2)
  └─ ダンジョンの階の定義 ("261" ファイル、A90C8038 の 0004〜0021。dungeonData +0x04 で引く)
        記録 (階・区域) ごとにマップ・群れ (monsterGroup のキー)・宝箱 (itemGroup のキー)・出口を持つ
```

- マップ DB の形 (`u32 件数` + `{u32 ハッシュ, u32 位置, u32 大きさ}` × 件数、ハッシュの昇順) は RPG2 と同じ。位置はエントリ表の後ろ (`4 + 12 × 件数`) から数える。(確定)
- RPG2 は 1 マップに区画 0〜9 (10 個) を持ち、区画の表は code.bin 0x4C1A74 の 205 件 ([kahara/map.md](../kahara/map.md))。初代は **1 マップに 2 つ** で、表は code.bin 0x2FF6D8 の 98 件 (下の §2)。マップ DB の 194 件 = 97 マップ × 2。(確定)
- 宝箱・出現する敵は、RPG2 のように区画に入っていない。ダンジョンの階の定義 (§4) が群れと宝箱のキーを持つ。(データ)

## 2. マップ → 区画の表 (code.bin 0x2FF6D8、98 × 8)

- 1 件 = `{u32 マップのハッシュ, u32 2 つ目の区画のハッシュ}`。どちらもマップ DB のエントリ。97 マップのうち 1 つ (`E4544B2E`) が 2 回出るので 98 件。(データ)
- 読み手 `FUN_002A6xxx` (0x2A6824〜): マップ DB `A2C14C00` を読み込み、今のマップのハッシュで表を 0x62 (98) 件まで線形に探して 2 つ目のハッシュを得る。その後 2 つのハッシュでマップ DB を二分探索し、1 つ目のデータの位置を物体の +0x0C、2 つ目のエントリの大きさを +0x10 に置く。件数 98 はコードに固定。(コード)
- 表の直後 (0x2FF9E8) は s16 × 9 の表 `8, 8, 10, 10, 14, 14, 16, 18, 18`。階の定義の頭 +0x2A (0 なら +0x2B) を添字にして階の幅・高さ (セル) の既定値を引く。範囲外は 8。頭 +0x28 / +0x29 が 4 以上ならそちらを使う (§4.2)。(コード、`FUN_002A66DC`)

## 3. 区画のデータ

### 3.1 1 つ目 (マップのハッシュそのもの): タイル

1 件 12 バイト。csvMap の 97 マップで計 5812 件 (0x2FF6D8 の表で 2 回出る `E4544B2E` を 2 回数えると 5878 件)。(データ)

| +0x04 | s16 | x (セル、最大 49) | データ |
| +0x06 | s16 | y (セル、最大 33) | データ |
| +0x08 | u16 | いつも 0xFE4E (下位バイトは `'N'`) | データ (意味は未解析) |
| +0x0A | u16 | いつも 0x0028 | データ (意味は未解析) |

- RPG2 の区画 0 (`{u32 種類, s16 x, s16 y, u8 向き, u8 文字, u16 0}`、種類 0〜46) と同じ 12 バイトだが、種類は mapParts の行ではなく部品名ファイルの番号で、向きと変種も種類に含まれる (§3.3)。

### 3.3 タイルのモデル

タイルの種類からモデルまでは次のようにたどる。97 マップのタイルすべて (階の定義が使うタイルセットごと) で、たどった先のエントリがタイルのモデルのアーカイブにあることを確かめた。(データ)

```
タイルの種類 k
  └─ 部品名ファイル (A90C8038 のエントリ 0003 = 63165400) の要素 k の名前 ("room28a")
        └─ "room_28" + 変種 1 ('a') → mapParts の行 16 + 28 = 44
              └─ mapParts +0x0C + 0x20 × タイルセット + 4 × 変種 = モデルのエントリ
                    (タイルセット = mapData +0x00、アーカイブ = mapResource[mapData +0x06] +0x00)
```

**部品名ファイル (`63165400`、1456 B)**: `u32 件数 (121)` + `{char 名前[8], u8 × 4}` × 121。(データ)

- 名前は `path_00`〜`path_14`・`room_00`〜`room_31` (mapParts の名前と同じ) か、その数字の後ろに変種の文字 `a`〜`g` を付けたもの (`path01a`・`room02c` など。区切りの `_` がない)。
- 種類 k = 要素 k。根拠: 実データに出ない種類 0・9〜16・65〜72・90・103〜106 は要素 `path00a`・`path07a`〜`path14a`・`room18a`〜`room25a`・`room_01`・`room_14`〜`room_17`。3 × 3 の部屋の中央が 89 (`room_00`)、四辺が 91〜94 (`room_02`〜`room_05`、壁 1 枚)、四隅が 117〜120 (`room_28`〜`room_31`、壁 2 枚) になる。(データ)
- 後ろの 4 バイトは上・右・下・左の辺の種類と推定 (0 = 開いている、1 = 壁、3 = 通路の壁、8・9 = 部屋の辺の左右違い)。読み手は未確認。(推定)
- 名前 → 行・変種 (`FUN_0016CB70`): 名前の 5 文字目が `_` でなければ `xxxx_NN` に組み直し、7 文字目 `a`〜`g` を変種 1〜7 としてセル +0x14 に置く (`_` 付きの名前は変種 0)。`path_NN` は行 1 + NN (`'0'` → 字 − 0x2F、`'1'` → 字 − 0x25)、`room_NN` は行 16 + NN (`'0'`〜`'3'` → 字 − 0x20・−0x16・−0x0C・−0x02)。結果はセル +0x00。(コード)

**mapParts (master エントリ 36、48 × 0x114、保持体 +0x444)**:

| 位置 | 型 | 内容 | 確度 |
|---|---|---|---|
| +0x00 | u32 | 名前 (ファイル内の位置。`なし`・`path_00`〜`path_14`・`room_00`〜`room_31`)。行 1〜15 が通路、16〜47 が部屋 | データ |
| +0x04 | u32 | ミニマップの絵の名前 (`path01.bclim` など) | データ |
| +0x08 | u8 | 形の番号 (3〜31 の奇数)。向きだけ違う行が同じ値 | データ |
| +0x09 | u8 | いつも 0x1A | データ |
| +0x0C + 0x20 × t + 4 × v | u32 × 64 | タイルセット t (0〜7) の変種 v (0〜7) のモデル (タイルのモデルのアーカイブのエントリ) | コード + データ |
| +0x10C | u8 | 辺のビット。上位 4 bit が部屋の壁 (0x40 上・0x80 右・0x20 下・0x10 左)、下位 4 bit が通路の開いた辺と推定 | データ (推定) |
| +0x10D | u8 | 通路の行だけ 1〜15 (下位 4 bit の補数に近い) | 未解析 |
| +0x10E | s16 | Y 軸の回転 (度)。0・90・−90・180。向き違いの行は同じモデルを持ち、この値だけが違う | データ |
| +0x110 | u16 | いつも 0xD0D0 | データ |

- 変種 0 は `_` 付きの名前、1〜7 は `a`〜`g`。使われない変種の欄は変種 0 と同じモデルが入る。(データ)
- マップのないダンジョンの階 (生成、§4) も同じ表を使う。描き分け `FUN_00199584` はセル +0x00 の行の `+0x0C + 0x20 × タイルセット` から、乱数で変種を選ぶか (セルの設定による) セル +0x14 の変種で 1 つ選ぶ。(コード)

**タイルセットとアーカイブ**:

- タイルセット = mapData (master エントリ 33、15 × 0xC、保持体 +0x3D4) の行 +0x00 (0〜7)。行 +0x06 が mapResource の行。実データでは mapResource の行 = タイルセット + 1。(コード `FUN_00197300` 付近 + データ)
- mapData の行は、階の定義の頭 +0x14 (§4.2) が 0 でなければそのキー (mapData の追加領域) の行、0 なら dungeonData +0x16 の値 (`FUN_00197300` 付近、0x19736C〜0x197388)。(コード。0x197380 で読む行が dungeonData であることは、この規則で全マップのモデルが揃うことからの推定)
- mapResource (master エントリ 37、9 × 0x14): +0x00 タイルのモデルのアーカイブ (`46910AB6` ほか 8 つ)、+0x04 テクスチャ (`469B3DC6` のエントリ)、+0x08 モデルのアーカイブのエントリ (用途は未確認)、+0x0C どのアーカイブにもないエントリ、+0x10 の 3 バイトは色と推定。(コード `FUN_00197564`〜 + データ)
- mapData の行の残り: +0x05 も mapResource の行、+0x07 は音 (`FUN_0020C2A0` に渡す) と推定、+0x08 (0x3D〜0x41) は別の物体の +3 に写す。(コード、意味は推定)

**作り込みの部屋 (designedMap)**: 階の定義の頭 +0x4C (§4.2) が designedMap のキーのとき、`FUN_00197300` はタイルのモデルを組まず、designedMap の行 +0x04 を `AD853AFD` のエントリ (部屋まるごとのモデル)、+0x08 を mapResource の行として読む (0x197440〜)。designedMap の 83 行は、+0x04 を持つ頭の行 (15 行) と、その後ろの位置・回転 (+0x0C s16・+0x10 s16・+0x12 s16 の度)・種類 (+0x18)・番号 (+0x19、mapObject の行と推定) を持つ行に分かれる。頭 +0x4C を持つ 20 記録 (ボスの部屋など、§4.2) がこれを使う。(コード + データ、後ろの行の意味は推定)

## 4. ダンジョンの階の定義 ("261" ファイル)

`A90C8038` のエントリ 0004〜0021 (18 個) は、先頭が `32 36 31 00` ("261") の独自形式。中身は「記録」の並びで、1 記録が 1 つの階 (または階の中の区域) に当たる。

### 4.1 ファイルと読み手

- 読み込み: `FUN_001BF7xx` (0x1BF838〜) が dungeonData の行を引き、行の +0x00 と +0x04 を `FUN_001B0144` に渡す。+0x04 (u32) が `A90C8038` のエントリのハッシュで、`FUN_001AFF80` がそのファイルを開いて 0x173F0 B の物体に展開する。(コード)
- 展開 `FUN_0025E0EC`: +0x04 の u32 が記録の数。+0x08 から記録を順に読み、記録の先頭へのポインタを配列に積む。記録は 0x64 B の頭と、`u32 件数 + 件数 × 要素` の配列 9 つ。読み飛ばしの要素の大きさは順に 20・12・12・12・12・6・8・12・4 B (`FUN_001DBC70` が配列 0〜3 を、`FUN_0025E0EC` が 4〜8 を飛ばす)。18 ファイルすべてで記録を読み終えた位置がファイルの大きさと一致する。(確定)
- 記録ごとの設定 `FUN_002A66DC(階の物体, ファイル, 記録)`: 記録の欄を 0x2D4458〜0x2D4F9C の小さな読み出し関数で 1 つずつ読み、階の物体 (0x770 B、最大 50 階 = `FUN_001AFF80` の 0x32) に写す。配列の要素は上限まで写し、それ以上は捨てる (上限は §4.3 の表)。(コード)
- 記録の数は物体 +0x04 (`FUN_001EA504`)、記録 i は `FUN_001EA4F0`、記録の id から記録を探すのは `FUN_002D4458`。(コード)
